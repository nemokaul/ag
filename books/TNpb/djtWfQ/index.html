Optimizing Performance in React Applications

Performance optimization in React operates on two fronts: actual performance (how fast things happen) and perceived performance (how fast things feel). A network request that takes 500ms is slow, but if users see immediate feedback, a loading state, an optimistic update, it feels responsive. React 19's architecture supports both through concurrent rendering, which allows React to interrupt and prioritize work, and transitions, which let you mark updates as non-urgent so the UI stays responsive during heavy computation.

This chapter builds on the rendering concepts from earlier chapters and connects them to measurable outcomes. We'll focus on Core Web Vitals, Largest Contentful Paint (LCP) for load performance, Interaction to Next Paint (INP) for responsiveness, and Cumulative Layout Shift (CLS) for visual stability, because these are the metrics that reflect real user experience and impact search rankings. Beyond metrics, we'll explore the mechanisms React provides: memoization to skip unnecessary work, code splitting to reduce initial bundle size, and Suspense to coordinate loading states. The goal isn't to optimize everything, but to identify what actually matters and measure whether your changes make a difference.

In this chapter, we will cover the following topics:

  • Performance optimization techniques for React apps
  • Tools and libraries for performance monitoring
  • Hydration performance
  • Advanced performance enhancements in React 19

Understanding React's rendering and reconciliation process

Before we can optimize effectively, we need to understand what actually makes DOM operations expensive. A single DOM update is cheap. What's expensive is layout thrashing, repeatedly reading and writing to the DOM in a way that forces the browser to recalculate layout multiple times. When you read a layout property (like offsetHeight), the browser must flush any pending style changes to give you an accurate value. If you then write to the DOM and read again, you've forced two layout calculations instead of one. React's reconciliation process helps by batching updates: instead of updating the DOM after each state change, React collects changes, diffs them against the current state, and applies them in a single pass. This minimizes reflows and avoids interleaved reads and writes. But React can't fix everything, if your components trigger layout reads during render or effects, you can still cause layout thrashing within a single React commit.

How React's Fiber tree works

When you write JSX, you're not creating DOM elements, you're creating React elements, lightweight JavaScript objects that describe what the UI should look like. A component that returns <div className="card">Hello</div> actually returns an object like { type: 'div', props: { className: 'card', children: 'Hello' } }. React maintains these elements in a structure called the Fiber tree, which tracks each component's state, props, and position in the UI hierarchy.

When state changes, React builds a new tree of elements and compares it against the current Fiber tree, a process called reconciliation. React walks both trees, identifies what changed, and computes the minimum set of DOM operations needed. This comparison happens in JavaScript, which is fast; the actual DOM updates are batched and applied together at the end.

Batching is key to React's efficiency. Multiple state updates that happen in the same event handler or effect are processed in a single pass. If you call setCount(1), setName('Carlos'), and setActive(true) in the same click handler, React doesn't re-render three times, it batches them into one render, one reconciliation, and one DOM commit. This reduces layout calculations and keeps the UI responsive:

import { useState } from 'react';
interface User {
 name: string;
 email: string;
 preferences: { theme: string; notifications: boolean };
}
const UserProfile = () => {
 const [user, setUser] = useState<User>({
   name: 'Carlos Santana',
   email: 'carlos@example.com',
   preferences: { theme: 'dark', notifications: true }
 });
 const updatePreferences = () => {
   // These updates are batched automatically since React +18
   setUser(prev => ({ ...prev, preferences: { ...prev.preferences, theme: 'light' } }));
   setUser(prev => ({ ...prev, preferences: { ...prev.preferences, notifications: false } }));
   // Only one re-render occurs despite two state updates
 };
 return (
   <div className="max-w-md mx-auto p-6 bg-white rounded-lg shadow-lg">
     <h2 className="text-2xl font-bold mb-4">{user.name}</h2>
     <p className="text-gray-600 mb-2">{user.email}</p>
     <div className="mt-4 p-4 bg-gray-50 rounded">
       <p className="text-sm">Theme: {user.preferences.theme}</p>
       <p className="text-sm">Notifications: {user.preferences.notifications ? 'On' : 'Off'}</p>
     </div>
     <button
       onClick={updatePreferences}
       className="mt-4 px-4 py-2 bg-blue-600 text-white rounded hover:bg-blue-700"
     >
       Update Preferences
     </button>
   </div>
 );
};

In this example, the two state updates inside updatePreferences are automatically batched together, resulting in only one re-render. This is automatic batching, a feature that became default in React 18, and it applies to updates inside event handlers, promises, timeouts, and even native events.

Understanding reconciliation and the Fiber architecture

React's update process involves two distinct phases handled by separate systems. The Reconciler determines what changed by comparing the previous and next element trees. The Renderer (ReactDOM for browsers, React Native for mobile) applies those changes to the actual platform. This separation is why React can target multiple platforms, the reconciliation logic stays the same, only the renderer changes.

The reconciliation algorithm uses heuristics to achieve O(n) complexity instead of the O(n³) that a full tree diff would require. These are shortcuts, not sophisticated analysis:

  • React only compares elements at the same level in the tree. If you move a component from one parent to another, React doesn't detect the move, it destroys the old instance and creates a new one. Any local state, form input values, scroll position, or focus is lost. This is a limitation you need to design around, not a feature.
  • If an element's type changes, say, from <div> to <section>, or from <Input> to <TextArea>, React destroys the entire subtree and rebuilds it. This is a destructive operation. Components inside that subtree unmount, their state disappears, and effects clean up. React assumes that different types produce different trees, which is usually true, but you pay the cost when it happens.
  • When rendering lists, React uses the key prop to track identity across renders. Without stable keys, React can't tell if an item moved, was added, or was removed, it falls back to index-based comparison, which causes unnecessary unmounts and remounts when the list order changes.

Here's how stable keys look in practice, each task uses its unique id rather than the array index. This matters because when items are reordered, added, or removed, React uses keys to track which DOM elements correspond to which data. If you use array indices as keys, React sees position, not identity: removing the first item makes React think every subsequent item changed because their indices all shifted. With stable IDs, React correctly identifies that only one item was removed and leaves the others untouched, preserving their DOM state, input values, and focus:

The key prop in this task list isn't just a formality, it's critical for performance. When a task's completed status changes, React can identify exactly which DOM element corresponds to that task and update only that element, rather than recreating the entire list.

When and why React re-renders components

Understanding when React re-renders is crucial for optimization. A component re-renders in four scenarios: when its state changes, when its parent re-renders, when a context it consumes changes, or when a custom hook it uses triggers an update. Notice that props change isn't on this list. By default, React doesn't compare props at all. When a parent re-renders, all children re-render unconditionally, regardless of whether their props changed.

This might seem wasteful, but it's a deliberate design choice. React prioritizes a simple mental model over complex dependency tracking. Instead of analyzing which props actually changed and which components truly need updates, React re-renders the entire subtree and trusts that the reconciliation process will minimize actual DOM mutations. For most applications, this works fine, JavaScript is fast, and the Fiber architecture can interrupt work if higher-priority updates arrive.

React provides memo() to opt into props comparison, but reach for it carefully. Wrapping everything in memo hurts code readability and adds overhead: React must now compare all props on every parent render. For components that receive complex objects or functions as props, that comparison runs on every render and the component re-renders anyway unless you also stabilize those props with useMemo and useCallback. Sometimes the cost of comparison exceeds the cost of just re-rendering. Profile first, then optimize the components where unnecessary re-renders actually cause measurable problems.

Here's an example where memo() makes sense, the dashboard's refresh counter updates frequently, but the metric cards don't need to re-render since their data hasn't changed:

import { useState, memo } from 'react'
interface MetricCardProps {
 title: string;
 value: number;
 change: number;
 icon: string;
}
const MetricCard = memo(({ title, value, change, icon }: MetricCardProps) => {
 console.log(`Rendering: ${title}`)

 return (
   <div className="p-6 bg-white rounded-lg shadow-md">
     <div className="flex items-center justify-between mb-2">
       <span className="text-gray-600 text-sm font-medium">{title}</span>
       <span className="text-2xl">{icon}</span>
     </div>
     <div className="text-3xl font-bold text-gray-900">{value.toLocaleString()}</div>
     <div className={`text-sm mt-2 ${change >= 0 ? 'text-green-600' : 'text-red-600'}`}>
       {change >= 0 ? '↑' : '↓'} {Math.abs(change)}% from last month
     </div>
   </div>
 )
})

 { title: 'Total Users', value: 12543, change: 12.5, icon: '' },
 { title: 'Revenue', value: 54320, change: 8.3, icon: '' },
 { title: 'Active Sessions', value: 1834, change: -3.2, icon: '' }
]

 const [refreshCount, setRefreshCount] = useState(0)
 const [selectedMetric, setSelectedMetric] = useState<string | null>(null)
 return (
   <div className="max-w-6xl mx-auto p-6">
     <div className="flex justify-between items-center mb-6">
       <h1 className="text-3xl font-bold">Dashboard</h1>
       <button
         onClick={() => setRefreshCount(c => c + 1)}
         className="px-4 py-2 bg-blue-600 text-white rounded hover:bg-blue-700"
       >
         Refresh {refreshCount}
       </button>
     </div>
     <div className="grid grid-cols-1 md:grid-cols-3 gap-6">
       {metrics.map((metric) => (
         <MetricCard key={metric.title} {...metric} />
       ))}
     </div>
   </div>
 )
}

The MetricCard component is wrapped in memo(), which tells React to skip re-rendering if the props haven't changed. When you click the refresh button, the Dashboard component re-renders completely, it executes its function body and creates new React element objects for each MetricCard. However, memo() intercepts this: React compares the new props against the previous props, and if they're equal, it reuses the cached render result instead of executing the MetricCard function body.

A critical detail: memo() uses shallow comparison. It checks if prevProps.title === nextProps.title, prevProps.value === nextProps.value, and so on. This works here because all props are primitives (strings and numbers). If you passed an object or array as a prop, say, data={{ value: 100 }}, a new object is created on every parent render, and shallow comparison sees different references even when the content is identical. The memoization breaks, and the component re-renders anyway. To handle complex props, you'd need to stabilize references with useMemo() or provide a custom comparison function as memo()'s second argument.

Performance optimization techniques for React apps

Now that we understand how React works under the hood, let's explore practical techniques for optimizing our applications. Performance optimization should be data-driven: measure first, identify bottlenecks, apply targeted fixes, then measure again to verify improvement. Without measurement, you're guessing, and often optimizing code that wasn't a problem while ignoring the actual bottlenecks.

Start with React DevTools Profiler, which shows you exactly which components rendered, how long each render took, and what triggered the update. Chrome DevTools' Performance tab captures a broader picture, JavaScript execution, layout calculations, paint operations, and helps identify whether your problem is React-specific or browser-level. For production monitoring, Lighthouse and Web Vitals give you the Core Web Vitals metrics (LCP, INP, CLS) that reflect real user experience.

Avoiding unnecessary state updates and re-renders

One of the most common performance pitfalls in React applications is creating new object references unnecessarily. JavaScript's equality comparison for objects and arrays is based on reference, not value. This means {a: 1} is never equal to {a: 1}, they're different objects, even though their contents are identical.

This becomes a problem when you pass objects or functions as props. If you create a new object or function on every render, React's memoization tools can't help you because the props appear different every time.

Historically, developers solved this with useMemo() and useCallback() to stabilize references manually. React Compiler (previously called React Forget) changes this, it analyzes your code at build time and automatically inserts memoization where beneficial. If your project uses React 19 with the compiler enabled, you don't need to think about most of these reference stability issues; the compiler handles them.

That said, understanding why reference equality matters is still valuable. The compiler isn't magic; it follows the same rules you would. Knowing when and why references break memoization helps you debug unexpected re-renders, understand the compiler's output, and work in codebases that haven't adopted it yet. The patterns that follow apply whether you're writing manual memoization or reviewing what the compiler generated:

import { useState, useMemo, useCallback, memo } from 'react'
interface Product {
 id: string
 name: string
 price: number
 category: string
}
interface ProductListProps {
 products: Product[]
 onProductClick: (product: Product) => void
}
// memo() prevents re-renders when products and onProductClick references are stable
const ProductList = memo(({ products, onProductClick }: ProductListProps) => {
 console.log('ProductList rendered')
 return (
   <div className="grid grid-cols-2 gap-4">
     {products.map(product => (
       <div
         key={product.id}
         onClick={() => onProductClick(product)}
         className="p-4 bg-white rounded-lg shadow cursor-pointer"
       >
         <h3 className="font-medium">{product.name}</h3>
         <p className="text-gray-500">{product.category}</p>
         <p className="text-blue-600 font-bold">${product.price}</p>
       </div>
     ))}
   </div>
 )
})
const allProducts: Product[] = [
 { id: '1', name: 'Laptop Pro', price: 1299, category: 'Electronics' },
 { id: '2', name: 'Wireless Mouse', price: 29, category: 'Electronics' },
 { id: '3', name: 'Office Chair', price: 299, category: 'Furniture' }
]
const ProductStore = () => {
 const [category, setCategory] = useState('all')
 const [search, setSearch] = useState('')
 // useMemo: only recompute filtered list when category or search changes
 // Without this, filtering runs on every render even if inputs haven't changed
 const filteredProducts = useMemo(() => {
   return allProducts.filter(product => {
     const matchesCategory = category === 'all' || product.category === category
     const matchesSearch = product.name.toLowerCase().includes(search.toLowerCase())
     return matchesCategory && matchesSearch
   })
 }, [category, search])
 // useCallback: stable function reference across renders
 // Without this, memo() on ProductList is useless—new function = new props
 const handleProductClick = useCallback((product: Product) => {
   console.log('Clicked:', product.name)
 }, [])
 return (
   <div className="p-6">
     <div className="flex gap-4 mb-6">
       <input
         type="text"
         placeholder="Search..."
         value={search}
         onChange={(e) => setSearch(e.target.value)}
         className="flex-1 px-4 py-2 border rounded-lg"
       />
       <select
         value={category}
         onChange={(e) => setCategory(e.target.value)}
         className="px-4 py-2 border rounded-lg"
       >
         <option value="all">All</option>
         <option value="Electronics">Electronics</option>
         <option value="Furniture">Furniture</option>
       </select>
     </div>
     {/* Both props are now stable references, so memo() actually works */}
     <ProductList products={filteredProducts} onProductClick={handleProductClick} />
   </div>
 )
}

The useMemo hook caches the result of the filtering operation, recalculating only when category or search changes. This doesn't prevent ProductList from re-rendering when you type, if the search term changes, useMemo recalculates the filtered array, returns a new reference, and ProductList re-renders with the new results. That's correct behavior. What useMemo prevents is running the filtering logic when unrelated state changes. If this component had other state, say, a modal open/closed toggle, the filter would normally recalculate on every render even though its inputs haven't changed. With useMemo, React skips the calculation and returns the cached array.

The useCallback hook serves a different purpose: it keeps the function reference stable across renders. Without it, memo() on ProductList would be useless, a new function is created on every render, memo() sees different props, and the component re-renders regardless. Together, useMemo and useCallback ensure that ProductList only re-renders when the actual data changes, not when unrelated parts of the parent update.

Managing large data sets efficiently with virtualization

When dealing with large lists (hundreds or thousands of items), rendering every item at once can grind your application to a halt. The solution is virtualization: only rendering the items that are currently visible in the viewport.

Virtualization dramatically reduces the number of DOM nodes in your application. Instead of rendering 10,000 list items, you might render only 20, the ones the user can actually see. As the user scrolls, the library calculates which items should be visible and renders only those, unmounting items that scroll out of view. Most virtualization libraries also support an overscan setting, rendering a few extra items above and below the visible area so content is ready before the user scrolls to it, reducing flicker on fast scrolling:


import { useState, useCallback, useMemo, useRef, useEffect } from 'react'
// Generic type T allows this component to work with any data type
// VirtualList<Message> renders messages, VirtualList<Product> renders products
interface VirtualListProps<T> {
 items: T[]
 itemHeight: number
 containerHeight: number
 overscan?: number
 // renderItem receives the typed item, ensuring type safety in the callback
 renderItem: (item: T, index: number) => React.ReactNode
}
// The <T> after function name makes this a generic function component
// TypeScript infers T from the items array you pass in
function VirtualList<T>({ 
 items,
 itemHeight,
 containerHeight,
 overscan = 3,
 renderItem
}: VirtualListProps<T>) {
 const [scrollTop, setScrollTop] = useState(0)
 const rafId = useRef<number | null>(null)
 // Cancel any pending animation frame on unmount
 // Prevents "setState on unmounted component" warnings
 useEffect(() => {
   return () => {
     if (rafId.current) {
       cancelAnimationFrame(rafId.current)
     }
   }
 }, [])
 // Throttle scroll updates to animation frames
 // Without this, scroll fires 60-120 times/second, each triggering a state update
 const handleScroll = useCallback((e: React.UIEvent<HTMLDivElement>) => {
   const target = e.currentTarget
   if (rafId.current) cancelAnimationFrame(rafId.current)
   rafId.current = requestAnimationFrame(() => setScrollTop(target.scrollTop))
 }, [])
 const { visibleItems, offsetY, totalHeight } = useMemo(() => {
   const start = Math.max(0, Math.floor(scrollTop / itemHeight) - overscan)
   const end = Math.min(items.length, Math.ceil((scrollTop + containerHeight) / itemHeight) + overscan)
  
   return {
     visibleItems: items.slice(start, end).map((item, i) => ({ item, index: start + i })), 
     offsetY: start * itemHeight,
     totalHeight: items.length * itemHeight
   }
 }, [items, itemHeight, containerHeight, scrollTop, overscan])
 return (
   <div onScroll={handleScroll} style={{ height: containerHeight, overflow: 'auto' }}>
     <div style={{ height: totalHeight, position: 'relative' }}>
       <div style={{ transform: `translateY(${offsetY}px)` }}>
         {visibleItems.map(({ item, index }) => (
           <div key={index} style={{ height: itemHeight }}>
             {renderItem(item, index)}
           </div>
         ))}
       </div>
     </div>
   </div>
 )
}
interface Message {
 id: string
 sender: string
 content: string
}
const MessageList: React.FC = () => {
 const messages = useMemo<Message[]>(() =>
   Array.from({ length: 10000 }, (_, i) => ({
     id: `msg-${i}`,
     sender: `User ${i % 50}`,
     content: `Message content ${i} - Sample text for virtualization demo.`
   })), [])
 const renderMessage = useCallback((message: Message) => (
   <div className="p-3 border-b border-gray-100">
     <span className="font-medium">{message.sender}</span>
     <p className="text-gray-600">{message.content}</p>
   </div>
 ), [])
 return (
   <div className="max-w-2xl mx-auto p-4">
     <h2 className="text-xl font-bold mb-4">Messages (10,000 items)</h2>
     <VirtualList
       items={messages}
       itemHeight={72}
       containerHeight={400}
       overscan={5}
       renderItem={renderMessage}
     />
   </div>
 )
}

The requestAnimationFrame throttling ensures scroll updates align with the browser's repaint cycle, at most one state update per frame. The overscan prop renders extra items beyond the visible area to prevent blank flashes during fast scrolling. For production use, libraries like @tanstack/react‑virtual handle additional edge cases such as variable-height items and horizontal scrolling.

Lazy loading components and code splitting with React Suspense

Your application doesn't need to load everything at once. Code splitting breaks your JavaScript bundle into smaller chunks that load on demand. Before implementing manual code splitting, know that modern frameworks like Next.js, Remix, and React Router v7 handle route-based splitting automatically, you get it for free.

Manual lazy loading makes sense for components that are genuinely heavy (100KB+ after minification), conditionally rendered, and not needed on initial page load. Common examples include rich text editors, charting libraries, or PDF viewers. For smaller components, the overhead of an extra network request can exceed the savings.

The basic pattern uses lazy() with Suspense, but this naive approach has problems:

import { lazy, Suspense, useState } from 'react'
// Components load only when rendered—but this creates a network waterfall
const HeavyChart = lazy(() => import('./HeavyChart'))
const HeavyDataTable = lazy(() => import('./HeavyDataTable'))
const Analytics = () => {
 const [activeTab, setActiveTab] = useState<'overview' | 'chart' | 'data'>('overview')
 return (
   <div className="p-6">
     <div className="flex gap-4 mb-6">
       <button onClick={() => setActiveTab('overview')}>Overview</button>
       <button onClick={() => setActiveTab('chart')}>Charts</button>
       <button onClick={() => setActiveTab('data')}>Data</button>
     </div>
     {/* Problem: switching tabs unmounts components, losing all state */}
     {/* Problem: spinner shows even for fast loads, causing flash */}
     <Suspense fallback={<div>Loading...</div>}>
       {activeTab==='chart'&&<HeavyChart />}
       {activeTab==='data'&&<HeavyDataTable />}
     </Suspense>
   </div>
 )
}
A better approach prefetches on hover so content is ready when clicked:
import { lazy, Suspense, useState, useTransition } from 'react'
const HeavyChart = lazy(() => import('./HeavyChart'))
const HeavyDataTable = lazy(() => import('./HeavyDataTable'))
// Prefetch functions—call these on hover
const prefetchChart = () => import('./HeavyChart')

 }
 return (

     <div className="flex gap-4 mb-6">
       <button onClick={() => handleTabChange('overview')}>
         Overview
       </button>
       <button
         onClick={() => handleTabChange('chart')}
         onMouseEnter={prefetchChart}
       >
         Charts
       </button>
       <button
         onClick={() => handleTabChange('data')}
         onMouseEnter={prefetchDataTable}
       >
         Data
       </button>
     </div>

The new component

The prefetch approach still has a limitation: switching tabs unmounts the previous component, losing any internal state like form inputs, scroll position, or chart zoom settings. React 19 introduces the <Activity> component which keeps components mounted but hidden, preserving their state:

import { lazy, Suspense, useState, useTransition, Activity } from 'react'
const HeavyChart = lazy(() => import('./HeavyChart'))
const HeavyDataTable = lazy(() => import('./HeavyDataTable'))
const prefetchChart = () => import('./HeavyChart')
const prefetchDataTable = () => import('./HeavyDataTable')
const Analytics = () => {
 const [activeTab, setActiveTab] = useState<'overview' | 'chart' | 'data'>('overview')
 const [isPending, startTransition] = useTransition()
 const handleTabChange = (tab: typeof activeTab) => {
   startTransition(() => setActiveTab(tab))
 }
 return (
   <div className="p-6">
     <div className="flex gap-4 mb-6">
       <button onClick={() => handleTabChange('overview')}>Overview</button>
       <button onClick={() => handleTabChange('chart')} onMouseEnter={prefetchChart}>
         Charts
       </button>
       <button onClick={() => handleTabChange('data')} onMouseEnter={prefetchDataTable}>
         Data
       </button>
     </div>
     <div className={isPending ? 'opacity-50' : ''}>
       <Suspense fallback={<div>Loading...</div>}>
         {/* Activity keeps components mounted but hidden when mode="hidden" */}
         {/* All state is preserved: form inputs, scroll position, selections */}
         <Activity mode={activeTab === 'overview' ? 'visible' : 'hidden'}>
           <div>Welcome to Analytics</div>
         </Activity>
         <Activity mode={activeTab === 'chart' ? 'visible' : 'hidden'}>
           <HeavyChart />
         </Activity>
         <Activity mode={activeTab === 'data' ? 'visible' : 'hidden'}>
           <HeavyDataTable />
         </Activity>
       </Suspense>
     </div>
   </div>
 )
}

With <Activity>, when you switch from the chart tab to the data tab, the chart component stays mounted but enters a hidden state. This isn't just CSS display: none, React treats hidden components differently at the scheduler level. Effects are deferred until the component becomes visible again, so a hidden component won't make network requests or set up subscriptions while offscreen. Update priority is lowered, meaning React deprioritizes re-renders for hidden content in favor of visible UI. The component's state (zoom level, selected data points, form inputs) remains intact, but React avoids wasting resources on content the user can't see. When you switch back, the component reactivates instantly without remounting or refetching data. Its state, zoom level, selected data points, any ongoing animations, remains intact. When you switch back, it reappears instantly without reloading data or resetting state. The tradeoff is higher memory usage since all visited tabs remain in memory, but for complex interactive components, preserved state provides a significantly better user experience.

Optimizing event handling and listeners

Event handlers can be a hidden source of performance issues, especially when dealing with high-frequency events like scrolling, resizing, or mouse movements. Each time these events fire, your handler executes, and if that handler is expensive, you'll notice janky, unresponsive behavior.

Debouncing and throttling are two techniques for controlling how often a function executes. Debouncing waits until events stop firing before executing the handler, while throttling ensures the handler executes at most once per specified time period.

Let's look at debouncing and throttling separately. Debouncing delays execution until activity stops, ideal for search inputs where you want the final value, not intermediate keystrokes:

import { useState, useEffect } from 'react'
function useDebounce<T>(value: T, delay: number): T {
 const [debouncedValue, setDebouncedValue] = useState(value)
 useEffect(() => {
   const handler = setTimeout(() => {
     setDebouncedValue(value)
   }, delay)
   // Cancel and restart if value changes before delay completes
   return () => clearTimeout(handler)
 }, [value, delay])
 return debouncedValue
}
function SearchInput() {
 const [searchTerm, setSearchTerm] = useState('')
 const debouncedSearch = useDebounce(searchTerm, 500)
 useEffect(() => {
   if (debouncedSearch) {
     console.log('Searching for:', debouncedSearch)
     // API call goes here
   }
 }, [debouncedSearch])
 return (
   <input
     value={searchTerm}
     onChange={(e) => setSearchTerm(e.target.value)}
     placeholder="Type to search..."
   />
 )
}

Throttling limits execution rate, ideal for continuous events like scrolling or mouse movement where you need updates but not 60 per second:

import { useRef, useCallback, useEffect } from 'react'
// This implementation includes "trailing edge" -
// ensures the final value is captured even if events stop
function useThrottle<T extends (...args: any[]) => any>(
 callback: T,
 delay: number
) {
 const lastRun = useRef(Date.now())
 const timeoutRef = useRef<NodeJS.Timeout | null>(null)
 const lastArgs = useRef<Parameters<T> | null>(null)
 // Cleanup on unmount
 useEffect(() => {
   return () => {
     if (timeoutRef.current) clearTimeout(timeoutRef.current)
   }
 }, [])
 return useCallback((...args: Parameters<T>) => {
   const now = Date.now()
   lastArgs.current = args
   if (now - lastRun.current >= delay) {
     // Enough time passed - run immediately
     callback(...args)
     lastRun.current = now
   } else {
     // Schedule trailing edge call to capture final value
     if (timeoutRef.current) clearTimeout(timeoutRef.current)
     timeoutRef.current = setTimeout(() => {
       if (lastArgs.current) {
         callback(...lastArgs.current)
         lastRun.current = Date.now()
       }
     }, delay - (now - lastRun.current))
   }
 }, [callback, delay])
}
function MouseTracker() {
 const [position, setPosition] = useState({ x: 0, y: 0 })
 const handleMouseMove = useThrottle((e: React.MouseEvent) => {
   setPosition({ x: e.clientX, y: e.clientY })
 }, 100)
 return (
   <div onMouseMove={handleMouseMove} className="h-64 bg-gray-100">
     Position: ({position.x}, {position.y})
   </div>
 )
}

The throttle implementation includes a trailing edge. When events stop, it fires one final time with the last captured value. Without this, rapid mouse movement that stops suddenly would lose the final position. Debouncing is for wait until done scenarios; throttling is for execute regularly but not too often.

While React's Profiler focuses on component-level performance, Web Vitals measure the user experience of your entire application. The Core Web Vitals are three metrics that directly correlate with how users perceive your application's speed and responsiveness:

Hydration performance

Hydration is the process where React takes over server-rendered HTML and makes it interactive. During hydration, React reconstructs its internal representation of the component tree, attaches event listeners, and sets up state management, all while ensuring the existing DOM matches what React would have rendered. Poor hydration performance can make your application feel unresponsive during the critical first seconds after load.

Understanding hydration costs

Hydration isn't free. React must walk through your entire component tree, execute every component function, and reconcile with the existing DOM. The more components you have, the longer this takes. Users see your content but can't interact with it, buttons don't respond, forms don't work, until hydration completes:

// components/HydrationMonitor.tsx - Measure hydration time
'use client'
import { useEffect, useState } from 'react'
interface HydrationMetrics {

 const [metrics, setMetrics] = useState<HydrationMetrics | null>(null)

   setMetrics({
     hydrationTime: Math.round(hydrationEnd - hydrationStart),
     componentCount,
   })
   // Report to analytics
   if (process.env.NODE_ENV === 'production') {
     // sendToAnalytics('hydration', { hydrationTime, componentCount })
   }

}

Partial pre-rendering (PPR)

Next.js 15 introduces Partial Pre-rendering (PPR), which takes this further by combining static and dynamic rendering in a single request.

PPR is an experimental technology that is not recommended for production. You may run into some DX issues, especially on larger code bases.

With PPR, the static shell of your page (header, layout, static content) is pre-rendered at build time and served instantly from the CDN, while dynamic parts (user-specific content, real-time data) stream in afterward. This means users see a complete-looking page immediately, with interactive elements hydrating as their code arrives:

import { ProductGrid } from './ProductGrid' // Static - pre-rendered
// Dynamic components stream in after initial render
import { UserGreeting } from './UserGreeting'
import { RecommendedProducts } from './RecommendedProducts'
export default function HomePage() {
 return (
   <>
     {/* Static shell - served instantly from CDN */}
     <Header />
    
     {/* Dynamic - streams in after authentication check */}
     <Suspense fallback={<div className="h-8 bg-gray-200 animate-pulse" />}>
       <UserGreeting />
     </Suspense>
    
     {/* Static product grid - pre-rendered */}
     <ProductGrid />
    
     {/* Dynamic recommendations - streams based on user history */}
     <Suspense fallback={<RecommendationsSkeleton />}>
       <RecommendedProducts />
     </Suspense>
   </>
 )
}

To enable PPR you need to update your next.config.ts file:

PPR reduces hydration scope because the static parts don't need hydration at all, they're plain HTML. Only the dynamic, interactive components require JavaScript and hydration, and they load in priority order based on their position in the Suspense tree. This is different from traditional SSR where the entire page hydrates as a unit; with PPR, you get the best of static generation (instant load, CDN caching) and dynamic rendering (personalization, real-time data) in the same page.

Advanced performance enhancements in React 19

React introduces several powerful features that push the boundaries of what's possible with web applications. These features aren't just incremental improvements, they represent fundamental shifts in how we think about React application architecture.

Leveraging concurrent rendering for a more responsive UI

Concurrent rendering allows React to work on multiple versions of the UI simultaneously. This might sound complex, but the result is straightforward: your application stays responsive even during expensive updates. React can pause, resume, or abandon work as needed, prioritizing urgent updates like user input over less critical updates like animations.

The beauty of concurrent rendering is that you don't need to do anything special to enable it, it's automatically available in React 18 and later. However, you can leverage specific APIs to take full advantage of it:

import { useState, useTransition, useMemo } from 'react'

 id: number
 name: string
 category: string
 price: number
}
// Generate products once, outside the component
const products: Product[] = Array.from({ length: 5000 }, (_, i) => ({
 id: i,
 name: `Product ${i}`,
 category: ['Electronics', 'Clothing', 'Home', 'Sports'][i % 4],
 price: Math.floor(Math.random() * 1000) + 10
}))
const SearchableProductCatalog = () => {
 // Two separate states: one for input, one for filtering
 const [inputValue, setInputValue] = useState('')
 const [filterQuery, setFilterQuery] = useState('')
 const [isPending, startTransition] = useTransition()
 // Only recalculate when filterQuery changes
 const filteredProducts = useMemo(() => {
   return products.filter(product =>
     product.name.toLowerCase().includes(filterQuery.toLowerCase()) ||
     product.category.toLowerCase().includes(filterQuery.toLowerCase())
   )
 }, [filterQuery])
 const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
   const value = e.target.value
  
   // Urgent: update input immediately so typing feels instant
   setInputValue(value)
  
   // Non-urgent: update filter with low priority
   // React can interrupt this if user keeps typing
   startTransition(() => {
     setFilterQuery(value)
   })
 }
 return (
   <div className="p-6 max-w-4xl mx-auto">
     <div className="mb-6">
       <div className="relative">
         <input
           type="text"
           value={inputValue}
           onChange={handleChange}
           placeholder="Search 5,000 products..."
           className="w-full px-4 py-3 border rounded-lg"
         />
         {/* isPending is true while the transition is processing */}
         {isPending && (
           <div className="absolute right-3 top-1/2 -translate-y-1/2">
             <div className="w-5 h-5 border-2 border-blue-600 border-t-transparent rounded-full animate-spin" />
           </div>
         )}
       </div>
       <p className="text-sm text-gray-500 mt-2">
         Found {filteredProducts.length} products
       </p>
     </div>
     {/* Dim the list while transition is pending */}
     <div className={`grid grid-cols-2 gap-4 ${isPending ? 'opacity-50' : ''}`}>
       {filteredProducts.slice(0, 50).map(product => (
         <div key={product.id} className="p-4 bg-white rounded-lg shadow">
           <h3 className="font-medium">{product.name}</h3>
           <p className="text-gray-600 text-sm">{product.category}</p>
           <p className="text-blue-600 font-bold">${product.price}</p>
         </div>
       ))}
     </div>
   </div>
 )
}

The useTransition hook marks the filter update as non-urgent, allowing React to keep the input responsive even while filtering through 5,000 products. The key is separating state: inputValue updates immediately on every keystroke so typing feels instant, while filterQuery updates inside startTransition so React can interrupt and restart the expensive filtering if the user keeps typing. The isPending boolean lets you show visual feedback, here a spinner and dimmed list, while the transition processes. This pattern works because React treats the two state updates differently: the urgent one commits immediately, the non-urgent one can be interrupted and deferred.

Using startTransition for non-urgent UI updates

The startTransition API is your way of telling React, "This update is important, but it's not urgent." React will complete this update when it has time, but it won't let it interfere with more urgent updates like user input or animations.

This is useful for updates that trigger expensive rendering but aren't directly tied to user interaction, like updating a large data visualization or recalculating complex layouts:

import { useState, useTransition } from 'react'
interface Tab {
 id: string
 title: string
 content: string
}
// Simulates a heavy component that takes time to render
// In real apps, this might be a complex chart, data grid, or form
const HeavyTabContent = ({ content }: { content: string }) => {
 const items = Array.from({ length: 1000 }, (_, i) => `${content} - Item ${i}`)
 return (
   <div className="space-y-2">
     {items.map((item, index) => (
       <div key={`content-${index}`} className="p-2 bg-gray-50 rounded">
         {item}
       </div>
     ))}
   </div>
 )
}
// Tabs defined outside component to avoid recreation on each render
const tabs: Tab[] = [
 { id: 'tab1', title: 'Dashboard', content: 'Dashboard Data' },
 { id: 'tab2', title: 'Analytics', content: 'Analytics Data' },
 { id: 'tab3', title: 'Reports', content: 'Report Data' },
 { id: 'tab4', title: 'Settings', content: 'Settings Data' }
]
const TabNavigator = () => {
 const [activeTab, setActiveTab] = useState('tab1')
 // isPending: true while transition is processing
 // startTransition: wraps state updates to mark them as non-urgent
 const [isPending, startTransition] = useTransition()
 const handleTabChange = (tabId: string) => {
   // Without startTransition, clicking a tab would freeze the UI
   // until HeavyTabContent finishes rendering 1,000 items
   // With startTransition, the tab click feels instant—React keeps
   // the old content visible while preparing the new content
   startTransition(() => {
     setActiveTab(tabId)
   })
 }
 const currentTab = tabs.find(tab => tab.id === activeTab)!
 return (
   <div className="p-6">
     <div className="flex border-b">
       {tabs.map(tab => (
         <button
           key={tab.id}
           onClick={() => handleTabChange(tab.id)}
           // Tab button updates immediately even though content is pending
           className={`px-6 py-3 font-medium transition-colors relative ${
             activeTab === tab.id
               ? 'border-b-2 border-blue-600 text-blue-600'
               : 'text-gray-600 hover:text-gray-900'
           }`}
         >
           {tab.title}
           {/* Show loading indicator on the clicked tab while transitioning */}
           {isPending && activeTab !== tab.id && (
             <span className="absolute top-1 right-1 w-2 h-2 bg-blue-600 rounded-full animate-pulse" />
           )}
         </button>
       ))}
     </div>
     {/* Dim content while new tab is loading */}
     <div className={`mt-6 ${isPending ? 'opacity-50' : ''}`}>
       <h2 className="text-xl font-bold mb-4">{currentTab.title}</h2>
       <div className="max-h-96 overflow-y-auto">
         <HeavyTabContent content={currentTab.content} />
       </div>
     </div>
   </div>
 )
}

Notice that the tab content dims during the transition (via isPending), keeping the old content visible while the new content prepares. However, the tab button itself doesn't highlight immediately, because activeTab is the only state and it's inside startTransition, the visual selection doesn't update until the heavy render completes.

Streaming and Suspense for faster page loads

Server-side rendering has always been about getting content to users faster, but traditional SSR had a significant limitation: the server had to finish rendering the entire page before sending anything to the client. Streaming SSR changes this by sending HTML in chunks as they become ready.

It's important to distinguish between two different uses of Suspense:

  • Client-side code splitting uses lazy() to split JavaScript bundles. The server sends fallback HTML, then the client downloads and executes JS files. This reduces initial bundle size but isn't streaming, the HTML is complete when it arrives.
  • Streaming SSR requires RSC or framework support (Next.js App Router, Remix). The server sends the page shell immediately as HTML, then streams additional HTML chunks as async operations complete. No client-side JavaScript needed for the initial content.

Here's actual streaming SSR with Next.js App Router:

// app/product/[id]/page.tsx
import { Suspense } from 'react'
import { getProduct, getReviews, getRelatedProducts } from '@/lib/api'
interface Review { id: string; author: string; content: string }
interface Product { id: string; name: string; price: number; description: string; category: string }
// Async Server Component - runs on server, streams HTML when data resolves
async function Reviews({ productId }: { productId: string }) {
 const reviews = await getReviews(productId)
 return (
   <section className="mt-8">
     <h2 className="text-xl font-bold mb-4">Reviews</h2>
     {reviews.map((review: Review) => (
       <div key={review.id} className="p-4 border-b">
         <p className="font-medium">{review.author}</p>
         <p className="text-gray-600">{review.content}</p>
       </div>
     ))}
   </section>
 )
}
async function RelatedProducts({ category }: { category: string }) {
 const products = await getRelatedProducts(category)
 return (
   <section className="mt-8">
     <h2 className="text-xl font-bold mb-4">Related Products</h2>
     <div className="grid grid-cols-3 gap-4">
       {products.map((product: Product) => (
         <div key={product.id} className="p-4 bg-white rounded-lg shadow">
           <h3 className="font-medium">{product.name}</h3>
           <p className="text-blue-600">${product.price}</p>
         </div>
       ))}
     </div>
   </section>
 )
}
function ReviewsSkeleton() {
 return (
   <section className="mt-8">
     <div className="h-6 w-32 bg-gray-200 rounded animate-pulse mb-4" />
     {[1, 2, 3].map(i => <div key={i} className="h-20 bg-gray-100 rounded animate-pulse mb-2" />)}
   </section>
 )
}
function RelatedSkeleton() {
 return (
   <section className="mt-8">
     <div className="h-6 w-40 bg-gray-200 rounded animate-pulse mb-4" />
     <div className="grid grid-cols-3 gap-4">
       {[1, 2, 3].map(i => <div key={i} className="h-32 bg-gray-100 rounded animate-pulse" />)}
     </div>
   </section>
 )
}
// Next.js 15: params is now a Promise
export default async function ProductPage({ params }: { params: Promise<{ id: string }> }) {
 const { id } = await params
 const product = await getProduct(id)
 return (
   <div className="max-w-4xl mx-auto p-6">
     {/* Sent immediately - blocks initial HTML */}
     <div className="bg-white rounded-lg shadow p-6">
       <h1 className="text-3xl font-bold">{product.name}</h1>
       <p className="text-2xl text-blue-600 mt-2">${product.price}</p>
       <p className="text-gray-600 mt-4">{product.description}</p>
       <button className="mt-6 px-6 py-3 bg-blue-600 text-white rounded-lg">Add to Cart</button>
     </div>
     {/* Stream independently as data resolves - no client JS needed */}
     <Suspense fallback={<ReviewsSkeleton />}>
       <Reviews productId={id} />
     </Suspense>
     <Suspense fallback={<RelatedSkeleton />}>
       <RelatedProducts category={product.category} />
     </Suspense>
   </div>
 )
}

This is RSC with streaming, fundamentally different from client-side lazy(). The Reviews and RelatedProducts components are async functions that run entirely on the server. When a request comes in, Next.js sends the product details and skeleton HTML immediately. As each async component's data fetch completes, the server streams an HTML chunk that replaces the skeleton, no JavaScript downloads, no hydration for these components. The browser receives ready-to-display HTML over a single HTTP connection. Note that in Next.js 15, params is a Promise and must be awaited.

Improving data fetching performance with RSC

RSC represent a paradigm shift in how we think about React applications. Server Components run exclusively on the server, allowing them to access databases, file systems, and other server-only resources directly. The component tree they generate is serialized and sent to the client, but the component code itself never ships to the browser.

This has profound implications for performance. You can fetch data directly in your components without client-side waterfall requests. You can use server-only libraries without increasing your bundle size. And you can compute expensive operations on the server where CPU and memory are plentiful:

// UserProfile.tsx - This runs only on the server (notice does not have "use client")
import { Suspense } from 'react'
import db from './database'
// Only the fields safe to expose to the client
// The database entity might have password, role, tokens, etc.
interface UserDTO {
 id: string
 name: string
 email: string
 posts: number
 joined: string
}
// Data Access Layer: controls what data leaves the server
// Never return raw database entities to components
async function getUserProfile(userId: string): Promise<UserDTO> {
 const user = await db.users.findById(userId)

 // Explicitly pick safe fields—everything else stays on the server
 // Raw entity might include: passwordHash, resetToken, role, isAdmin, etc.
 return {
   id: user.id,
   name: user.name,
   email: user.email,
   posts: user.posts,
   joined: user.joined
 }
}
async function UserProfile({ userId }: { userId: string }) {
 // Fetch through the data access layer, not directly from db
 const user = await getUserProfile(userId)
 return (
   <div className="bg-white rounded-lg shadow p-6">
     <div className="flex items-center gap-4">
       <div className="w-16 h-16 bg-blue-600 rounded-full flex items-center justify-center text-white text-xl font-bold">
         {user.name.charAt(0)}
       </div>
       <div>
         <h1 className="text-2xl font-bold">{user.name}</h1>
         <p className="text-gray-600">{user.email}</p>
       </div>
     </div>
     <div className="grid grid-cols-2 gap-4 mt-6">
       <div className="p-4 bg-gray-50 rounded">
         <p className="text-sm text-gray-500">Posts</p>
         <p className="text-xl font-bold">{user.posts}</p>
       </div>
       <div className="p-4 bg-gray-50 rounded">
         <p className="text-sm text-gray-500">Member Since</p>
         <p className="text-xl font-bold">{user.joined}</p>
       </div>
     </div>
   </div>
 )
}
function ProfileSkeleton() {
 return (
   <div className="bg-white rounded-lg shadow p-6 animate-pulse">
     <div className="flex items-center gap-4">
       <div className="w-16 h-16 bg-gray-200 rounded-full" />
       <div>
         <div className="h-6 w-32 bg-gray-200 rounded" />
         <div className="h-4 w-48 bg-gray-200 rounded mt-2" />
       </div>
     </div>
   </div>
 )
}
export default function ProfilePage({ userId }: { userId: string }) {
 return (
   <div className="max-w-2xl mx-auto p-6">
     <Suspense fallback={<ProfileSkeleton />}>
       <UserProfile userId={userId} />
     </Suspense>
   </div>
 )
}

Server Components have direct database access, which makes it easy to accidentally expose sensitive data. Never return raw database entities, always use a Data Transfer Object (DTO) that explicitly lists the fields safe for the client. The getUserProfile function acts as a data access layer: it fetches the full entity but returns only the public fields. This pattern protects against leaking sensitive fields like password hashes, authentication tokens, or internal flags that might exist on the database model.

Performance optimization in React operates at two levels that require different approaches. Client-side optimizations, memoization, virtualization, code splitting, can often be applied incrementally. When you notice a slow interaction, you profile it, identify the bottleneck, and apply a targeted fix. The React DevTools Profiler shows you exactly which components rendered and why, making it straightforward to find unnecessary re-renders or expensive computations.

Server Components are different. They're an architectural decision, not an optimization you bolt on later. The boundaries between Server and Client Components affect your entire data fetching strategy, your component composition patterns, and how state flows through your application. If you design these boundaries poorly at the start, you may need significant rewrites to fix them, not incremental improvements. For new projects using Next.js App Router or similar frameworks, think through your server/client split early. Note that standard React DevTools can't profile Server Component render times since that happens on the server; you'll need server-side logging and monitoring tools instead.

The techniques in this chapter, concurrent rendering, Suspense boundaries, streaming SSR, give you tools for building responsive applications. But tools aren't solutions. The real skill is knowing when each technique applies and recognizing that simpler code is often faster code.

Summary

React 19 represents a fundamental shift in how we think about performance. The manual optimization patterns that dominated React development for years, wrapping components in memo(), stabilizing references with useMemo and useCallback, are being automated by the React Compiler. Instead of developers manually tracking which values need memoization, the compiler analyzes your code at build time and inserts optimizations automatically. This doesn't mean understanding these concepts is useless; it means you can write straightforward code and let tooling handle the tedious parts.

Perhaps most critically, we've examined hydration, the often-invisible process that bridges server-rendered HTML and client-side interactivity, and learned strategies to minimize its impact on user experience. These techniques work together synergistically: a smaller bundle hydrates faster, selective hydration with Suspense boundaries enables streaming SSR, and code splitting reduces both initial download size and hydration scope. We've also learned that effective optimization begins with measurement, using tools like React Profiler, Lighthouse, and Web Vitals to identify real bottlenecks before applying solutions.

As you continue building React applications, carry forward the mindset that performance is a feature, not an afterthought. Users perceive speed holistically, a fast initial load means nothing if interactions feel sluggish, and instant updates are undermined by janky animations. The advanced features we've explored, particularly concurrent rendering and Server Components, represent React's evolution toward applications that feel native in their responsiveness. Start with clean, maintainable code, measure your application's real-world performance through Core Web Vitals and user-centric metrics, and apply optimizations strategically where they matter most for your specific application and audience. Remember that the best optimization is often the code you don't write, simplifying your component architecture and data flow can yield greater performance gains than any memoization technique. With the knowledge from this chapter, you're now equipped to build React applications that don't just work well but feel exceptional.
