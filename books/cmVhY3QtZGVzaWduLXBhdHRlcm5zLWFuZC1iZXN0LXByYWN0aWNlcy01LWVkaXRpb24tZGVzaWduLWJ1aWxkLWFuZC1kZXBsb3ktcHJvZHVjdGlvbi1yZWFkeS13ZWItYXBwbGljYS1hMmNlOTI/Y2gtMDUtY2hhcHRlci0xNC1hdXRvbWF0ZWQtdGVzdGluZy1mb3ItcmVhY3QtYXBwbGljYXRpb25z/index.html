Automated Testing for React Applications

Testing is the invisible foundation that holds your React applications together. While users never see your tests, they experience their benefits every time a feature works correctly and every time a bug is caught before deployment.

This reliability comes at a cost. Writing tests takes time that could otherwise be spent building features. Tests require maintenance as your application evolves, change a component's behavior and you'll update its tests too. A comprehensive test suite can significantly slow your CI pipeline: unit tests run in milliseconds, but end-to-end tests that spin up browsers and interact with real services can take minutes. Across a large application, a full test run might take 20-30 minutes, blocking deployments and slowing feedback loops. Flaky tests, those that pass and fail intermittently, erode trust in your test suite and waste developer time investigating false failures.

The goal isn't to test everything. It's to test strategically, focusing effort where it provides the most value relative to cost. A checkout flow that handles payments deserves thorough testing; a static About Us page probably doesn't. Critical business logic warrants unit tests with edge cases covered; straightforward UI components might only need a smoke test confirming they render.

The testing landscape for React is often described as three layers: unit, integration, and end-to-end. In practice, these boundaries blur. When you test a component that renders children and manages state, is that a unit test or integration test? The distinction matters less than understanding what each test validates. Tests that examine components in isolation with mocked dependencies catch different problems than tests that let components interact naturally. End-to-end tests validate your entire stack, frontend, backend, database, simulating real user behavior against real infrastructure.

Throughout this chapter, we'll build a practical understanding of testing by creating a task management application. You'll learn to write tests that are maintainable, meaningful, and give you confidence in your code without slowing you down.

In this chapter, we will cover the following topics:

  • Writing unit tests with Jest and React Testing Library
  • Integration testing for React Components
  • Setting up Playwright for end-to-end testing
  • Automating tests in CI/CD pipelines with GitHub Actions

Writing unit tests with Jest and React Testing Library

React Testing Library has revolutionized how we think about testing React components. Rather than testing implementation details, it encourages us to test components the way users interact with them. This philosophy leads to tests that are more resilient to refactoring and better reflect real-world usage.

Let's begin with a simple but realistic component, a task item in our task manager. This component displays a task, allows users to toggle its completion status, and provides a delete button:

// TaskItem.tsx
interface Task {
  id: string;
  title: string;
  completed: boolean;
}

interface TaskItemProps {
task: Task;
onToggle: (id: string) => void;
onDelete: (id: string) => void;
}

export const TaskItem = ({ task, onToggle, onDelete }: TaskItemProps) => {
return (
<div className="flex items-center justify-between p-4 bg-white border border-gray-200 rounded-lg shadow-sm">
<div className="flex items-center gap-3">
<input
type="checkbox"
checked={task.completed}
onChange={() => onToggle(task.id)}
className="w-5 h-5 text-blue-600 rounded focus:ring-2 focus:ring-blue-500"
aria-label={Toggle ${task.title}}
/>
<span
className={text-lg ${              task.completed ? 'line-through text-gray-400' : 'text-gray-800'            }}
>
{task.title}
</span>
</div>
<button
onClick={() => onDelete(task.id)}
className="px-3 py-1 text-sm text-white bg-red-500 rounded hover:bg-red-600
focus:outline-none focus:ring-2 focus:ring-red-500"
aria-label={Delete ${task.title}}
>
Delete
</button>
</div>
);
};

Now let's write tests that verify this component behaves correctly. We'll test the visual presentation, user interactions, and accessibility features:

// TaskItem.test.tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { TaskItem } from './TaskItem';

describe('TaskItem', () => {
const mockTask = {
id: '1',
title: 'Write unit tests',
completed: false,
};

const mockOnToggle = jest.fn();
const mockOnDelete = jest.fn();

beforeEach(() => {
jest.clearAllMocks();
});

it('renders the task title correctly', () => {
render(
<TaskItem task={mockTask} onToggle={mockOnToggle} onDelete={mockOnDelete} />
);

expect(screen.getByText('Write unit tests')).toBeInTheDocument();

});
it('displays unchecked checkbox for incomplete tasks', () => {
render(
<TaskItem task={mockTask} onToggle={mockOnToggle} onDelete={mockOnDelete} />
);
const checkbox = screen.getByRole('checkbox', { name: /toggle write unit tests/i });
expect(checkbox).not.toBeChecked();

});
it('displays checked checkbox for completed tasks', () => {
const completedTask = { ...mockTask, completed: true };
render(
<TaskItem task={completedTask} onToggle={mockOnToggle} onDelete={mockOnDelete} />
);
const checkbox = screen.getByRole('checkbox', { name: /toggle write unit tests/i });
expect(checkbox).toBeChecked();

});
it('applies strike-through styling to completed tasks', () => {
const completedTask = { ...mockTask, completed: true };
render(
<TaskItem task={completedTask} onToggle={mockOnToggle} onDelete={mockOnDelete} />
);
const title = screen.getByText('Write unit tests');
expect(title).toHaveClass('line-through');

});
it('calls onToggle when checkbox is clicked', async () => {
const user = userEvent.setup();
render(
<TaskItem task={mockTask} onToggle={mockOnToggle} onDelete={mockOnDelete} />
);
const checkbox = screen.getByRole('checkbox', { name: /toggle write unit tests/i });
await user.click(checkbox);

expect(mockOnToggle).toHaveBeenCalledTimes(1);
expect(mockOnToggle).toHaveBeenCalledWith('1');

});
it('calls onDelete when delete button is clicked', async () => {
const user = userEvent.setup();
render(
<TaskItem task={mockTask} onToggle={mockOnToggle} onDelete={mockOnDelete} />
);
const deleteButton = screen.getByRole('button', { name: /delete write unit tests/i });
await user.click(deleteButton);

expect(mockOnDelete).toHaveBeenCalledTimes(1);
expect(mockOnDelete).toHaveBeenCalledWith('1');

});
});

We use screen.getByRole to find elements by their accessibility role, which encourages thinking about how assistive technologies will interpret our components and makes tests more resilient to markup changes. However, passing these queries doesn't guarantee accessibility, it only confirms that ARIA roles are present. True accessibility requires additional considerations like keyboard navigation, focus management, color contrast, and proper labeling that these tests don't cover.

The beforeEach hook resets mock state between tests, ensuring each test runs independently. Note that clearAllMocks() only resets call history (.calls, .results), so if a previous test changed a mock's return value, that change persists. Use resetAllMocks() to also reset mock implementations, or restoreAllMocks() when working with spies that need their original functions restored.

Let's explore a more complex scenario with a component that manages state internally. Our TaskForm component needs to handle user input, validation, and form submission:

// TaskForm.tsx
import { FormEvent, useState } from 'react';

interface TaskFormProps {
onSubmit: (title: string) => void;
}

export const TaskForm = ({ onSubmit }: TaskFormProps) => {
const [title, setTitle] = useState('');
const [error, setError] = useState('');

const handleSubmit = (e: FormEvent) => {
e.preventDefault();

const trimmedTitle = title.trim();

if (!trimmedTitle) {
  setError('Task title cannot be empty');
  return;
}

if (trimmedTitle.length &lt; 3) {
  setError('Task title must be at least 3 characters');
  return;
}

onSubmit(trimmedTitle);
setTitle('');
setError('');

};
return (
<form onSubmit={handleSubmit} className="mb-6">
<div className="flex gap-2">
<div className="flex-1">
<input
type="text"
value={title}
onChange={(e) => {
setTitle(e.target.value);
setError('');
}}
placeholder="Enter a new task..."
className="w-full px-4 py-2 border border-gray-300 rounded-lg focus:outline-none
focus:ring-2 focus:ring-blue-500"
aria-label="Task title"
aria-invalid={!!error}
aria-describedby={error ? 'task-error' : undefined}
/>
{error && (
<p id="task-error" className="mt-1 text-sm text-red-600" role="alert">
{error}
</p>
)}
</div>
<button
type="submit"
className="px-6 py-2 text-white bg-blue-600 rounded-lg hover:bg-blue-700
focus:outline-none focus:ring-2 focus:ring-blue-500"
>
Add Task
</button>
</div>
</form>
);
};

Testing this form requires verifying both happy paths and error cases. We need to ensure validation works correctly and that the form clears after successful submission:

// TaskForm.test.tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { TaskForm } from './TaskForm';

describe('TaskForm', () => {
const mockOnSubmit = jest.fn();

beforeEach(() => {
jest.clearAllMocks();
});

it('allows users to type in the input field', async () => {
const user = userEvent.setup();
render(<TaskForm onSubmit={mockOnSubmit} />);

const input = screen.getByLabelText(/task title/i);
await user.type(input, 'New task');

expect(input).toHaveValue('New task');

});
it('submits the form with valid input', async () => {
const user = userEvent.setup();
render(<TaskForm onSubmit={mockOnSubmit} />);
const input = screen.getByLabelText(/task title/i);
const submitButton = screen.getByRole('button', { name: /add task/i });

await user.type(input, 'Valid task');
await user.click(submitButton);

expect(mockOnSubmit).toHaveBeenCalledWith('Valid task');
expect(input).toHaveValue('');

});
it('shows error for empty input', async () => {
const user = userEvent.setup();
render(<TaskForm onSubmit={mockOnSubmit} />);
const submitButton = screen.getByRole('button', { name: /add task/i });
await user.click(submitButton);

expect(screen.getByRole('alert')).toHaveTextContent('Task title cannot be empty');
expect(mockOnSubmit).not.toHaveBeenCalled();

});
it('shows error for input that is too short', async () => {
const user = userEvent.setup();
render(<TaskForm onSubmit={mockOnSubmit} />);
const input = screen.getByLabelText(/task title/i);
const submitButton = screen.getByRole('button', { name: /add task/i });

await user.type(input, 'ab');
await user.click(submitButton);

expect(screen.getByRole('alert')).toHaveTextContent(
  'Task title must be at least 3 characters'
);
expect(mockOnSubmit).not.toHaveBeenCalled();

});
it('clears error when user starts typing again', async () => {
const user = userEvent.setup();
render(<TaskForm onSubmit={mockOnSubmit} />);
const input = screen.getByLabelText(/task title/i);
const submitButton = screen.getByRole('button', { name: /add task/i });

await user.click(submitButton);
expect(screen.getByRole('alert')).toBeInTheDocument();

await user.type(input, 'a');
expect(screen.queryByRole('alert')).not.toBeInTheDocument();

});
});

Notice how we verify what users can observe: error messages appearing and clearing appropriately. Testing Library provides three query variants, each for different scenarios. getByRole throws an error immediately if the element isn't found, making it ideal for elements that should be present. queryByRole returns null instead of throwing, perfect for asserting that something should not exist synchronously. findByRole waits asynchronously and retries until the element appears or times out, essential for elements that appear after state updates or API calls. For elements that disappear asynchronously, like a loading spinner after an API completes, use waitForElementToBeRemoved or wrap your query in waitFor. A plain queryByRole check would pass immediately before the element has time to disappear.

That said, testing whether mockOnSubmit was called is a pragmatic compromise rather than a true user-perspective test, users experience success messages, redirects, or loading states, not callback invocations. These assertions test the component's contract with its parent, not the complete user journey.

Integration testing for React Components

While unit tests verify individual components in isolation, integration tests ensure that multiple components work together correctly. This level of testing catches issues that emerge from component interactions, data flow, and shared state management.

Let's build a complete task list that combines our previous components with state management. This represents a realistic slice of functionality that users interact with as a cohesive feature:

// TaskList.tsx
import { useState } from 'react';
import { TaskItem } from './TaskItem';
import { TaskForm } from './TaskForm';

interface Task {
id: string;
title: string;
completed: boolean;
}

export const TaskList = () => {
const [tasks, setTasks] = useState<Task[]>([]);

const addTask = (title: string) => {
const newTask: Task = {
id: crypto.randomUUID(),
title,
completed: false,
};
setTasks((prev) => [...prev, newTask]);
};

const toggleTask = (id: string) => {
setTasks((prev) =>
prev.map((task) =>
task.id === id ? { ...task, completed: !task.completed } : task
)
);
};

const deleteTask = (id: string) => {
setTasks((prev) => prev.filter((task) => task.id !== id));
};

const completedCount = tasks.filter((task) => task.completed).length;
const totalCount = tasks.length;

return (
<div className="max-w-2xl mx-auto p-6">
<h1 className="text-3xl font-bold text-gray-800 mb-2">Task Manager</h1>
<p className="text-gray-600 mb-6">
{completedCount} of {totalCount} tasks completed
</p>

  &lt;TaskForm onSubmit={addTask} /&gt;

  {tasks.length === 0 ? (
    &lt;p className="text-center text-gray-500 py-8"&gt;
      No tasks yet. Add one above to get started!
    &lt;/p&gt;
  ) : (
    &lt;div className="space-y-2"&gt;
      {tasks.map((task) =&gt; (
        &lt;TaskItem
          key={task.id}
          task={task}
          onToggle={toggleTask}
          onDelete={deleteTask}
        /&gt;
      ))}
    &lt;/div&gt;
  )}
&lt;/div&gt;

);
};

Our integration tests will verify the entire workflow from the user's perspective: adding tasks through the form, seeing them appear in the list, toggling their completion status, deleting them, and ensuring the summary count updates correctly throughout these interactions. Unlike our unit tests, we won't mock TaskForm or TaskItem, we want to verify that these components work together as users will actually experience them:

// TaskList.test.tsx
import { render, screen, within } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { TaskList } from './TaskList';

describe('TaskList Integration', () => {
it('displays empty state when no tasks exist', () => {
render(<TaskList />);

expect(screen.getByText(/no tasks yet/i)).toBeInTheDocument();
expect(screen.getByText('0 of 0 tasks completed')).toBeInTheDocument();

});
it('adds a new task and displays it', async () => {
const user = userEvent.setup();
render(<TaskList />);
const input = screen.getByLabelText(/task title/i);
const addButton = screen.getByRole('button', { name: /add task/i });

await user.type(input, 'Buy groceries');
await user.click(addButton);

expect(screen.getByText('Buy groceries')).toBeInTheDocument();
expect(screen.queryByText(/no tasks yet/i)).not.toBeInTheDocument();

});
it('adds multiple tasks in sequence', async () => {
const user = userEvent.setup();
render(<TaskList />);
const input = screen.getByLabelText(/task title/i);
const addButton = screen.getByRole('button', { name: /add task/i });

await user.type(input, 'First task');
await user.click(addButton);

await user.type(input, 'Second task');
await user.click(addButton);

await user.type(input, 'Third task');
await user.click(addButton);

expect(screen.getByText('First task')).toBeInTheDocument();
expect(screen.getByText('Second task')).toBeInTheDocument();
expect(screen.getByText('Third task')).toBeInTheDocument();
expect(screen.getByText('0 of 3 tasks completed')).toBeInTheDocument();

});
it('toggles task completion and updates counter', async () => {
const user = userEvent.setup();
render(<TaskList />);
const input = screen.getByLabelText(/task title/i);
const addButton = screen.getByRole('button', { name: /add task/i });

await user.type(input, 'Complete me');
await user.click(addButton);

const checkbox = screen.getByRole('checkbox', { name: /toggle complete me/i });
await user.click(checkbox);

expect(checkbox).toBeChecked();
expect(screen.getByText('1 of 1 tasks completed')).toBeInTheDocument();

await user.click(checkbox);
expect(checkbox).not.toBeChecked();
expect(screen.getByText('0 of 1 tasks completed')).toBeInTheDocument();

});
});

Let's continue with more complex integration scenarios that test the complete workflow:

// TaskList.test.tsx (continued)
describe('TaskList Integration - Complex Workflows', () => {
  it('deletes a task and updates the list', async () => {
    const user = userEvent.setup();
    render(<TaskList />);

const input = screen.getByLabelText(/task title/i);
const addButton = screen.getByRole('button', { name: /add task/i });

await user.type(input, 'Task to delete');
await user.click(addButton);
const deleteButton = screen.getByRole('button', { name: /delete task to delete/i });
await user.click(deleteButton);

expect(screen.queryByText('Task to delete')).not.toBeInTheDocument();
expect(screen.getByText(/no tasks yet/i)).toBeInTheDocument();

});
it('manages a realistic task workflow', async () => {
const user = userEvent.setup();
render(<TaskList />);
const input = screen.getByLabelText(/task title/i);
const addButton = screen.getByRole('button', { name: /add task/i });

await user.type(input, 'Morning exercise');
await user.click(addButton);
await user.type(input, 'Check emails');
await user.click(addButton);
await user.type(input, 'Team meeting');
await user.click(addButton);

const morningCheckbox = screen.getByRole('checkbox', {
  name: /toggle morning exercise/i
});
await user.click(morningCheckbox);

const emailCheckbox = screen.getByRole('checkbox', { name: /toggle check emails/i });
await user.click(emailCheckbox);

expect(screen.getByText('2 of 3 tasks completed')).toBeInTheDocument();

const deleteButton = screen.getByRole('button', { name: /delete check emails/i });
await user.click(deleteButton);

expect(screen.getByText('1 of 2 tasks completed')).toBeInTheDocument();
expect(screen.getByText('Morning exercise')).toBeInTheDocument();
expect(screen.queryByText('Check emails')).not.toBeInTheDocument();
expect(screen.getByText('Team meeting')).toBeInTheDocument();

});
});

The final test demonstrates the value of integration testing. In a single test, we exercise three components (TaskList, TaskForm, and multiple TaskItem instances), perform six user interactions (three additions, two toggles, one deletion), and verify that state updates propagate correctly through the entire component tree. Notice what we're not testing: we never check internal state variables, we don't verify that specific functions were called, and we don't mock any child components. Instead, we verify outcomes a user would recognize, tasks appear when added, checkboxes reflect completion status, the counter stays accurate as tasks change, and deleted items disappear. If you later refactor TaskList to use useReducer instead of useState, or extract the task logic into a custom hook, these tests continue to pass unchanged because they test behavior rather than implementation. This resilience to refactoring is the hallmark of well-designed integration tests.

While integration tests give us confidence that components work together, they still run in a controlled environment, so next, we'll step into real-world conditions with end-to-end testing.

Setting up Playwright for end-to-end testing

End-to-end testing takes us even further, running your application in a real browser and simulating genuine user interactions. Playwright excels at this level of testing, offering powerful APIs for interacting with web applications across multiple browsers.

First, you'll need to install Playwright and initialize it in your project. The setup process creates configuration files and installs browser binaries:

npm init playwright@latest

Playwright's configuration allows you to specify which browsers to test against, set base URLs, and configure parallel test execution. Here's a practical configuration for a React application:

// playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
testDir: './e2e',
fullyParallel: true,
forbidOnly: !!process.env.CI,
retries: process.env.CI ? 2 : 0,
workers: process.env.CI ? 1 : undefined,
reporter: 'html',

use: {
baseURL: 'http://localhost:3000',
trace: 'on-first-retry',
screenshot: 'only-on-failure',
},
projects: [
{
name: 'chromium',
use: { ...devices['Desktop Chrome'] },
},
{
name: 'firefox',
use: { ...devices['Desktop Firefox'] },
},
{
name: 'webkit',
use: { ...devices['Desktop Safari'] },
},
],
webServer: {
command: 'npm run dev', // Normally you should prefer to run this as prod (npm run build && npm run start)
url: process.env.PLAYWRIGHT_BASE_URL || 'http://localhost:3000',
reuseExistingServer: !process.env.CI,
},
});

This configuration automatically starts your development server before running tests and tears it down afterward. In CI environments, it runs tests with retries to handle flaky tests and captures traces for debugging failures.

Now let's write end-to-end tests for our task manager. Since our current implementation stores state in memory with useState, data won't persist across page reloads. These tests verify the user experience within a single session, creating tasks, marking them complete, and deleting them. If your application persists data to an API or database, you'd add tests that reload the page and verify data survives:

// e2e/task-manager.spec.ts
import { test, expect } from '@playwright/test';

test.describe('Task Manager E2E', () => {
test.beforeEach(async ({ page }) => {
await page.goto('/');
});

test('displays the application with correct title', async ({ page }) => {
await expect(page.locator('h1')).toHaveText('Task Manager');
await expect(page.getByText('0 of 0 tasks completed')).toBeVisible();
});

test('shows empty state message initially', async ({ page }) => {
await expect(
page.getByText('No tasks yet. Add one above to get started!')
).toBeVisible();
});

test('creates a new task through the form', async ({ page }) => {
await page.getByLabel('Task title').fill('Write E2E tests');
await page.getByRole('button', { name: 'Add Task' }).click();
await expect(page.getByText('Write E2E tests')).toBeVisible();
await expect(page.getByText('0 of 1 tasks completed')).toBeVisible();
await expect(page.getByLabel('Task title')).toHaveValue('');
});

test('validates form input and shows errors', async ({ page }) => {
await page.getByRole('button', { name: 'Add Task' }).click();

await expect(page.getByRole('alert')).toHaveText(
  'Task title cannot be empty'
);

await page.getByLabel('Task title').fill('ab');
await page.getByRole('button', { name: 'Add Task' }).click();

await expect(page.getByRole('alert')).toHaveText(
  'Task title must be at least 3 characters'
);

});
test('completes a full task lifecycle', async ({ page }) => {
await page.getByLabel('Task title').fill('Buy groceries');
await page.getByRole('button', { name: 'Add Task' }).click();
await page.getByLabel('Task title').fill('Do laundry');
await page.getByRole('button', { name: 'Add Task' }).click();

await expect(page.getByText('0 of 2 tasks completed')).toBeVisible();

const groceriesCheckbox = page.getByRole('checkbox', {
  name: /toggle buy groceries/i,
});
await groceriesCheckbox.check();

await expect(groceriesCheckbox).toBeChecked();
await expect(page.getByText('1 of 2 tasks completed')).toBeVisible();

const laundryCheckbox = page.getByRole('checkbox', {
  name: /toggle do laundry/i,
});
await laundryCheckbox.check();

await expect(page.getByText('2 of 2 tasks completed')).toBeVisible();

const deleteButton = page.getByRole('button', {
  name: /delete buy groceries/i,
});
await deleteButton.click();

await expect(page.getByText('Buy groceries')).not.toBeVisible();
await expect(page.getByText('1 of 1 tasks completed')).toBeVisible();

});
});

Playwright's API mirrors how users think about interacting with web pages. You click buttons, fill forms, and make assertions about what's visible. The framework handles waiting for elements to appear, animations to complete, and network requests to finish. However, real users interact with applications in ways that go beyond clicking buttons in sequence, they use keyboard shortcuts, act quickly without waiting for animations, and expect visual feedback to confirm their actions. The following tests cover four scenarios that reflect this reality: keyboard navigation (verifying Enter key submission), visual feedback (confirming strikethrough styling on completed tasks), rapid task creation (ensuring quick successive inputs don't lose data), and state consistency during rapid interactions (catching race conditions where the UI might fall out of sync with underlying state):

// e2e/task-manager-advanced.spec.ts
import { test, expect } from '@playwright/test'

test.describe('Task Manager - Advanced Interactions', () => {
test.beforeEach(async ({ page }) => {
await page.goto('/')
})

test('submits form using Enter key', async ({ page }) => {
await page.getByLabel('Task title').fill('Test keyboard submission')
await page.getByLabel('Task title').press('Enter')

await expect(page.getByText('Test keyboard submission')).toBeVisible()

})
test('visually distinguishes completed tasks', async ({ page }) => {
await page.getByLabel('Task title').fill('Style test task')
await page.getByRole('button', { name: 'Add Task' }).click()
const checkbox = page.getByRole('checkbox', { name: /toggle style test task/i })
await checkbox.check()

// Test the user-visible result, not the implementation
// Screenshot comparison catches any visual change (strikethrough, opacity, color)
await expect(page.getByTestId('task-list')).toHaveScreenshot('completed-task.png')

// Or verify accessibility: completed tasks should be marked
await expect(checkbox).toBeChecked()
await expect(page.getByText('1 of 1 tasks completed')).toBeVisible()

})
test('creates multiple tasks sequentially', async ({ page }) => {
// Renamed: this is sequential, not "rapid"
const taskTitles = [
'First task',
'Second task',
'Third task',
]
for (const title of taskTitles) {
  await page.getByLabel('Task title').fill(title)
  await page.getByRole('button', { name: 'Add Task' }).click()
}

for (const title of taskTitles) {
  await expect(page.getByText(title)).toBeVisible()
}

await expect(page.getByText('0 of 3 tasks completed')).toBeVisible()

})
test('handles rapid checkbox toggling', async ({ page }) => {
await page.getByLabel('Task title').fill('Quick task')
await page.getByRole('button', { name: 'Add Task' }).click()
const checkbox = page.getByRole('checkbox', { name: /toggle quick task/i })

// Rapid clicks without waiting for state to settle
// Tests that the UI doesn't break under fast interaction
await checkbox.click()
await checkbox.click()
await checkbox.click()

// Final state should be checked (odd number of clicks)
await expect(checkbox).toBeChecked()
await expect(page.getByText('1 of 1 tasks completed')).toBeVisible()

})
})
// For actual race condition testing with API calls,

Playwright excels at testing responsive behavior and cross-browser compatibility. You can simulate different viewport sizes and test across Chrome, Firefox, and Safari simultaneously. The framework captures screenshots and traces on failure, making it easy to diagnose issues that only occur in specific browsers or screen sizes.

Most real applications require authentication, and logging in before every test wastes time and adds flakiness. Playwright solves this with storageState, you authenticate once, save the session, and reuse it across tests:

// e2e/auth.setup.ts
import { test as setup, expect } from '@playwright/test'

// This runs once before all tests
setup('authenticate', async ({ page }) => {
await page.goto('/login')
await page.getByLabel('Email').fill('test@example.com')
await page.getByLabel('Password').fill('password123')
await page.getByRole('button', { name: 'Sign in' }).click()

// Wait for authentication to complete
await expect(page.getByText('Welcome back')).toBeVisible()

// Save signed-in state to a file
await page.context().storageState({ path: './e2e/.auth/user.json' })
})

The storageState file contains cookies and localStorage data from the authenticated session. Add .auth/ to your .gitignore, these files contain session tokens. For applications with multiple user roles (admin, regular user), create separate setup files and storage states for each role.

The isMobile fixture is automatically true for mobile device projects, letting you write conditional assertions. Playwright's device descriptors include viewport size, user agent, touch support, and device scale factor, matching real device behavior more accurately than just changing viewport width.

Automating tests in CI/CD pipelines with GitHub Actions

Writing tests is only half the battle. To truly benefit from automated testing, your tests need to run automatically whenever code changes. GitHub Actions provides a powerful platform for continuous integration, running your entire test suite on every pull request and push to main branches.

Let's create a comprehensive CI workflow that runs unit tests, integration tests, and E2E tests in parallel, maximizing feedback speed. A word of caution about coverage metrics: a codebase with 100% line coverage can still have bugs. Coverage measures which lines executed during tests, not whether those tests make meaningful assertions or cover all possible input combinations. You can achieve full coverage with tests that never assert anything, or miss critical edge cases entirely. Treat coverage as a tool for finding untested code, not as proof that tested code works correctly:

# .github/workflows/test.yml
name: Test Suite

on:
push:
branches: [main, develop]
pull_request:
branches: [main, develop]

jobs:
unit-and-integration:
name: Unit & Integration Tests
runs-on: ubuntu-latest

steps:
  - name: Checkout code
    uses: actions/checkout@v4
 
  - name: Setup Node.js
    uses: actions/setup-node@v4
    with:
      node-version: '22'
      cache: 'npm'
 
  - name: Install dependencies
    run: npm ci
 
  - name: Run unit and integration tests
    run: npm test -- --coverage --watchAll=false
 
  - name: Upload coverage reports
    uses: codecov/codecov-action@v3
    with:
      files: ./coverage/coverage-final.json
      flags: unittests
      name: codecov-umbrella

e2e-tests:
name: E2E Tests - ${{ matrix.browser }}
runs-on: ubuntu-latest
strategy:
  fail-fast: false
  matrix:
    browser: [chromium, firefox, webkit]

steps:
  - name: Checkout code
    uses: actions/checkout@v4
 
  - name: Setup Node.js
    uses: actions/setup-node@v4
    with:
      node-version: '22'
      cache: 'npm'
 
  - name: Install dependencies
    run: npm ci

  - name: Cache Playwright browsers
    uses: actions/cache@v4
    with:
      path: ~/.cache/ms-playwright
      key: playwright-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}
 
  - name: Install Playwright browsers
    run: npx playwright install --with-deps ${{ matrix.browser }}
 
  - name: Build application
    run: npm run build
 
  - name: Run Playwright tests
    run: npx playwright test --project=${{ matrix.browser }}
 
  - name: Upload Playwright report
    uses: actions/upload-artifact@v4
    if: always()
    with:
      name: playwright-report-${{ matrix.browser }}
      path: playwright-report/
      retention-days: 7</code></pre>

This workflow configuration runs unit tests and E2E tests in parallel, reducing total pipeline duration. However, parallel execution isn't always optimal for feedback speed. If unit tests fail in two minutes, you've already identified the problem, there's no need to wait for a ten-minute E2E suite to finish. A sequential strategy (unit → integration → E2E) that fails fast can surface issues sooner and conserve CI resources. The choice depends on your priorities: parallel execution minimizes total time when tests pass, while sequential execution minimizes time-to-failure when they don't.
Note that fail‑fast: false is set in the matrix configuration, meaning all three browser tests run to completion even if one fails. This ensures you catch issues across all browsers in a single run, but it also consumes resources on tests that may be irrelevant if you're just trying to fix the first failure. Consider setting fail‑fast: true during active development and disabling it only for comprehensive pre-release testing.
When tests fail, Playwright generates detailed HTML reports, and the actions/upload‑artifact step uploads them to GitHub. Accessing these reports requires downloading the artifact, extracting it, and opening the HTML file locally, functional but not exactly seamless. For teams that need faster debugging, consider integrating with Playwright's trace viewer or a third-party reporting service that provides direct links to failure details.
Let's enhance our workflow with additional quality checks and optimizations:
# .github/workflows/quality.yml
name: Code Quality

Trigger on pushes and pull requests to main branches


on:
push:
branches: [main, develop]
pull_request:
branches: [main, develop]

jobs:
lint:
name: Lint Code
runs-on: ubuntu-latest

steps:
  - name: Checkout code
    uses: actions/checkout@v4
 
  # Cache is set to 'npm' which caches ~/.npm (the download cache)
  # This speeds up npm ci but still performs a clean install
  - name: Setup Node.js
    uses: actions/setup-node@v4
    with:
      node-version: '22'
      cache: 'npm'
 
  # npm ci is preferred over npm install in CI environments
  # It's faster and ensures reproducible builds from package-lock.json
  - name: Install dependencies
    run: npm ci
 
  - name: Run ESLint
    run: npm run lint
 
  # Runs tsc --noEmit to catch type errors without generating output files
  # Catches errors that ESLint might miss (type mismatches, missing imports)
  - name: Check TypeScript types
    run: npm run type-check

Runs in parallel with lint job since there's no dependency between them
Consider adding 'needs: lint' if you want sequential execution to fail faster
test-coverage:
name: Test Coverage Check
runs-on: ubuntu-latest
steps:
  - name: Checkout code
    uses: actions/checkout@v4
 
  - name: Setup Node.js
    uses: actions/setup-node@v4
    with:
      node-version: '22'
      cache: 'npm'
 
  - name: Install dependencies
    run: npm ci
 
  # --watchAll=false ensures tests run once and exit (required for CI)
  # Coverage output goes to /coverage directory by default
  - name: Run tests with coverage
    run: npm test -- --coverage --watchAll=false
 
  # Manual threshold check using shell commands
  # Alternative: configure coverageThreshold in vitest.config.ts or jest.config.js
  # to fail automatically when coverage drops below threshold
  - name: Check coverage thresholds
    run: |
      COVERAGE=$(cat coverage/coverage-summary.json | jq '.total.lines.pct')
      if (( $(echo "$COVERAGE &lt; 80" | bc -l) )); then
        echo "Coverage is below 80%: $COVERAGE%"
        exit 1
      fi
      echo "Coverage is acceptable: $COVERAGE%"</code></pre>

Coverage check
The shell script approach using jq, bc, and cat to parse coverage JSON is fragile. It can break if the JSON format changes between versions, if jq isn't installed on the runner, or if bc behaves differently across environments. The 80% threshold is also hardcoded in the YAML, buried in CI configuration rather than living with your codebase. A more robust approach is configuring coverage thresholds directly in vitest.config.ts (or jest.config.js), where npm test ‑‑ ‑‑coverage fails automatically when coverage drops below your defined limits. This keeps thresholds version-controlled alongside your code and ensures consistent behavior across local development and CI environments.
Beyond running tests, this workflow enforces baseline code quality checks: linting for style consistency, TypeScript compilation for type safety, and coverage thresholds to flag untested code:
// RECOMMENDED: Configure thresholds in vitest.config.ts instead:
export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      thresholds: {
        lines: 80,
        branches: 80,
        functions: 80,
        statements: 80,
      }
    }
  }
})
These are foundational practices for any modern project, not exceptional standards. Keep in mind that CI feedback is measured in minutes, not seconds, by the time you see a failure, you've likely context-switched to something else. For truly fast feedback, run npm run lint and npm run type‑check locally before pushing, or configure your editor to surface these issues as you type. The CI pipeline serves as a safety net, not a primary feedback mechanism. Also note that this workflow runs jobs in parallel without needs dependencies, meaning a linting failure won't stop the test job from running. If you prefer to conserve CI resources and fail earlier, add needs: lint to the test job so it only runs after linting passes.
For larger teams or projects where staging environments matter, deployment previews add another layer of validation. The idea is straightforward: deploy each pull request to a temporary environment, run your E2E tests against it, and give reviewers a live URL to verify changes before merging. This catches environment-specific issues that don't surface when testing locally, misconfigured environment variables, CDN behaviors, serverless function timeouts, or third-party integrations that behave differently in production.
This approach has tradeoffs. Each preview deployment consumes build minutes and hosting resources, and the workflow adds several minutes to your PR feedback cycle. It's most valuable when your application depends heavily on infrastructure that's difficult to replicate locally, or when stakeholders need to review changes in a realistic environment. For smaller teams or simpler applications, running E2E tests against a local build during CI may be sufficient.
The following workflow deploys to Vercel, but the pattern applies to any preview hosting service (Netlify, AWS Amplify, Cloudflare Pages). It requires storing deployment credentials as repository secrets:
# .github/workflows/deploy-preview.yml
name: Deploy Preview
on:
  pull_request:
    branches: [main]
jobs:
  deploy-preview:
    name: Deploy Preview
    runs-on: ubuntu-latest
    # Only run on non-draft PRs to save resources during active development
    if: github.event.pull_request.draft == false
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

  - name: Setup Node.js
    uses: actions/setup-node@v4
    with:
      node-version: '22'
      cache: 'npm'
 
  - name: Install dependencies
    run: npm ci
 
  - name: Build application
    run: npm run build
 
  - name: Deploy to Vercel
    id: deploy
    uses: amondnet/vercel-action@v20
    with:
      vercel-token: ${{ secrets.VERCEL_TOKEN }}
      vercel-org-id: ${{ secrets.VERCEL_ORG_ID }}
      vercel-project-id: ${{ secrets.VERCEL_PROJECT_ID }}
      scope: ${{ secrets.VERCEL_ORG_ID }}
 
  # Simple health check to verify deployment succeeded
  - name: Verify deployment
    run: curl --fail --retry 3 --retry-delay 5 ${{ steps.deploy.outputs.preview-url }}
 
  - name: Comment preview URL on PR
    uses: actions/github-script@v7
    with:
      script: |
        github.rest.issues.createComment({
          issue_number: context.issue.number,
          owner: context.repo.owner,
          repo: context.repo.repo,
          body: ` Preview deployed to: ${{ steps.deploy.outputs.preview-url }}`
        })</code></pre>

This workflow creates a preview deployment for every pull request, giving reviewers a live URL to verify changes in a production-like environment.
We've intentionally skipped running E2E tests against the preview since they already run in the main test workflow, duplicating them would only increase CI costs without catching additional bugs.
Testing automation does transform how teams ship software, but the benefits depend entirely on how you write your tests. The examples in this chapter used queries like getByText('Buy groceries') and getByRole('button', { name: 'Add Task' }) for clarity, but these selectors are fragile in practice. Change a button label from Add Task to Create Task and every test that references it breaks. Multiply this across a large codebase and refactoring becomes a burden rather than a confidence boost, developers avoid changes because they don't want to spend half a day fixing broken tests.
To write tests that actually enable confident refactoring, prefer selectors that are decoupled from user-facing text: data‑testid attributes for stable element targeting, or role-based queries with flexible matchers. Structure your tests around user workflows rather than implementation details, and be willing to delete tests that cost more to maintain than the bugs they prevent. A smaller suite of resilient tests beats comprehensive coverage that nobody trusts.
As you build your testing infrastructure, remember that tests are code too. They need maintenance, refactoring, and thoughtful design. Write tests that document your application's behavior, catch real bugs, and give you confidence to move fast. When your test suite becomes reliable and comprehensive, you'll wonder how you ever shipped code without it.
The journey from writing your first test to building a robust testing culture takes time, but each test you write makes your application more stable and your development process more enjoyable. Your future self, your teammates, and your users will thank you for the time invested in automated testing.
