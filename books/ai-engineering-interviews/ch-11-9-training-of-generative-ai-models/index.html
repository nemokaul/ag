Chapter 9. Training of Generative AI Models

Training large language models involves coordinating multiple components that work together to form the end-to-end training pipeline. Figure 9-1 shows these components.

First, the Dataset and DataLoader decide which data points are available to form a batch. Then the Tokenizer and Data Collator decide how that batch is packaged into the exact tensor shapes and fields that the model expects. Then the model runs a forward pass on those tensors to produce predictions. A loss function compares the predictions to the targets to compute a scalar loss, and backpropagation computes gradients that the optimizer uses to update the model parameters. Finally, the scheduler updates the learning rate and the training loop records metrics and checkpoints so training can be monitored and resumed.

In this chapter, we unpack the core building blocks of the training pipeline and discuss training optimization techniques.

Training Core Components

This section introduces the core components of the LLM training pipeline, from raw data to parameter updates. We begin with how training examples are loaded and prepared, then move to tokenization and batching, and finally examine how the model computes loss and updates its weights.

Dataset and DataLoader

The Dataset is the entry point of the training pipeline. Conceptually, it is just a function that maps an integer index to a training example, but in LLM training that simple abstraction hides a lot of engineering. At this stage we usually work with raw samples such as documents, lines, and JSON records. The Dataset object is responsible for discovering the underlying files, building an index over them, so “sample 42B” is cheap to locate.

The DataLoader drives iteration over the Dataset during training. Its job is to keep the GPUs busy, that is, while one batch is on the device, DataLoader prepares the next few batches in the background. DataLoader is responsible for several key decisions including how samples are shuffled per epoch and how samples are assigned to GPUs.

Tokenizer and Data Collator

Tokenizer receives one batch of data from DataLoader, and converts the raw text into the model’s discrete input representation. Conceptually, it performs four main steps:

  1. Tokenization (text → tokens). The tokenizer splits the input string into a sequence of tokens according to its vocabulary and tokenization algorithm, for example BPE, WordPiece, or Unigram. Tokens may correspond to words, subwords, or even individual characters.

  2. Mapping tokens to IDs (tokens → input_ids). Each token is mapped to an integer ID from the model’s vocabulary, producing input_ids. This is the primary tensor the model consumes.

  3. Adding special tokens (optional). If add_special_tokens=True, the tokenizer inserts model-specific markers such as start/end delimiters, for example [BOS], [EOS], or separators for paired inputs, for example [SEP]. The exact strings differ by family: GPT-2 uses a single <|endoftext|>, BERT uses [CLS] and [SEP], and Llama uses <s> and </s>. Because these conventions vary, special tokens are part of the model contract.

  4. Truncation and padding (optional). If truncation=True and/or max_length is set, the tokenizer cuts sequences that exceed the maximum length. If padding=True or padding="max_length", it pads shorter sequences with a pad token up to a common length. Padding is often deferred to the data collator so that each batch can be padded dynamically to the longest example in that batch.

Figure 9-2 illustrates the four tasks above on the sentence example I like tea.

It is easy to call a tokenizer on either a single string or an entire batch of text. The Hugging Face AutoTokenizer handles all the details for us.

Data collator, which is the final step in preparing a batch, takes the individual tokenized samples and turns them into a uniform batch. A data collator is responsible for several key tasks:

1) Padding and truncation: Text sequences often have varying lengths. The collator pads shorter sequences with a special padding token so that all examples have the same length. Figure 9-3 illustrates this concept.

2) Constructing attention masks: The collator builds attention masks that indicate which positions correspond to real tokens and which correspond to padding. These masks allow the model to ignore padded positions during attention. Padded positions are separately excluded from the loss through the label mask. Figure 9-4 explains this task.

3) Building labels and targets: For next-token prediction, the collator typically derives the labels tensor by shifting the input sequence by one position and marking padding or ignored positions with a special index, for example -100. For classification or other supervised objectives, the collator maps example-level metadata into label IDs. Figure 9-5 explains this task.

4) Batching into tensors: Finally, the collator converts a list of per-example dictionaries into a single dictionary of batched tensors, for example, input_ids, attention_mask, and labels, ready to be moved to the device and passed into the model. Figure 9-6 illustrates this task.

In summary, while the dataset decides what examples are available and the DataLoader decides which examples form a batch, the data collator decides how that batch is packaged into the exact tensor shapes and fields that the model expects.

Do not confuse attention masking with loss masking. An attention mask controls which tokens the model can attend to, for example by preventing attention to padded positions. Loss masking controls which positions contribute to the training objective, commonly by setting their labels to an ignore value such as -100. In causal language modeling, a causal mask additionally prevents tokens from attending to future positions.

Forward Pass, Loss, and Backpropagation

Once the Dataset/DataLoader and the Tokenizer/Collator have produced a batched dictionary of tensors, for example, input_ids, attention_mask, and possibly labels, training proceeds through the core “training step” as follows:

  1. Forward pass (prediction). The model consumes the batch and produces outputs such as token-level logits for language modeling or class logits for classification. In a causal language model, the output logits typically has shape [B,T,V], where B is batch size, T is sequence length, and V is the vocabulary size.

  2. Loss computation (objective). The loss function compares the model outputs to training targets and returns a scalar loss. For next-token prediction, the common objective is cross-entropy between the predicted distribution at each position and the ground-truth next token. Positions that correspond to padding, or otherwise should not contribute to training, are masked out, often by setting their label to an ignore index such as -100. Conceptually, the loss aggregates over the valid, non-ignored token positions in the batch.

  3. Backpropagation (gradients). Calling loss.backward() computes gradients of the loss with respect to all trainable parameters via automatic differentiation. These gradients indicate how each parameter should change to reduce the loss.

  4. Parameter update (optimizer step). The optimizer, for example AdamW, uses the gradients to update model parameters. In most training loops, this is followed by optimizer.zero_grad() to clear gradients before the next step. Learning-rate schedules are typically applied here, or immediately before, to adjust step size over training.

So far, we have seen the basic single-GPU training step. For small models this loop is often sufficient, but large language models quickly run into memory and throughput limits on a single GPU or even a single machine. In practice, we therefore augment this basic training step with a range of optimization techniques for scaling and efficiency, which we discuss next.

Training Optimization

Training large-scale machine learning models, especially generative models, often exceeds the compute and memory capacity of a single machine. To overcome these limits and scale model training, various optimization techniques are employed.

Before diving into these techniques, let us clarify a few key concepts:

  • Weights: These are the model parameters used during the forward and backward passes. They represent learnable parameters of each layer. They are stored once per layer.

  • Activations: These are the intermediate outputs produced by each layer during the forward pass. Activations are the output value produced by each neuron, or layer, during the forward pass for a specific input batch.

  • Gradient: A gradient is the partial derivative of the loss with respect to a model parameter. It tells you how much the loss will change if that specific weight or bias changes. If activations are what the network “computes,” gradients are what the network “learns from.”

In modern transformer training, GPU memory is consumed by several major components: model weights, gradients, optimizer states, and activations. Their relative contribution depends on the model architecture, batch size, sequence length, numerical precision, optimizer, and distributed-training strategy. Activations can become a major memory bottleneck for large batches and long sequences, while optimizer states and gradients can dominate the model-state memory for large parameter counts. Techniques such as mixed-precision training, activation checkpointing, gradient accumulation, and state sharding reduce different parts of this memory footprint.

Mixed Precision Training

By default, deep learning models are trained using 32-bit floating-point (FP32) arithmetic, which is the standard single-precision format for representing real numbers. FP32 is numerically stable, but operations in FP32 are memory-intensive and computationally costly. Mixed-precision training alleviates this by combining lower-precision formats such as FP16 (16-bit floating point) or BF16 (brain floating point 16-bit) with FP32 during training.

One common approach to FP16 mixed-precision training maintains higher-precision parameter state for optimization while using lower-precision values for computation. <fig:mixed_pr> illustrates this classic FP16 setup.

  1. Master weights (FP32): a full-precision (FP32) version of the model weights that is used only for the optimizer update.

  2. Compute weights (FP16/BF16): a lower-precision version of the model weights (FP16 or BF16) that is used in the forward and backward passes.

Figure 9-7 illustrates the full loop for one training iteration.

  1. Forward pass: The FP16 weights are used for the forward pass because FP16 computation is faster and uses less memory. The forward pass produces an FP32 loss.

  2. Loss scaling: The FP32 loss is multiplied by a large scale factor, such as 1024 or 8192. This produces a scaled FP32 loss. The goal is to make the gradients larger before backpropagation so they do not underflow in FP16.

  3. Backpropagation: Backpropagation is performed using the scaled loss. Because the loss was scaled, the resulting gradients are also scaled. In this mixed-precision setup, these gradients are produced as scaled FP16 gradients.

  4. Copy / cast gradients: The scaled FP16 gradients are copied or cast to FP32. This gives scaled FP32 gradients, which are safer to manipulate numerically.

  5. Remove scale: The scaled FP32 gradients are divided by the same scale factor used earlier. This recovers the true FP32 gradients.

  6. Apply gradients: The optimizer uses the unscaled FP32 gradients to update the FP32 master weights. The master weights are kept in FP32 so that small updates are not lost due to FP16 rounding.

  7. Copy updated weights: The updated FP32 master weights are copied or cast back to FP16. These FP16 weights are then used for the next forward and backward pass.

This classic FP16 setup combines lower-precision computation with higher-precision optimization and loss scaling for numerical stability. BF16 has a much larger dynamic range and generally does not require loss scaling; exact precision handling depends on the training framework and hardware.

Activation Checkpointing

Activation checkpointing is a memory-saving technique that reduces GPU activation memory during training.

During the forward pass, the model computes activations, but only a subset of these are saved as checkpoints. In the backward pass, any unsaved intermediate activations are recomputed on the fly between checkpoints. This saves a significant amount of memory at the cost of additional compute.

Figure 9-8 illustrates this process: only the checkpointed layers store their activations, while the intermediate layers are recomputed during the backward pass.

Activation checkpointing is especially important when training large models or when training models on long sequences, as both of these increase activation memory. Activation checkpointing is also known as gradient checkpointing as the checkpointing is used during gradient computation in backpropagation.

Gradient Accumulation

Training large models often requires very large batch sizes to achieve stable convergence and good generalization. However, memory limitations on hardware, especially GPUs, can restrict the maximum batch size that fits into device memory. Gradient accumulation is a technique that simulates a larger batch size than what fits in GPU memory.

As Figure 9-9 illustrates gradient accumulation splits a large batch into smaller “micro-batches.” It runs forward and backward passes on each micro-batch. But in the backward pass, instead of updating the model weights after every micro-batch, it accumulates, or sums, the gradients from several micro-batches. Once the desired number of micro-batches has been processed, the optimizer applies a single update using the accumulated gradients.

This approach enables training with much larger effective batch sizes without increasing memory consumption.

Large-model training often combines activation checkpointing and gradient accumulation. Checkpointing reduces activation memory, while gradient accumulation enables larger effective batch sizes without increasing the memory required for each micro-batch.

Do not treat activation checkpointing and gradient accumulation as interchangeable memory optimizations. Activation checkpointing reduces activation memory by discarding intermediate activations and recomputing them during backpropagation. Gradient accumulation reduces per-step batch memory by processing several smaller micro-batches before performing one optimizer update. They solve different constraints and are commonly used together.

The optimization techniques above reduce memory use and improve numerical efficiency on a single device, but modern generative AI models are often too large to train on one GPU alone. This brings us to parallelism, where the training workload is split across multiple devices to make large-scale training feasible.

Parallelism in Training

Parallelism refers to splitting computation and memory requirements across multiple devices, such as GPUs or compute nodes, in a coordinated manner. Broadly, we can either split the data (the batch), or split the model by tensors (for example weight matrices), or split the model by layers. The choice of parallelism strategy depends on the model size, batch size, hardware setup, and training efficiency goals. At a high level, the main types of parallelism include:

  • Data parallelism: This is where you split the batch because a single GPU cannot hold the whole batch. Each GPU receives a slice of the dataset as well as a full replica of the model. Each GPU trains its copy of the model independently on its data shard, and then gradients, and parameters, are synchronized across GPUs so all replicas stay identical. Figure 9-10 illustrates this concept.

  • Model parallelism: This is when the model’s parameters are split across multiple GPUs because a single GPU cannot hold the whole model. Model parallelism includes several strategies.

    Tensor parallelism, illustrated in Figure 9-11 is a form of model parallelism where individual tensors inside a layer are split across GPUs. For example, in an attention or feedforward layer, the weight matrix is split column-wise and each GPU computes a shard of the matrix multiplication, and the results are combined. Tensor parallelism allows very large layers, for example, 32k×32k matrices, to fit across multiple GPUs and be computed in parallel.

    Pipeline parallelism, illustrated in Figure 9-12 is where the model layers are divided into stages and are processed sequentially across GPUs. For example, GPU 1 processes layers 1–12, and GPU 2 processes layers 13–24.

In practice, large-scale training often combines these strategies. Data parallelism increases throughput, tensor parallelism splits very large layer computations, and pipeline parallelism distributes layers across devices. Together, they help the model fit in memory while keeping GPUs busy and minimizing communication overhead.

When choosing a parallelism strategy in an interview, start by identifying what needs to be split. If the model fits on each GPU and you want more throughput, use data parallelism to split the batch. If individual layer computations are too large for one GPU, tensor parallelism splits operations within a layer. If the model stack itself is too large, pipeline parallelism distributes groups of layers across devices. Large-scale training often combines these approaches through hybrid parallelism.

So far, these methods scale training by distributing work across hardware. Mixture of Experts takes a different path: it scales model capacity architecturally by activating only a subset of specialized experts for each token.

Mixture of Experts (MoE)

Mixture of Experts (MoE) is an architectural approach for increasing model capacity without increasing computation proportionally. In a standard dense model, every token passes through the same set of parameters. In an MoE model, each token is routed to only a small subset of specialized subnetworks, called experts. This means the model can contain many more total parameters, but only a fraction of them are active for any given token.

The core insight is to decouple total model capacity from per-token computational cost. For example, a dense model with 100 billion parameters may use most of those parameters during each forward pass. An MoE model may also contain 100 billion total parameters, but if each token is routed to only 2 out of 64 experts, the computation depends mainly on the active experts rather than the full parameter count. As a result, MoE models can increase representational capacity while keeping training and inference costs closer to those of a smaller dense model.

Architecture and Routing

The key architectural change in MoE is that the model replaces some dense feed-forward networks with a set of parallel expert networks. Instead of sending every token through the same FFN, the model uses a router to decide which expert, or small set of experts, should process each token. This routing mechanism is what makes MoE efficient, but it also introduces new training challenges: the model must learn both useful representations and a good way to distribute tokens across experts.

Architecture Fundamentals

In a standard transformer block, each token passes through attention followed by a dense feed-forward network (FFN). In an MoE transformer, the FFN is replaced by an MoE layer. This MoE layer contains multiple parallel FFNs, called experts, and a gating network, or router, that selects which experts process each token.

The router is usually a learned linear layer applied to each token representation. For a model with E experts, the router produces E scores, one per expert. These scores are typically passed through a softmax to obtain routing probabilities. With top-k routing, the model selects the k highest-scoring experts, commonly k=1 or k=2, and sends the token only to those experts. The selected expert outputs are then combined, usually weighted by their routing probabilities.

This creates a natural split between dense and sparse computation. The attention layers and router are dense because they are applied to all tokens. The expert FFNs are sparse because each token activates only a small subset of experts. The efficiency gain comes from the gap between total parameters and active parameters: the model may contain many experts overall, but each token only pays the compute cost of the experts it uses.

The Routing Challenge

The main difficulty in MoE is not simply adding more experts, but learning how to use them effectively. The router must send each token to experts that can process it well, while also keeping traffic balanced across the expert pool. If routing becomes too concentrated, too uniform, or unstable during training, the model can lose much of the benefit of sparse activation.

  • Expert collapse occurs when the router learns to send most tokens to a small subset of experts while others receive little to no traffic. The underutilized experts fail to learn meaningful representations; they become “dead” parameters consuming memory without contributing capability. In extreme cases, a model might effectively use only 2 or 3 of 64 experts.

  • Representation collapse happens when all experts learn similar functions rather than specializing. The model pays the memory cost of multiple experts without gaining the representational diversity that makes MoE valuable.

  • Training instability can emerge from the discrete routing decision. Hard routing, selecting exactly which experts to use, creates non-differentiable operations that complicate gradient flow. The router and experts must co-adapt: the router learns which experts are good at what, while experts learn to handle the tokens they receive, creating complex optimization dynamics.

Training Challenges

These failure modes are why MoE training usually requires additional mechanisms beyond the standard language modeling objective. In particular, the model needs losses, routing constraints, and capacity limits that encourage balanced expert usage, stable routing, and meaningful expert specialization.

Load Balancing and Auxiliary Losses.

Preventing expert collapse requires explicit mechanisms that encourage the router to use the expert pool more evenly. The standard approach is to add an auxiliary load-balancing loss to the training objective. This loss penalizes routing patterns where a small number of experts receive most of the tokens while others remain underused.

A common load-balancing objective compares two quantities for each expert: the fraction of tokens routed to expert i, denoted fi, and the average router probability assigned to that expert, denoted pi. The loss is often proportional to ∑ifi·pi. Intuitively, this term becomes large when experts that receive high routing probability also receive a disproportionate share of tokens. It encourages token assignments and routing probabilities to remain more evenly distributed across the E experts.

MoE systems may also use capacity constraints to limit how many tokens each expert can process in a batch. If too many tokens are routed to the same expert, some tokens may be dropped, rerouted, or handled by a fallback path depending on the implementation. Other regularization terms may encourage diversity among experts or encourage the router to make confident decisions rather than spreading probability mass too broadly.

The auxiliary loss coefficient requires careful tuning. If it is too weak, expert collapse can occur. If it is too strong, the model may prioritize balanced routing over useful routing, forcing tokens toward experts that are not the best fit. The right balance depends on model scale, number of experts, batch size, and training dynamics.

Expert Specialization.

Beyond balancing expert usage, another important question is whether the experts learn meaningfully different functions. Ideally, different experts would specialize in different types of inputs, such as particular languages, domains, syntactic patterns, or semantic categories.

Empirical studies show mixed results. Some specialization often emerges naturally: certain experts may prefer specific token types, languages, or topics. However, this specialization is usually softer than intuition suggests. Experts often show preferences rather than clean boundaries, and the degree of specialization can vary across layers, model sizes, and training setups.

The routing decision itself may also encode useful information. Even before expert processing, the router’s selection reflects learned associations between token representations and expert behavior. Some architectures exploit this by conditioning routing on task or domain information, or by treating routing patterns as an additional signal about how the model organizes computation.

Scaling and Systems Considerations

So far, we have focused on the modeling side of MoE: routing, load balancing, and expert specialization. At large scale, these modeling choices become tightly coupled with systems concerns, because tokens must be routed across devices, experts must be sharded efficiently, and communication can become a major bottleneck.

Training at Scale: Expert Parallelism.

MoE models enable scaling to parameter counts impossible for dense models, but this scale introduces distributed systems challenges. Expert parallelism, sharding experts across devices, is the primary strategy.

In expert parallelism, each device holds a subset of experts. When processing a batch, tokens must be routed to their assigned experts, which may reside on different devices. This requires all-to-all communication: each device sends tokens to the devices holding their target experts and receives tokens destined for its local experts.

The communication pattern differs fundamentally from data parallelism, where the same model is replicated across devices and different data is processed, or tensor parallelism, where a single layer is split across devices. Expert parallelism creates a dynamic communication pattern where the volume of data transferred depends on routing decisions, not just batch size.

Capacity factors limit how many tokens each expert can process per batch, preventing any single expert from becoming a bottleneck. If an expert reaches capacity, excess tokens may be dropped, processed by a secondary expert, or handled by a fallback mechanism. This introduces a trade-off: higher capacity factors reduce dropped tokens but increase memory requirements and potential load imbalance.

System-Level Optimization.

Efficient MoE deployment requires careful system design beyond the basic parallelism strategy.

Communication overhead can dominate training time if not managed. Techniques include overlapping communication with computation, processing local experts while transferring tokens for remote experts, hierarchical routing, first routing within a device group and then across groups, and careful placement of experts to minimize cross-device traffic for common routing patterns.

Memory management is complex because different experts have different activation patterns. Memory-efficient approaches may use expert offloading, moving inactive experts to CPU memory, activation checkpointing tailored to sparse activation patterns, or dynamic batching that groups tokens by their routing decisions.

Inference optimization faces different challenges than training. During inference, batch sizes are often smaller, making the overhead of routing decisions proportionally larger. Speculative expert loading, expert caching based on predicted routing patterns, and quantization strategies that respect expert boundaries all contribute to practical deployment.

These systems constraints mean that MoE design is not just about adding more experts. Each architectural choice changes the balance between capacity, specialization, communication cost, memory usage, and hardware utilization.

Design Trade-offs

Practitioners face several key design decisions when building MoE models.

Number of experts affects capacity, specialization potential, and routing difficulty. More experts provide more capacity but make routing harder, because there are more choices, and may lead to underutilization. Common configurations range from 8 to 128 experts, with recent models pushing to thousands.

Expert granularity determines expert size. Fewer large experts provide more capacity per expert but less specialization. Many small experts enable fine-grained specialization but may not individually have enough capacity for complex computations.

Top-k selection balances compute cost against representational richness. k=1, a single expert per token, is most efficient but may miss beneficial expert combinations. k=2 provides redundancy and richer representations at doubled expert compute cost.

Which layers use MoE affects the sparsity pattern. Some architectures use MoE for all FFN layers; others use MoE only for a subset, for example every other layer, to balance efficiency with training stability.

The optimal configuration depends on target model scale, available hardware, and the specific capability-efficiency trade-off required for the application.

When explaining MoE in an interview, do not stop at “different tokens go to different experts.” Start with the central trade-off: MoE increases total model capacity without increasing per-token compute proportionally because each token activates only a small subset of experts. Then discuss the main challenge, routing: experts must receive useful and reasonably balanced traffic to avoid expert collapse. Finally, mention the systems cost: expert parallelism introduces all-to-all communication, so the theoretical compute savings do not automatically translate into proportional training or inference speedups.

MoE improves efficiency by activating only part of a large model for each token. Knowledge distillation approaches the same capability-efficiency problem from the opposite direction: instead of sparsely using a very large model, it trains a smaller model to imitate a larger one. The goal is to preserve as much of the teacher model’s behavior as possible while reducing inference cost, memory use, and latency.

Knowledge Distillation

Knowledge distillation trains a smaller student model to imitate the behavior of a larger teacher model. Unlike techniques that make the same model cheaper to train or serve, distillation creates a new model: the student can have fewer parameters, a different architecture, or a design better suited to the target hardware. The goal is to preserve as much of the teacher’s behavior as possible while reducing inference cost, memory use, and latency.

Soft distillation. The classic approach, introduced by Hinton et al. (2015), trains the student on the teacher’s full probability distribution over the vocabulary rather than only the correct next token. Both teacher and student logits are divided by a temperature T>1 before softmax. This softens the distribution and reveals structure among lower-probability tokens.

For example, if the teacher assigns one token probability 0.001 and another probability 0.0001, both may look irrelevant under a hard label, but the teacher still considers the first token 10× more likely than the second. This relative information is what Hinton called “dark knowledge”: the ranking of incorrect answers can encode similarity structure that helps the student generalize.

The loss combines KL divergence between the softened teacher and student distributions with standard cross-entropy on the hard labels:

ℒ=α·T2·KL(σ(zt/T)‖σ(zs/T))+(1−α)·CE(y,zs)

where zt and zs are the teacher and student logits, σ is softmax, T is the temperature, and α controls the balance between the distillation loss and the hard-label loss. The T2 factor compensates for the change in gradient magnitude introduced by temperature scaling.

Hard distillation. In hard distillation, the student is trained on the teacher’s generated outputs using standard supervised fine-tuning. Instead of matching the teacher’s full probability distribution, the student learns from (prompt, teacher_response) examples. This is common in LLM distillation because closed-source teacher models, such as GPT-4 or Claude, usually expose generated text but not logits.

Hard distillation is simpler and easier to apply at scale because it only requires teacher-generated responses. However, it discards the distributional information available in soft labels. The student sees what the teacher produced, but not how strongly the teacher preferred that answer over alternatives. Figure 9-13 compares soft and hard distillation.

Most small language models deployed today, including Phi-3 (3.8B), Gemma 2 (2B), LLaMA 3.2 (1B/3B), and Mistral-Small, were distilled from larger teachers using some combination of hard and soft distillation. The result is a family of models purpose-built for on-device and latency-sensitive deployment: a 3B distilled student quantized to INT4 fits under 2 GB and runs on a phone, while retaining much of the teacher’s capability on focused tasks. Chapter 12 covers a specialized form, reasoning distillation, where the teacher’s chain-of-thought traces are distilled into a smaller model.

Summary

In this chapter we walked through the end-to-end training pipeline for large language models, from raw text on disk to updated model weights. We started with the Dataset and DataLoader, which define what examples exist, how they’re indexed and shuffled, and how batches are prepared efficiently to keep accelerators busy. Next we covered the Tokenizer and Data Collator, which translate text into token IDs and package variable-length samples into uniform tensors with padding, attention masks, and correctly shifted labels. With the batch prepared, we stepped through the core training step—forward pass, loss computation, backpropagation, optimizer update, and learning-rate scheduling.

We then zoomed out to practical scaling optimizations used in modern LLM training. These include mixed-precision training, activation checkpointing, gradient accumulation, and multi-GPU parallelism strategies, data, tensor, and pipeline parallelism, explaining how they trade compute, memory, and communication to make large models trainable. We then introduced Mixture of Experts (MoE), a sparse architecture that scales model capacity by activating only a subset of experts for each token. This allows MoE models to achieve much larger total parameter counts without incurring the full compute cost of dense models, while also introducing new challenges in routing, load balancing, and distributed systems design.

Finally, we covered knowledge distillation, a complementary strategy for model efficiency. Instead of making models larger, distillation transfers the behavior of a large teacher model into a smaller student model, producing models that are easier to deploy while retaining much of the original capability.

Taken together, these ideas show that training modern generative models is not just about defining a loss and running gradient descent. It also requires careful engineering of data pipelines, numerical efficiency, distributed execution, architecture design, and model compression.

Interview Questions and Answers

Thread: The Training Data Pipeline

  1. Walk me through how training data flows from raw text to gradient updates.

    Raw text is first cleaned and tokenized into integer token IDs. These IDs are organized into training examples, usually fixed-length sequences for next-token prediction. A Dataset defines how each example is retrieved from storage, while a DataLoader samples examples, loads them in parallel, prefetches batches, and moves data efficiently toward the GPU.

    A data collator turns individual examples into a batch by stacking token IDs, padding sequences when necessary, creating attention masks, and constructing labels. For causal language modeling, the labels are the input sequence shifted by one position, so the model learns to predict the next token.

    The batch is sent through the model, which produces vocabulary logits at each position. The loss function, typically cross-entropy, compares those logits with the target labels. Backpropagation computes gradients from the loss, and the optimizer applies those gradients to update the model parameters.

  2. How do you handle datasets too large to fit in memory, and what does an “epoch” mean at that scale?

    When the dataset is too large to fit in RAM, the goal is to keep the GPUs fed without loading the entire corpus at once. Common approaches include:

    • Memory-mapped or sharded datasets: Store preprocessed/tokenized data in files that can be read by offset, such as binary shards, Arrow files, WebDataset shards, or memory-mapped arrays. This allows random or semi-random access without loading everything into RAM.

    • Streaming: Read examples on the fly from local SSDs, network storage, or object stores. Streaming scales to very large corpora, but it can become I/O-bound if data cannot be read, decoded, tokenized, and transferred fast enough to keep the GPUs busy. It also requires careful handling of shuffling, retries, and worker failures.

    • Caching: Cache frequently used shards, tokenized outputs, or decoded examples on local NVMe. This reduces repeated preprocessing and network reads across epochs, but requires cache invalidation, versioning, and enough local storage.

    At distributed scale, each worker or GPU should receive a distinct shard or slice of the data so that examples are not duplicated unnecessarily. Distributed samplers, shard assignment, and epoch-dependent shuffling are used to maintain randomness while ensuring that different nodes process different parts of the corpus.

    For language model pretraining, long documents are often tokenized and then packed or sliced into fixed-length blocks. This avoids loading entire documents into memory and produces efficient fixed-size training examples for next-token prediction.

    A note on epochs: when you are streaming from a massive corpus, “epoch” becomes a convention rather than one full pass over the data. Most large-scale pretraining runs define an epoch as a fixed number of tokens or optimizer steps, and rely on long-horizon shuffling to approximate coverage. Progress is typically tracked in tokens seen, not epochs completed.

  3. How do you batch variable-length sequences efficiently?

    Naively padding every sequence to a fixed global maximum length wastes memory and computation, because the model spends FLOPs on padding tokens.

    Common strategies include:

    • Dynamic padding: Pad only to the longest sequence in the current batch.

    • Length-based bucketing: Group examples with similar lengths so each batch requires less padding.

    • Token-budget batching: Choose batches based on a maximum number of tokens rather than a fixed number of examples, so shorter sequences can use larger batch sizes.

    • Packing: Concatenate multiple short sequences into one context window, often separated by special tokens, to reduce or eliminate padding.

    • Padding to hardware-friendly multiples: Pad sequence lengths to multiples such as 8, 16, or 64 to improve GPU efficiency.

    The data collator handles the mechanics: it pads shorter sequences, creates an attention mask with 1 for real tokens and 0 for padding, and masks padding positions in the labels so they do not contribute to the loss. For packing, it must also ensure that document boundaries and loss masks are handled correctly.

  4. In autoregressive language model training, how are attention masks, labels, and the loss constructed?

    In autoregressive training, there are usually two masking concepts. The first is the padding mask, often called the attention_mask, where 1 marks real tokens and 0 marks padding tokens. This prevents the model from attending to padded positions. The second is the causal mask, a lower-triangular mask that prevents each token from attending to future tokens. Together, these masks ensure that the model attends only to valid previous context.

    For labels, the training objective is next-token prediction: at position i, the model predicts the token at position i+1. In practice, some frameworks explicitly shift the labels, while others accept labels = input_ids and perform the shift inside the model. Positions that should not contribute to the loss, such as padding tokens or prompt tokens during instruction tuning, are set to −100, which is PyTorch’s default ignore index for cross-entropy. The collator is responsible for constructing the batch tensors, including the padding mask and the label tensor.

    Given that setup, the loss computation follows directly. The model’s forward pass produces a logits tensor of shape [B,T,V], where B is the batch size, T is the sequence length, and V is the vocabulary size. At each sequence position, the logits contain one score for every token in the vocabulary. The logits at position i are compared against the ground-truth token at position i+1, the same shift-by-one described above. The shifted logits are reshaped from [B,T,V] to [B×T,V], and the labels are reshaped to [B×T]. In PyTorch, CrossEntropyLoss(ignore_index=-100) skips positions labeled −100, applies the softmax internally, and averages the loss over valid positions. Lower loss means the model is assigning higher probability to the correct next token.

Thread: Mixed Precision Training

  1. What is mixed-precision training, why does it matter for LLMs, and how does the training loop work?

    Mixed-precision training uses a combination of lower-precision formats, such as FP16 or BF16, and higher precision, typically FP32, during training. The goal is to perform computationally expensive operations in lower precision for greater throughput and lower memory usage, while using higher precision where additional numerical stability is helpful.

    A typical mixed-precision training iteration has the following steps:

    1. Forward pass: Computationally intensive operations, such as matrix multiplications, are typically performed in FP16 or BF16. Numerically sensitive operations may be performed or accumulated in higher precision according to the framework’s autocasting policy.

    2. Loss computation: The model computes the loss. The framework may evaluate or accumulate parts of the loss computation in higher precision for numerical stability.

    3. Loss scaling, when needed: With FP16, the loss may be multiplied by a scale factor before backpropagation to prevent very small gradients from underflowing to zero. BF16 generally does not require loss scaling because it has a much larger dynamic range.

    4. Backward pass: Backpropagation computes gradients using the selected precision policy. If loss scaling was used, the gradients are subsequently unscaled before they are used by the optimizer.

    5. Optimizer step: The optimizer updates the model parameters. Optimizer states and parameter updates are often maintained or accumulated in FP32 so that small updates are not lost to rounding.

    Modern frameworks automate much of this process through autocasting, choosing lower precision for operations that benefit from faster computation while using higher precision where needed for stability.

    The main benefits are higher training throughput and lower memory consumption, which can make it possible to train larger models, use larger batches, or process longer sequences on the same hardware.

  2. What is loss scaling and how does dynamic loss scaling work?

    In FP16 training, very small gradients may fall below the representable range and underflow to zero. If this happens, the corresponding parameter updates are lost. Loss scaling prevents this by multiplying the loss by a large scale factor before backpropagation. Because gradients are proportional to the loss, this also scales up the gradients. Before the optimizer step, the gradients are divided by the same scale factor so the update uses the correct gradient values. PyTorch describes this as multiplying the loss, running backward on the scaled loss, and then unscaling each parameter’s gradient before the optimizer update.

    Static loss scaling uses a fixed scale factor chosen before training. If the scale is too small, gradient underflow can still occur. If it is too large, gradients may overflow to inf or NaN. This makes static scaling simple but often hard to tune.

    Dynamic loss scaling adjusts the scale automatically during training. It starts from an initial scale, commonly 216=65,536 in PyTorch, and checks whether the gradients are finite. If gradients are finite for a configured number of steps, the scale is increased, typically doubled. If inf or NaN gradients are detected, the optimizer step is skipped, the scale is reduced, typically halved, and training continues with the smaller scale. PyTorch’s GradScaler implements this behavior; in current PyTorch, the preferred API is torch.amp.GradScaler("cuda").

  3. What is the difference between FP16 and BF16, and why are some operations performed in higher precision?

    FP16 and BF16 both use 16 bits, but they allocate those bits differently.

    FP16 uses 1 sign bit, 5 exponent bits, and 10 mantissa bits. It provides greater precision within its representable range, but its relatively small exponent range makes it more susceptible to numerical overflow and underflow.

    BF16 uses 1 sign bit, 8 exponent bits, and 7 mantissa bits. Because it has the same number of exponent bits as FP32, it provides a much larger dynamic range than FP16, but with less mantissa precision.

    This difference has an important consequence for training. FP16 often requires loss scaling to prevent small gradients from underflowing to zero. BF16’s larger dynamic range usually makes loss scaling unnecessary, which is why BF16 is often preferred for training large models when the hardware supports it.

    Mixed-precision training does not mean that every operation is performed in 16-bit precision. Numerically sensitive operations are often computed or accumulated in higher precision, commonly FP32, to improve stability. Examples include:

    • Softmax and normalization: These operations involve reductions, exponentiation, means, or variances that can be sensitive to limited numerical precision.

    • Loss computation: Losses such as cross-entropy are commonly evaluated using numerically stable higher-precision operations.

    • Optimizer updates: Parameter updates can be very small, so optimizer states and updates are often maintained or accumulated in FP32 to avoid losing small changes through rounding.

    Modern training frameworks manage these choices automatically through autocasting, selecting lower precision for operations that benefit from faster computation while using higher precision where additional numerical stability is needed.

Thread: Memory and Compute Optimization

  1. Where does GPU memory go during LLM training?

    Four components compete for GPU memory:

    • Model weights: A 7B model in FP32 requires 7×109×4 bytes ≈28 GB. Depending on the mixed-precision implementation, training may maintain higher-precision parameter or optimizer state in addition to lower-precision values used for computation.

    • Optimizer states: Adam maintains two momentum buffers per parameter, each the same size as the weights. For 7B parameters in FP32, that adds about 56 GB.

    • Gradients: One gradient tensor per parameter. Another 28 GB in FP32 for a 7B model.

    • Activations: Intermediate values stored for backpropagation. Their memory usage depends strongly on batch size, sequence length, hidden dimension, model depth, and the checkpointing strategy, and they can become a major memory bottleneck for large batches or long contexts.

    A rough estimate for 7B with Adam in FP32 is 28 + 56 + 28 ≈112 GB before activations. Techniques like FSDP, ZeRO, activation checkpointing, and gradient accumulation exist precisely to manage this budget.

  2. What is activation checkpointing, when is it necessary, and what gets saved versus recomputed?

    Activation checkpointing, also called gradient checkpointing, is a memory-saving technique that stores only selected activations during the forward pass rather than keeping all intermediate activations needed for backpropagation. During the backward pass, the discarded activations are recomputed from the saved checkpoints when they are needed to calculate gradients.

    It is particularly useful when activation memory becomes a bottleneck, such as when training deep models, using large batch sizes, or working with long sequences. The training computation can be divided into segments: activations at selected boundaries are retained, while intermediate activations within those segments are discarded after the forward pass and recomputed during backpropagation.

    The trade-off is memory for compute. Saving fewer activations reduces peak GPU memory usage, but requires more recomputation during the backward pass. More aggressive checkpointing therefore saves more memory but generally increases training time.

    Activation checkpointing does not change the training objective or the gradients being computed; it changes how intermediate values needed for those gradients are obtained. In practice, training frameworks handle the required recomputation while preserving the expected training behavior.

  3. How does gradient accumulation work, how does it differ from activation checkpointing, and how does it interact with the training loop and learning-rate schedule?

    Gradient accumulation allows the optimizer to use a larger effective batch than can fit in GPU memory at once. Instead of updating the model after every micro-batch, training runs forward and backward passes on several micro-batches and accumulates their gradients. After the configured number of accumulation steps, the optimizer performs one parameter update and the accumulated gradients are cleared.

    On a single device, the effective batch size is approximately:

    effective batch size=micro-batch size×accumulation steps

    For example, a micro-batch size of 512 with 4 accumulation steps gives an effective batch size of 2,048 examples. In distributed data-parallel training, the effective global batch size also includes the number of data-parallel workers:

    global batch size=micro-batch size×accumulation steps×data-parallel world size

    Because gradients from multiple micro-batches contribute to one optimizer update, gradient accumulation approximates the gradient that would have been obtained from processing the larger batch at once, provided the gradients are scaled or averaged appropriately.

    Contrast with activation checkpointing. The two techniques address different memory constraints. Activation checkpointing reduces activation memory by discarding selected intermediate activations and recomputing them during backpropagation. Gradient accumulation reduces per-micro-batch memory pressure by processing a large effective batch as several smaller micro-batches. The two techniques are complementary and are often used together.

    Correct loop order. Gradients must remain accumulated until all micro-batches belonging to the effective batch have been processed. A common mistake is to clear the gradients after every micro-batch, which prevents accumulation. Conceptually, the sequence is:

    1. Run the forward and backward passes for a micro-batch.

    2. Repeat for the remaining accumulation steps without clearing the gradients.

    3. Perform one optimizer update after the final micro-batch.

    4. Clear the gradients before beginning the next accumulation cycle.

    In APIs such as PyTorch, this means that optimizer.step() and optimizer.zero_grad() occur once per accumulation cycle rather than once per micro-batch.

    Interaction with learning-rate schedules. Learning-rate schedules are generally defined in terms of optimizer steps, not micro-batches. With gradient accumulation, several micro-batches correspond to a single optimizer step, so warmup duration and total training steps must be interpreted consistently. If a schedule was originally specified in micro-batch steps, it must be converted to optimizer steps using the accumulation factor. If it is already specified in optimizer steps, no additional adjustment is needed. The learning-rate scheduler should normally advance when the optimizer advances.

  4. What is gradient clipping and why is it essential for LLM training?

    Gradient clipping caps gradient magnitudes before the optimizer step to prevent exploding gradients from destabilizing training. Two variants exist.

    Clip-by-norm, the standard for LLMs, computes the global norm across all gradients and rescales them proportionally if the norm exceeds a threshold. A threshold of 1.0 is typical. In PyTorch, this is implemented via torch.nn.utils.clip_grad_norm_.

    Clip-by-value clamps each gradient element independently to a fixed range. It is simpler but can distort gradient direction, so it is less common for LLMs.

    When using mixed precision, gradient clipping must happen after unscaling so the gradients are at their true magnitudes before the norm is computed.

  5. Why is AdamW the standard optimizer for LLM training?

    AdamW combines three properties that matter at scale.

    • Adaptive learning rates: Adam tracks exponential moving averages of the gradients and their squared values, corresponding to first- and second-moment estimates. These statistics allow the optimizer to adapt the effective learning rate for each parameter.

    Momentum: β1, typically 0.9, is the decay rate for the first-moment estimate and smooths noise, while β2, typically 0.95-0.999, is the decay rate for the second-moment estimate and stabilizes step size.

    Decoupled weight decay: Standard Adam conflates L2 regularization with the adaptive step, weakening regularization for large-gradient parameters. AdamW applies weight decay directly to weights after the gradient step, making regularization uniform. Typical values are 0.01—​0.1.

    AdamW is widely used for Transformer and LLM training because it combines Adam’s adaptive updates with decoupled weight decay. Other optimizers, such as Adafactor, are also used in some large-scale training settings.

Thread: Training Stability, Monitoring, and Scaling

  1. Describe a typical learning rate schedule for LLM pretraining, and how does batch size affect the learning rate?

    Most runs use a warmup-then-decay pattern.

    Warmup: The learning rate ramps linearly from near-zero to the peak value over the first 1—​10% of training steps. Early gradients are noisy because weights start randomly initialized; a large learning rate at this stage can cause divergence.

    Decay: After warmup, the rate decreases gradually. Cosine annealing is the most popular choice: it follows a half-cosine curve from peak down to a small minimum, often 10% of peak. Linear decay is simpler but less common. Some fine-tuning runs use inverse-square-root decay.

    The peak learning rate depends on model size, batch size, optimizer, and training setup. Larger models often use smaller learning rates, while increasing batch size can sometimes support a larger learning rate.

    On the batch-size relationship specifically, the linear scaling rule from Goyal et al. (2017) says that when you multiply the batch size by k, multiply the learning rate by k. A k-times-larger batch averages k times as many gradient samples, producing a cleaner signal that can support a proportionally larger step. This holds well up to a critical batch size from McCandlish et al. (2018), beyond which returns diminish and the relationship weakens. For very large batches, square-root scaling, multiplying the learning rate by k, is sometimes more stable. The practical workflow is to set the batch size based on memory and throughput constraints, then tune the peak learning rate with small-scale sweeps. Linear or square-root scaling can provide useful starting heuristics, but the appropriate peak learning rate is ultimately tuned for the model, optimizer, and training regime.

  2. What do you monitor during a training run to catch problems early?

    You should monitor:

    • Training loss: It should decrease smoothly. Sudden spikes may indicate data issues, learning rate problems, or numerical instability. Occasional small spikes are normal; repeated large ones are not.

    • Gradient norms: Track the global gradient norm each step. Sustained increases suggest the model is heading toward instability. Jumps to NaN or inf mean immediate intervention.

    • Learning rate curve: Verify the schedule looks correct. A misconfigured warmup or accumulation factor produces a visibly wrong curve.

    • Throughput: Tokens per second or FLOP utilization. Drops indicate I/O bottlenecks, communication stalls, or hardware faults.

    • Loss spikes: These can result from corrupted batches, poorly mixed data domains, or numerical overflow. Recovery strategies include skipping the batch, rolling back to a recent checkpoint, or temporarily lowering the learning rate.

    Dead neurons, meaning activations stuck at zero, and layer-wise gradient statistics are useful for deeper investigation when training stalls without obvious loss symptoms.

  3. What is Model FLOP Utilization (MFU) and why does it matter?

    MFU measures what fraction of a GPU’s theoretical peak compute is spent on actual model operations. For a transformer with N parameters, each training step costs approximately 6N FLOPs per token, with 2N for the forward pass and 4N for the backward pass. MFU is:

    MFU=tokens per second×6Nhardware peak FLOPS

    PaLM reported 46.2% MFU on TPUv4. Typical values on A100 clusters range from 30% to 55% depending on parallelism strategy and interconnect quality.

    Raw throughput, measured in tokens per second, does not account for hardware capability. A well-optimized cluster achieves higher MFU, meaning less wasted compute per dollar. MFU excludes overhead from communication, activation recomputation, and framework bookkeeping. Hardware FLOP Utilization (HFU) counts all FLOPs including overhead, so HFU is always greater than MFU.

  4. What goes into a training checkpoint and how do you resume after a failure?

    A complete checkpoint saves:

    • model weights, both FP32 master and FP16 or BF16 copies if using mixed precision,

    • optimizer state, including Adam’s first and second moment estimates for every parameter,

    • learning rate scheduler state,

    • random number generator states across all GPUs for reproducibility,

    • global step counter and tokens-seen counter,

    • data loader state, meaning which samples have been consumed.

    Resumption loads all of these and continues from exactly where training stopped. Missing any piece, especially optimizer state or RNG seeds, causes the resumed run to diverge from the original trajectory.

    Checkpointing frequency balances write overhead against lost work: saving every 1,000—​5,000 steps is common. Most teams keep the last k checkpoints and the best-validation one, deleting the rest. Cloud training adds preemption handling: the job registers a signal handler that triggers an emergency checkpoint when a preemption notice arrives.

  5. What are scaling laws and how do they guide training decisions?

    Scaling laws describe how model performance, usually measured as loss, improves with model size, dataset size, and compute budget. The key result from DeepMind’s Chinchilla paper by Hoffmann et al. (2022) is that for a fixed compute budget, you should scale model parameters and training tokens roughly equally. Earlier practice, such as GPT-3, used very large models with comparatively less data; Chinchilla showed this was compute-suboptimal.

    Given compute budget C, there is an optimal model size N and dataset size D such that C∝6ND.

    Scaling laws guide several decisions:

    • Model sizing: Choose parameters proportional to available training data, not just hardware.

    • Data collection: Ensure enough high-quality tokens before scaling up the model.

    • Compute allocation: Predict expected loss at different scales to decide if a run is worth the investment.

    Post-Chinchilla models like LLaMA trained smaller models on far more data than the Chinchilla ratio suggests, optimizing for inference efficiency rather than training compute. The right ratio depends on whether you optimize for training cost or deployment cost.

Thread: Distributed Training and Parallelism

  1. What are the main strategies for distributing training across multiple GPUs?

    There are two broad families.

    Data parallelism replicates the model on every GPU and splits the data. Each GPU processes a different mini-batch, computes gradients locally, and synchronizes them so every copy stays identical. The model must fit on a single GPU, or be sharded in advanced variants like FSDP and ZeRO.

    Model parallelism splits the model itself across GPUs:

    • Tensor parallelism: partitions computation within individual layers, for example splitting a weight matrix column-wise.

    • Pipeline parallelism: assigns different groups of layers to different GPUs.

    • Expert parallelism: distributes Mixture-of-Experts experts across GPUs, each device holding a subset.

    Large-scale training combines multiple strategies into hybrid parallelism.

  2. How do DDP, FSDP, and ZeRO differ, and when would you use each?

    DDP, FSDP, and ZeRO are all approaches to data-parallel training, but they differ mainly in how much of the model’s training state is replicated versus sharded across GPUs.

    Distributed Data Parallel (DDP) keeps a complete copy of the model on every GPU. Each GPU processes a different portion of the batch, computes gradients locally, and then synchronizes those gradients across workers, typically using all-reduce. DDP is conceptually simple and efficient when the model, gradients, and optimizer states fit comfortably in the memory of each GPU. Its main limitation is memory redundancy: every worker stores essentially the same training state.

    Fully Sharded Data Parallel (FSDP) reduces this redundancy by sharding parameters, gradients, and optimizer states across GPUs. When a layer is needed for computation, the required parameters are gathered across workers, used for the forward or backward pass, and then released or reshaped as training proceeds. This substantially reduces per-GPU memory requirements, at the cost of additional communication and implementation complexity.

    ZeRO, introduced by DeepSpeed, takes a staged approach to eliminating the same redundancy:

    • ZeRO-1 shards optimizer states.

    • ZeRO-2 shards optimizer states and gradients.

    • ZeRO-3 also shards model parameters.

    ZeRO-3 and fully sharded FSDP are therefore conceptually similar: both distribute parameters, gradients, and optimizer states across workers rather than replicating the full training state on every GPU. They differ primarily in implementation, communication strategies, tooling, and ecosystem.

    As a rule of thumb, use DDP when the full training state fits comfortably on each GPU and simplicity and throughput are the priorities. Use FSDP when memory becomes the primary constraint and you want a native PyTorch sharding solution. Use ZeRO when working in the DeepSpeed ecosystem, particularly when you want staged sharding or features such as CPU or NVMe offloading.

    These techniques address replication of the training state. At very large scales, they may be combined with tensor, pipeline, or other forms of model parallelism when additional partitioning of the model’s computation is required.

  3. Walk me through how DDP works, including the all-reduce operation it relies on.

    Distributed Data Parallel (DDP) replicates the full model on each GPU and gives each replica a different portion of the training batch. Each GPU independently runs the forward pass, computes the loss, and performs backpropagation on its local data.

    During backpropagation, each replica produces its own local gradients. Before the optimizer updates the parameters, these gradients must be synchronized so that all model replicas remain identical. DDP performs this synchronization using an all-reduce collective operation.

    In an all-reduce, every worker contributes its local gradient tensor. The gradients for corresponding parameters are combined, typically by summing and averaging them across workers, and the resulting gradient is made available to every worker. Each GPU therefore ends up with the same synchronized gradients and performs the same optimizer update, keeping all replicas in sync.

    For example, with four GPUs, each GPU processes a different micro-batch and computes a local gradient. All-reduce combines those four gradients into a single averaged gradient and distributes that result back to all four GPUs. The GPUs then independently apply the same parameter update.

    DDP also overlaps communication with backpropagation through gradient bucketing. Rather than waiting until the entire backward pass is complete, gradients are grouped into buckets. As soon as the gradients in a bucket are ready, their all-reduce can begin while backpropagation continues through earlier layers. This hides some of the communication cost behind computation.

    The key limitation is that DDP reduces data-processing time but not model-state memory: every GPU still holds a complete copy of the model, gradients, and optimizer states. When that replicated state no longer fits comfortably on each GPU, sharded approaches such as FSDP or ZeRO become more appropriate.

  4. How does tensor parallelism work?

    Tensor parallelism splits computation within individual layers across GPUs. For a transformer feed-forward layer with weight matrix W, it partitions W column-wise or row-wise so each GPU computes part of the matrix multiplication in parallel. Partial results are combined with an all-reduce or all-gather.

    Each GPU’s per-layer memory scales as 1/N for N GPUs, but synchronization happens within every layer at every forward and backward step. NVLink or NVSwitch, within a node, provides sufficient bandwidth; cross-node tensor parallelism is rare because of latency. Megatron-LM is the most widely used implementation, and most frontier models, including GPT-4, PaLM, and LLaMA, use tensor parallelism within each node.

  5. How does pipeline parallelism work, and how do you handle the bubble?

    Pipeline parallelism divides the model into sequential stages, each assigned to a different GPU. The challenge is the pipeline bubble: while GPU 0 computes its forward pass, downstream GPUs sit idle.

    Two scheduling strategies address this.

    GPipe: Split each mini-batch into m micro-batches. All of them run forward through the pipeline, then all backward passes run in reverse. The bubble ratio is (p−1)/(m+p−1), where p is the number of stages. With 4 stages and 16 micro-batches, about 16% of the schedule is idle. The downside is that all m sets of activations must be held simultaneously.

    1F1B (one-forward-one-backward): After a warmup phase, each stage alternates between one forward and one backward micro-batch. It has the same bubble ratio, but backward passes release memory as they go, significantly reducing peak activation usage.

    A useful rule of thumb is that m≥4p keeps the bubble around 15—​20%, which is acceptable for most setups. Reducing it below 5% requires m≥20p. Pipeline parallelism works well across nodes since communication happens only at stage boundaries.

  6. How does hybrid parallelism combine these strategies, including sequence and context parallelism, and what communication challenges arise?

    Hybrid parallelism uses each strategy where it works best:

    • Tensor parallelism within a node, where NVLink provides high bandwidth for frequent per-layer synchronization.

    • Pipeline parallelism across nodes, where only stage-boundary communication is needed.

    • Data parallelism via DDP, FSDP, or ZeRO across replicas of the full pipeline, each processing different data.

    A typical 175B model across 1,024 GPUs might use 8-way tensor parallelism within each node, 16-way pipeline parallelism across nodes, and 8-way data parallelism across replica groups. Systems like DeepSpeed and Megatron-LM manage these configurations. The key challenge is balancing dimensions to maximize throughput while minimizing communication overhead and memory waste.

    Two additional dimensions handle activation memory and very long sequences. Sequence parallelism (Korthikanti et al., 2022) distributes activation memory along the sequence dimension. In a typical Megatron-LM setup, tensor parallelism already splits attention and FFN computations across GPUs, but LayerNorm and dropout activations are replicated on every device. Sequence parallelism shards these replicated activations along the sequence length, reducing their memory footprint by 1/N for N GPUs. Context parallelism is a broader approach that splits the full attention computation across devices for very long sequences. Ring Attention (Liu et al., 2023) is one implementation: each GPU holds a chunk of the sequence and passes key/value blocks around a ring, enabling near-linear memory scaling with sequence length. Sequence parallelism addresses activation memory within typical context lengths, while context parallelism becomes necessary when sequences are too long for even sharded activations to fit.

    These placements are driven by communication reality, and several challenges shape them:

    • Bandwidth limitations: Synchronizing large gradient tensors across nodes connected by Ethernet rather than NVLink can bottleneck training.

    • Latency: Each synchronization point adds delay. Cumulative latency across thousands of steps reduces GPU utilization.

    • Stragglers: In heterogeneous or busy clusters, slower GPUs force all others to wait during synchronous operations.

      Key mitigation techniques include:

    • Gradient bucketing: all-reduce each bucket as soon as its backward computation finishes, overlapping communication with computation.

    • Asynchronous communication: PyTorch supports async_op=True for non-blocking collectives, letting computation proceed during transfers.

    • Delayed synchronization: combined with gradient accumulation, all-reduce can be amortized over multiple steps, reducing synchronization frequency.

    • High-speed interconnects: NVLink, NVSwitch, and InfiniBand reduce raw transfer time.

    Each placement maps onto this reality: tensor parallelism stays within a node to exploit NVLink, pipeline parallelism spans nodes to minimize inter-node traffic, and data parallelism via DDP, FSDP, or ZeRO runs across replicas.

Thread: Mixture of Experts

  1. What is Mixture of Experts and how does it scale more efficiently than dense models?

    MoE decouples model capacity from computational cost through sparse activation. A dense model uses all parameters for every token. An MoE model routes each token to a small subset of experts, so a model with 100B total parameters might activate only 10B per token, cutting compute proportionally while retaining the full model’s representational capacity.

    Architecturally, standard FFN layers are replaced with multiple parallel FFNs, the experts, plus a gating network, the router. The router produces a probability distribution over experts; top-k routing selects which ones process each token, and outputs are combined weighted by routing probabilities. Attention and the router remain dense; expert FFNs are sparse. Modern MoE models achieve 4—​8 times the parameter count at similar compute budgets to dense counterparts.

  2. How does the router decide which experts process each token?

    The router takes a token representation as input and produces a distribution over E experts.

    Standard softmax gating: A linear layer produces E logits, and softmax converts them to probabilities. This is simple but prone to collapsing onto a few experts.

    Top-k routing: Select the k highest-probability experts. Top-1 is most efficient; top-2 is common for redundancy. The output is a weighted sum of selected experts’ outputs.

    Noisy top-k: Add Gaussian noise to logits before routing during training, encouraging exploration and preventing premature convergence.

    Expert choice: Invert the selection so experts choose their top tokens from the batch. This guarantees perfect load balance but may leave some tokens unprocessed.

    Hash routing: Use deterministic routing based on token properties. There is no learned router, which eliminates routing computation but sacrifices adaptivity.

    The discrete expert selection itself is non-differentiable, but gradients still flow through the continuous softmax weights applied to the selected experts’ outputs. The router learns which experts to favor because changes in its parameters shift those weights and thus the weighted combination.

  3. What is expert collapse, how do you prevent it, and do experts actually specialize?

    Expert collapse occurs when the router sends most tokens to a few experts while others receive almost no traffic. Underutilized experts fail to learn, becoming dead parameters. A rich-get-richer dynamic drives this: initially better experts attract more tokens, get more training signal, improve further, and attract even more.

    Prevention relies on auxiliary losses.

    Load balancing loss: For expert i with token fraction fi and average routing probability pi, the loss is proportional to ∑ifi·pi, and it is minimized when distributions are uniform.

    Importance loss: Penalizes variance in total routing probability assigned to each expert across the batch.

    Diversity loss: Penalizes similarity between expert weight vectors, encouraging complementary rather than redundant representations.

    Capacity factors: Hard limits on tokens per expert; overflow goes to secondary experts or is dropped.

    The auxiliary loss coefficient is critical: too weak allows collapse, too strong forces poor routing. Typical values range from 0.01 to 0.1 of the main loss.

    Load balancing solves utilization but leaves open whether experts learn distinct functions. Specialization emerges, but it is usually less clean than intuition suggests. Some experts show soft preferences for token types such as punctuation or numbers, languages in multilingual models, or semantic domains, but most handle diverse tokens. Early layers tend toward less specialization because they process general features, while later layers may specialize more. Larger models with more experts can show more pronounced patterns because finer-grained routing is possible.

    Specialization is not automatic. Without proper training dynamics, experts may learn redundant functions rather than complementary ones. Load balancing ensures all experts receive signal but does not guarantee they learn different things. Some approaches encourage diversity through auxiliary losses, domain-conditioned routing, or diverse initialization. You should analyze actual routing patterns empirically rather than assuming neat divisions by interpretable categories.

  4. How does expert parallelism differ from data and tensor parallelism, and how do you handle capacity and communication?

    Expert parallelism shards experts across devices, each holding a subset. It is required because MoE models have far more total parameters than fit on one device.

    Data parallelism: same model on every device, different data. Communication is gradient all-reduce and predictable in volume.

    Tensor parallelism: a single layer is split across devices. Communication is activation synchronization at every step and is also predictable.

    Expert parallelism: experts are distributed across devices. Communication is all-to-all token exchange and is dynamic and routing-dependent. Each device sends tokens to whichever devices hold their target experts.

    Large MoE models typically combine all three. A key challenge is load imbalance: if routing favors certain experts, the devices holding them become bottlenecks while others idle.

    To bound that imbalance, capacity factors limit tokens per expert per batch. With B tokens, E experts, and top-1 routing, uniform distribution gives B/E tokens per expert. A capacity factor C allows up to C·B/E. Without limits, popular experts could receive an unbounded share of tokens, causing memory overflow and compute imbalance. When an expert hits capacity, excess tokens are handled in three main ways:

    • Drop: the token passes through the residual connection only. This is simple but loses expert processing.

    • Secondary routing: the token is sent to the next-best expert. This preserves processing, but at a suboptimal expert.

    • Shared fallback: a dense shared expert processes overflow tokens.

    Higher capacity, C=2−4, reduces drops but increases memory; lower capacity, C=1−1.5, is efficient but drops more. Training tolerates some drops averaged over large batches; inference with small batches is more sensitive, since a dropped token directly affects output quality.

    The all-to-all exchange also needs optimization. Each device determines which tokens route to remote experts, sends them, and receives tokens destined for local experts. Communication volume depends on routing; in the worst case, all tokens target remote devices. Optimization strategies include:

    • Overlap communication and computation: process tokens for local experts while transferring tokens for remote ones.

    • Hierarchical routing: route first within device groups, which use fast local links, then across groups. This reduces cross-node traffic at some cost to routing flexibility.

    • Expert placement: analyze routing patterns and co-locate frequently co-activated experts on the same device.

    • Topology-aware routing: slightly bias routing toward local experts for significant communication reduction at a small accuracy cost.

    • Batching by destination: group outgoing tokens by target device before transfer to improve bandwidth utilization.

    Communication overhead can dominate training time for large MoE models, making systems-level optimization as important as algorithmic improvements.

  5. How does MoE inference differ from training?

    Several factors make MoE inference harder.

    Batch size: Training uses large batches, often thousands of tokens, which amortize routing overhead. Inference often processes single sequences, making overhead proportionally larger.

    Load balancing: Training benefits from statistical balancing across large batches. Small inference batches can have heavily skewed routing, leaving most experts idle.

    Latency: Training tolerates per-batch variation. Inference has strict tail-latency requirements where the 99th percentile matters.

    Memory: All experts must be accessible, but only a fraction activate per token. Options include keeping everything in GPU memory, which is expensive; offloading to CPU with on-demand loading, which adds latency; or caching based on predicted routing.

    Optimization strategies include speculative expert loading, meaning predicting and preloading before routing completes; pruning rarely-used experts for deployment; differential quantization by expert importance; and request batching to form larger batches at the cost of latency.

  6. When should you choose MoE over a dense model?

    Choose MoE when:

    • you want to scale beyond dense compute limits at frontier scale,

    • your training budget exceeds your inference budget, so you can amortize extra training complexity,

    • your hardware supports efficient expert parallelism and all-to-all communication,

    • the task benefits from specialized sub-networks.

    Choose dense models when:

    • the model fits on a single device without parallelism complexity,

    • inference latency is critical with small batches,

    • fine-tuning is the primary use case, since expert specialization may not transfer well,

    • simplicity and debuggability matter more than maximum capacity.

    Mixtral, DBRX, and Grok all use MoE. Dense models remain practical for smaller scales and simpler deployment.

Thread: Knowledge Distillation

  1. What is knowledge distillation, how does it differ from quantization or pruning, and when would you choose it?

    Knowledge distillation trains a smaller student model to reproduce the behavior of a larger teacher. Unlike quantization, which reduces precision but keeps the architecture, or pruning, which removes weights or structures from an existing model, distillation trains a separate student model, which may be smaller or architecturally different from the teacher. The student can be purpose-designed for target hardware.

    The core principle is that a large teacher has learned rich data representations. Distillation transfers that knowledge to a smaller model that could not have learned it as effectively from raw data alone.

    Comparing the three compression paths clarifies when to reach for each. Quantization reduces precision, for example FP16 to INT4, but keeps the architecture unchanged. It is fast to apply, since post-training quantization runs in minutes, and effective when the original architecture fits the target hardware. Pruning removes individual weights or structures such as heads or layers. It can reduce both compute and memory, but the resulting architecture is constrained by the starting model. Distillation trains a new architecture, giving maximum flexibility: fewer layers, smaller hidden size, or a completely different design. It requires a full training run but allows optimization for specific hardware.

    Choose distillation when you need a drastically different model size, for example 70B down to 3B, when you want to design for specific hardware, or when compressing from a closed-source teacher whose weights are unavailable. The best results often combine all three: distill a small student, then quantize it for deployment.

  2. What is the difference between soft and hard distillation, and which real models use them?

    Soft distillation (Hinton et al., 2015) trains the student on the teacher’s full probability distribution, not just the top-1 prediction. Both teacher and student logits are divided by a temperature T>1 before softmax, which softens the distribution and reveals structure in low-probability tokens. A token the teacher assigns probability 0.001 versus 0.0001 represents a 10 times difference that hard labels discard. Hinton called this “dark knowledge.” The loss combines KL divergence with cross-entropy:

    ℒ=α·T2·KL(σ(zt/T)‖σ(zs/T))+(1−α)·CE(y,zs)

    where zt and zs are teacher and student logits, and the T2 factor corrects for gradient magnitude changes from temperature scaling.

    Hard distillation trains the student on the teacher’s generated outputs, via standard supervised fine-tuning. No logits are needed, only (prompt, teacher_response) pairs. This is simpler and dominant for LLMs because closed-source teachers like GPT-4 and Claude do not expose logits. The tradeoff is losing distributional information.

    Most deployed small language models use some combination of these approaches. Examples include:

    • Phi-3 (3.8B) by Microsoft: distilled using high-quality synthetic data from larger models.

    • Gemma 2 (2B) by Google: combines soft and hard distillation from Gemini.

    • LLaMA 3.2 (1B and 3B) by Meta: logit-based distillation from larger LLaMA models combined with pruning.

    A 3B distilled student quantized to INT4 fits under 2 GB and runs on a phone, while retaining much of the teacher’s capability on focused tasks. These models power on-device assistants, latency-sensitive APIs, and edge deployments.
