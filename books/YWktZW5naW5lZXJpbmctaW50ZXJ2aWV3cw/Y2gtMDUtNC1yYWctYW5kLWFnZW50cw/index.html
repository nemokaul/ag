Chapter 4. RAG and Agents

In Chapter 3, we looked at prompt engineering as one way to equip LLMs with the information they need. In this chapter, we introduce retrieval-augmented generation (RAG) and show how it evolves into agentic RAG and, ultimately, tool-using agents.

The shortcoming with prompt engineering is that in many real systems, better prompts are not enough. The model may need facts that were never in its training data, details that change frequently, or private information that cannot be included in pretraining. RAG offers a practical and cost-effective alternative; instead of forcing the model to “know” everything, the system retrieves relevant information at runtime and injects it into the model’s context before generation. Figure 4-1 shows the comparison between RAG and prompt engineering.

RAG changed how LLM applications are built. Rather than treating the model as a self-contained knowledge base, modern systems increasingly treat it as a reasoning and synthesis engine that operates over external data. We’ll build up to that perspective in three steps:

  1. First, we cover vanilla RAG (also known as classical RAG or basic RAG). In its simplest form, a RAG system retrieves a set of top-k documents relevant to each user query, augments the user query with them, and asks the model to generate an answer using the retrieved context. RAG reduces factual errors and gives answers grounded in the external corpora. Vanilla RAG however is static and pipeline-shaped: retrieval is typically a fixed stage, often with a single retriever, a fixed top-k, and a one-shot generation step. As a result, the system may still produce confident answers even when retrieval is weak, incomplete, or only loosely relevant.

  2. Next, we move to Agentic RAG, where retrieval is no longer a mandatory step. The system can decide whether to retrieve, where to retrieve from, and how to retrieve. It can rewrite the query, try alternative sources, expand or narrow scope, and iterate until the evidence is sufficient or stop early when it isn’t. This brings flexibility and self-correction.

  3. Finally, we broaden from “retrieval as the main action” to agents with tools. In tool-using systems, retrieval becomes one action among many. The model may run calculations, query databases, call internal services, or trigger workflows. This shifts control from being entirely developer-defined to being partly determined by the model’s decisions. As a result, system design concerns change: interface boundaries, routing, sandboxing, permissions, observability, and stopping criteria become first-class components, not afterthoughts.

Figure 4-2 shows the progression of above three steps.

This chapter does not claim that more autonomy is always better. Each step in the spectrum above solves certain problems but also brings new costs and risks. The main goal is to make good decisions about system architecture: when to add complexity, when to keep things simple, and how to weigh these trade-offs in real projects and interviews.

Retrieval-Augmented Generation (RAG)

Retrieval-Augmented Generation (RAG) exists because language models only know what they were trained on. They do not have direct access to private documents, internal systems, or information that was added after training. When a question depends on any of those, the model has no reliable way to answer it on its own. Sometimes it guesses well enough. Other times it sounds confident and is simply wrong. RAG addresses this by bringing in relevant external information at runtime, so the model can base its response on actual evidence instead of relying only on memory.

The main advantage of RAG is that it separates the model from the knowledge it reasons over. When facts change, you typically do not need to retrain or fine-tune the model; instead updating the underlying data source is often sufficient. For applications built on internal knowledge or rapidly changing content, this separation is what makes RAG practical to deploy and maintain over time.

RAG typically has an offline indexing phase and an online query-time phase. In the offline phase, shown in Figure 4-3, documents are split into chunks, each chunk is embedded using an embedding model, and the resulting vectors are stored in a vector database. This phase usually runs asynchronously and is refreshed as documents change.

The online phase, shown in Figure 4-4, begins when a user submits a query. The system embeds the query, using the same embedding model used in the offline phase, and retrieves the most similar chunks from the vector database. The retrieved chunks are then used to augment the prompt, which is passed to a language model to generate an answer. This language model, often referred to as the generator model, can be different from the embedding model.

The diagrams shown in Figures 4-3 and 4-4 illustrate the basic classical RAG. In practice, each stage has multiple design choices, and a small handful of them dominate answer quality, latency and cost.

  1. Chunking strategy: How documents are split into chunks matters because it largely determines what retrieval can “see.” Chunks that are too small often lose important context, while chunks that are too large blur relevance and compete for attention inside the model’s context window. Two techniques help address this trade-off: parent-document retrieval changes what unit is returned, while contextual retrieval changes what is embedded.

    • Parent-document retrieval (small-to-big) embeds small chunks for precise matching but returns a larger parent section to provide richer context. Small chunks often improve retrieval precision because they contain less irrelevant information, but the model may need surrounding context to generate a complete answer. A typical setup stores chunks at two levels: child chunks, which may be a few sentences and are used for embedding and retrieval, and parent chunks, which may be full sections or pages. When a child chunk matches, the system returns its parent instead of, or in addition to, the child. This approach is useful when the model needs more context than the retrieval unit alone provides, such as in legal documents, technical manuals, and other long-form content.

    • Contextual retrieval prepends each chunk with LLM-generated context explaining where it fits in the original document. For example, a chunk about Q3 revenue might receive the header: “This chunk is from the 2024 Annual Report, Section 3: Financial Results, discussing third-quarter revenue by region.” Without this context, a statement such as “Revenue increased 12% year-over-year” may be ambiguous: which year, which company, and which metric? The added context helps disambiguate the chunk before it is embedded and retrieved. This technique typically requires one additional LLM call per chunk at indexing time and is especially useful when short chunks lose important context once separated from their source document.

  2. Embedding model and indexing pipeline: The embedding model defines what semantic similarity means, while the indexing pipeline determines whether you can search accurately and efficiently at scale. Poor embeddings, inconsistent preprocessing, or schema mismatches can make the right passage effectively invisible.

  3. Retrieval method (dense, sparse, hybrid): Retrieval can be performed in two main ways. One approach is dense retrieval, which retrieves documents using embedding vectors and semantic similarity. Another approach is sparse retrieval, which relies on exact lexical overlap between the user query and the documents. A common example of sparse retrieval is the BM25 algorithm. Hybrid retrieval combines dense and sparse methods and often performs best in production because it balances semantic matching with precise keyword matching.

  4. Re-ranking and post-retrieval processing: Initial retrieval is usually noisy. A re-ranker and simple post-processing can dramatically improve relevance, often more than tweaking the base retriever. The re-ranker is usually a more expensive relevance model that re-ranks over a small set of retrieved candidates from the first retriever. This two-stage approach has become standard in high-quality RAG deployments. For post-processing, it is common to de-duplicate results, increase diversity, apply filtering, and incorporate freshness.

  5. Top-k and context budgeting: How many chunks we fetch and how many tokens we allocate to retrieved context is a core trade-off. Too few misses evidence, while too many dilutes signal and can confuse the generator model.

Can long context replace RAG?

With the availability of models that support very long context windows, it is natural to ask whether retrieval is still necessary. In practice, long context does not replace retrieval. Large prompts are expensive, slower to process, and models do not attend evenly across long inputs (see the “lost in the middle” phenomenon in Chapter 14). When datasets are large, queries are frequent, or information changes often, RAG is the more scalable and reliable choice.

Even with these design choices implemented well, RAG is not guaranteed to succeed on every query. RAG is only as good as the evidence it can retrieve and assemble. If the retrieved content is irrelevant, incomplete, or only loosely related to the query, RAG will fail. Many of the hallucinations seen in production RAG systems trace back to retrieval failures.

If an interviewer tells you that a RAG system is hallucinating, do not immediately suggest changing the LLM or the prompt. First inspect the retrieved chunks. If the evidence is wrong or insufficient, debug chunking, embeddings, filters, or retrieval. If the evidence is correct but the answer is not grounded in it, then investigate prompting or generation. Separating retrieval failures from generation failures gives you a much stronger debugging answer.

Classical RAG has clear limits. It has a rigid execution model: retrieval is always invoked for every query, queries are formed in a fixed way, and the system proceeds to generation regardless of whether the retrieved evidence is relevant or sufficient. When retrieval fails, the system proceeds to generation anyway. This rigidity is why more adaptive RAG architectures are needed. The next set of RAG patterns can be understood as progressively adding decisions, branches, and feedback loops to the basic retrieve-then-generate pipeline.

Adaptive RAG Patterns

The limitations of basic RAG do not mean that every system should immediately become a full agent. Many production systems instead improve RAG incrementally, by adding specific control points around retrieval. Figure 4-5 summarizes four common patterns. The simplest is linear RAG, where every query follows the same retrieve-then-generate path. A more selective version is conditional RAG, where the system first decides whether retrieval is needed at all. In branching RAG, retrieval is split across multiple sources or retrievers, and the results are merged before generation. Finally, looping RAG checks whether the retrieved context is sufficient and, if not, reformulates the query and tries again.

Looping RAG is the closest of these patterns to agentic RAG as it introduces a feedback loop: the system can inspect the retrieved context, decide that it is insufficient, and try again with a revised query. However, the loop is still usually part of a predefined retrieval workflow. Agentic RAG generalizes this idea by giving the model more control over the retrieval process itself.

Agentic RAG

Basic RAG, even when extended with conditional, branching, or looping patterns, can still break at scale. These architectures add useful control points, but they are still predefined pipelines: the system designer decides the possible paths in advance, and the model follows those paths at runtime. As applications grow more complex, users ask under-specified questions, combine multiple intents, or rely on domain-specific language that does not align cleanly with indexed text. In these cases, the system may need to reason more actively about what the user is asking, which sources to query, whether to decompose the question, and whether more information is needed before answering.

Agentic RAG sits between adaptive RAG and full agents. It keeps retrieval as the central mechanism, but gives the model more control over retrieval decisions: when to retrieve, what to retrieve, which source to use, whether the evidence is sufficient, and whether to iterate. In broader systems, this same pattern can expand into full tool use, where retrieval becomes one tool among many.

Once retrieval is optional, self-correction becomes possible. An agentic system can inspect retrieved results and ask whether they meaningfully address the question. If results are sparse or off-topic, the system can reformulate the query, switch data sources, or decompose the original question into simpler sub-questions. If retrieval repeatedly fails, the system can abstain, ask for clarification, or deliberately fall back to parametric knowledge.

Figure 4-6 highlights this difference between looping RAG and agentic RAG.

At the core of Agentic RAG, there are four tightly coupled decisions that matter:

  1. Whether to retrieve: Whether retrieval is needed depends on the query itself. For example, conceptual questions differ from those requiring private or up-to-date data. Treating all queries the same increases cost and reduces accuracy.

  2. Where to retrieve from: Retrieval rarely targets a single index. Enterprise deployments span vector stores, document repositories, structured databases, and external APIs. Agentic RAG does not query everything indiscriminately, but enables source routing based on the intent of the query.

  3. How to retrieve: Agentic systems perform retrieval iteratively. They can reformulate the query, add missing context, expand or narrow keywords, and run multiple focused searches. Each search can use a mix of dense, sparse, and filtered retrieval. Each retry is driven by a diagnosis of what went wrong in the previous attempt. For example, the query was too vague, used the wrong terms, or retrieved results from the wrong part of the corpus.

  4. When to stop: Agentic RAG must decide whether the retrieved evidence is sufficient to answer. If the evidence is incomplete, conflicting, or off-topic, the system may retrieve again. If the evidence is strong enough, it should stop searching and generate the answer. This stopping decision is what separates useful iteration from endless retrieval.

Agentic behavior introduces its own risks. Poorly designed systems may enter infinite reformulation loops, retrieve excessive context in pursuit of completeness, or over-rely on retrieval even when parametric knowledge would suffice. Effective Agentic RAG therefore imposes explicit limits on retries, context size, and execution depth to balance adaptability with predictability.

Agentic RAG extends retrieval with reasoning, but it remains retrieval-centric. Many real systems need to do more than look things up. They must run computations, query structured stores, call internal services, and sometimes change external state. At that point, retrieval becomes just one tool among many.

Agents and Tool Use

Tools turn language models from text generators into systems that can act. Agents with tools make decisions at run time and execute. A helpful way to understand agents is to contrast them with workflows.

A workflow is a predefined control flow authored by a developer: retrieve → summarize → send → update. Workflows can be reliable and production-ready, but they are only as flexible as the branches explicitly encoded in them. If something unexpected happens, the workflow can only follow the recovery paths the developer wrote in advance.

An agent, by contrast, makes decisions at runtime. It chooses which tools to call, in what order, with what inputs, and when to stop. It can also retry with a different approach when intermediate steps fail. The benefit of an agent is flexibility on messy, real-world tasks. The cost is reduced predictability, because the agent’s behavior is much harder to fully enumerate at design time. Figure 4-7 shows the contrast between workflows and agents.

In practice, most real systems sit in the middle, workflow scaffolding with agentic steps inside.

In an interview, do not call every LLM application that uses tools an agent. The key distinction is who controls the execution flow. In a workflow, the developer defines the sequence of steps and possible branches. In an agent, the model decides at runtime which actions to take, which tools to call, and when to stop. Making this distinction clearly shows that you understand agent architecture rather than just agent terminology.

Structured Workflow Patterns

Before introducing the full agent loop, it is useful to recognize that many production systems do not need open-ended agency. They need structured workflows with limited model-driven decisions. Figure 4-8 shows five common workflow patterns. These cover a large fraction of practical LLM system designs, and often solve the problem with better predictability than a fully autonomous agent.

Prompt chaining which we discussed in Chapter 3 breaks a task into a fixed sequence of steps, where the output of one step becomes the input to the next. It is useful when the task naturally decomposes into stages and you want more control than a single prompt provides.

Routing first classifies the request and then sends it to the most appropriate handler, prompt, model, or subsystem. This pattern is common when different query types require different logic, tools, or cost profiles.

Parallelization splits a task into independent subtasks that can be executed concurrently and then aggregated. It is useful when latency matters or when multiple perspectives, checks, or partial results can be combined.

Orchestrator-workers uses a central controller to dynamically decompose a task, assign work to specialized workers, and synthesize the results. This pattern is more flexible than simple parallelization because the decomposition itself can depend on the input.

Evaluator-optimizer introduces a feedback loop in which one step generates a result and another step evaluates it, triggering refinement when necessary. This is useful when quality improves through critique and revision rather than through a single pass.

These patterns add controlled forms of intelligence while keeping the overall execution structure predictable. Some workflow patterns, especially orchestrator-workers and evaluator-optimizer, begin to look agentic. The difference is that in a workflow, the structure of the pattern is still designed in advance, even if some decisions happen at runtime. A full agent loop becomes necessary only when the system must decide actions, tool usage, and recovery paths more openly at runtime.

In a system-design interview, don’t jump straight to agents. Start with the simplest architecture that can solve the problem, then add complexity only when you can justify it. For example, start with a fixed workflow or basic RAG pipeline, then introduce routing, iterative retrieval, or an agent only when the requirements demand more dynamic decision-making. Interviewers are often looking for whether you understand the trade-off between flexibility and predictability, not whether you can design the most sophisticated agent.

Agent Loop

Tool-using agents typically run a repeated control cycle, shown in Figure 4-9: perception, reasoning, and action. In the perception phase, the agent observes the current state of the task, including the user request, tool outputs, retrieved passages, system constraints, and results from the environment. In the reasoning phase, the agent interprets these signals, recalls relevant context from memory, updates its plan, and decides what to do next. In the action phase, the agent invokes a tool; for example, it may retrieve documents, query a database, call an API, run code, or ask the user for a missing detail. The action affects the environment, and the resulting observation is fed back into the next perception step.

Memory supports this loop. The agent may store useful observations, intermediate results, or decisions after perceiving new information, and it may recall relevant past context while reasoning about the next step. Eventually, when a stopping condition is met, the agent stops. The stopping condition may be that success criteria have been met, a safety constraint has been triggered, or a budget such as time, tool calls, or tokens has been reached.

This simple loop turns a one-shot model call into a system that can pursue goals over multiple steps. The quality of an agent is not determined only by the model or the reasoning loop, but also by how tools are defined, exposed, selected, and executed.

Tools

A tool is a specific callable action with four components:

  1. a name, such as search, sql_query, or fetch_url,

  2. a description that explains what the tool does and when to use it,

  3. an input schema with required inputs, types, and constraints,

  4. a return contract that defines what the tool returns and how errors are represented.

Tool descriptions are particularly important because the model uses them to decide which tool to use and when to use it. A good description clearly states the tool’s purpose, when it should be used instead of alternatives, and any important constraints or side effects. Ambiguous or overlapping descriptions can cause the model to select the wrong tool, avoid a useful tool, or construct an inappropriate call.

For example, GitHub is a service that exposes multiple tools such as github.search_issues, github.create_pr, and github.list_repos.

Tools can also be categorized based on whether they change external state. Read tools, such as github.search_issues, retrieve information without modifying the underlying system. Write tools, such as github.create_pr, change state in an external system. In practice, agent systems often allow read tools more freely and gate write tools behind additional policy checks.

Tools are important because they address the biggest limitations of LLM-only systems:

    

  1. 

    First, tools provide freshness and access. Models do not automatically know your private documents, latest policies, or real-time data. Retrieval and APIs provide ground truth.


  2. 

    Second, tools provide higher precision on structured problems. For questions like “Which customers churned last month?”, a database query beats a model guess every time.


  3. 

    Third, tools enable LLMs to work on long-horizon tasks, i.e. tasks that require multiple steps such as gathering information, validation, computation, formatting, and delivering results. Tools allow the agent to make progress on these tasks step by step.




Historically, each LLM provider used its own convention to describe and invoke tools. This created an N×M integration problem where each LLM provider needed custom glue code to talk to each tool. As a result, tool integrations became expensive to build and maintain. The Model Context Protocol (MCP) addressed this issue by standardizing how agents discover and call tools.




Model Context Protocol (MCP)


MCP was introduced by Anthropic in late 2024 and gained broader ecosystem adoption in 2025. MCP is like a universal adapter. If your tool exposes an MCP interface, and your agent can speak MCP, they can connect seamlessly without a custom, vendor-specific integration. Figure 4-10 illustrates the utility of MCP.



MCP has three main components:

    

  1. 

    The Host: This is the main app the user interacts with, commonly referred to as the AI agent.


  2. 

    The Client: This is a protocol adapter that runs inside the host. It manages the connection to an MCP server, sends the host’s requests to the server, receives the server’s responses, and returns them to the host. In other words, the client is the host’s MCP-speaking endpoint for a particular server connection.


  3. 

    The Server: This is the tool provider that implements the MCP protocol and exposes one or more tools backed by external systems such as GitHub or Jira. The server advertises tool definitions, including names and input schemas, and executes tool calls when requested.




Figure 4-11 shows this relationship. An MCP host can run multiple MCP clients. Each MCP client is connected to an MCP server. Each MCP server typically exposes tools backed by one service, such as GitHub or Jira, and each service offers multiple tools.



In terms of communication flow, the host is where requests originate, and the server typically responds to those requests rather than initiating them on its own. Under the hood, MCP uses JSON-RPC to carry messages between clients and servers. In practice, most developers rarely interact with these protocol details directly because SDKs and integrations handle them.





Do not confuse MCP with function calling in an interview. Function calling is a model-level mechanism for expressing which function to invoke and with what arguments. MCP operates at the integration layer, standardizing how tools are exposed, discovered, connected to, and invoked. The two are complementary, not competing approaches.





Core Design Choices


Now that MCP standardizes interfaces, the next thing to do is design the agent loop reliably. Figure 4-12 illustrates this loop.



    

  1. 

    Tool selection: The agent needs a reliable way to choose the right tool, or decide not to use one. In practice, this is often a lightweight router prompt or classifier that answers questions such as “Should we retrieve at all?”, “Which index, database, or API should we use?”, and “Do we need one tool or multiple tools?”


  2. 

    Tool input construction: The agent needs to build valid, high-quality tool inputs such as queries, filters, IDs, and parameters. Strong agentic systems reformulate inputs, add constraints, and validate arguments before calling a tool.


  3. 

    Iteration and recovery: The agent needs to recover from failures and retry intelligently. Each retry should be guided by a simple diagnosis of what failed before, not blind repetition. For example, if retrieval quality is weak, the next attempt might rewrite the query, adjust filters, increase recall, or rerank results. If an API call fails, the agent may need to back off, fix parameters, or switch endpoints.


  4. 

    Stop conditions: The agent needs explicit stop conditions to avoid looping indefinitely. Use layered controls such as limits on iterations, tool calls, time, and tokens, along with progress checks. Define clear success criteria, such as gathering the required facts, completing the requested actions, or passing verification. If the agent repeatedly takes the same actions without making progress, detect the cycle and stop. When a task cannot be completed within these limits, terminate gracefully rather than continuing indefinitely.


  5. 

    Trust boundaries and sandboxing: The system needs clear trust boundaries between model decisions and tool execution. Trust boundaries are the line between what the model is allowed to decide and what the system is allowed to actually execute. The model proposes actions, but the execution environment enforces permissions, sandboxing, and safety limits.




These choices make the agent loop reliable at the system-design level. In production, however, a second layer of constraints shapes what can actually be deployed.






Production Reality Check


In practice, production systems are deliberately constrained because real environments impose hard constraints. Latency budgets are finite. Costs compound. Failures must be diagnosable. Actions must be reversible, gated, or prevented. In this section, we use a ``pressure → design`` response pattern to describe the design response required to handle each pressure.

1) Non-determinism → Observability:

Observability is a non-negotiable part of production agentic systems. In agentic systems, observability means capturing the full execution trace: prompts and model outputs, tool selections, tool inputs and results, retries, errors, and state transitions across steps. Without this visibility, debugging becomes guesswork. It becomes difficult to answer basic questions such as “Why did the agent choose this tool?” and “What evidence did it retrieve?”

2) Cost and latency → Routing and hybrid systems:

Agentic systems are expensive and slow by default. Each reasoning step consumes tokens. Each retrieval adds latency. Each tool call introduces overhead and new failure modes. A naive design that routes every request through a full agent loop is therefore economically infeasible.

This is why routing is central to production design. Most production systems distinguish between simple requests that can be handled by static pipelines, moderately complex requests that benefit from agentic retrieval, and truly complex tasks that justify full tool-using agents. Smaller models handle classification, extraction, and routing, while frontier models are reserved for cases where deeper reasoning actually matters. This is why fully autonomous agents are rare in production. Hybrid systems that combine workflows, RAG pipelines, and bounded agents are the norm.

3) Action risk → Safety boundaries and bounded autonomy:

As soon as agents can act through tools, safety becomes a systems problem rather than a model problem. The issue is not whether the model is intelligent, but whether the system can contain mistakes.

Effective production systems make trust boundaries explicit. Models propose actions; execution environments enforce what is allowed. Read-only access is treated differently from write access. High-impact actions require stricter validation, confirmation, or escalation. Tool execution is sandboxed so that even incorrect decisions have a limited blast radius.

This framing leads naturally to bounded autonomy. Agents are allowed to act freely within defined limits and must escalate beyond them. These limits are not static; they evolve based on observed behavior and risk tolerance. The goal is to ensure errors are detectable, auditable, and recoverable.





Evaluation


Retrieval-augmented generation (RAG) and agentic systems are the two most common production architectures. Evaluating them requires going beyond single-turn generation quality. Chapter 5 covers these systems in detail; here we focus on evaluation methodology.



RAG Evaluation Triad


A RAG system has two components that can fail independently: the retriever and the generator. A useful evaluation framework therefore separates retrieval quality from generation quality and examines three dimensions:

Context relevance: Are the retrieved documents relevant to the query? This is measured by recall@k (the fraction of relevant documents found in the top k results), MRR (Mean Reciprocal Rank, the average of 1/rank of the first relevant result), and NDCG (Normalized Discounted Cumulative Gain, which weights relevant results higher when they appear earlier in the ranked list).

Faithfulness: Is the generated answer supported by the retrieved context? This is the RAG-specific version of hallucination detection, evaluated via NLI models or LLM-as-judge faithfulness scoring.

Answer relevance: Does the response actually address the question? This is typically scored by an LLM judge.

Frameworks such as RAGAS (Retrieval-Augmented Generation Assessment; Es et al., 2024) automate many of these checks by scoring retrieval quality, grounding, and answer quality using a combination of LLM-based and similarity-based metrics.





Agent Evaluation


Agents introduce challenges that static benchmarks were never designed for. Instead of evaluating only the final answer, agent evaluation must consider whether the agent completed the task, how it got there, and whether its behavior is reliable across repeated runs.

Task completion is the most direct metric: did the agent accomplish the goal? For coding agents on SWE-bench, this means the patch passes the test suite. For web navigation agents on WebArena (Zhou et al., 2024), it means the task was completed correctly. Binary success or failure is simple but coarse.

Trajectory quality assesses the agent’s path: step count, token cost, whether it selected appropriate tools, and whether intermediate reasoning was sound. Two agents may both succeed, but one in 3 steps and the other in 30.

Run-to-run robustness captures the challenge of non-determinism. Agents have stochastic trajectories; the same agent may succeed on one run and fail on the next. Robust evaluation requires multiple runs per task and reporting success rates with confidence intervals. Single-run pass or fail is unreliable.







Summary


In this chapter, we introduced the progression from retrieval-augmented generation (RAG) to agentic systems that can reason, retrieve, and act through tools. We first established why grounding improves factuality, then extended the design space from static retrieval pipelines to agentic retrieval and tool use. We introduced tools as callable interfaces with schemas and contracts, and showed how MCP standardizes tool connectivity across hosts, clients, and servers. We then discussed the core design choices for building reliable agent loops and closed with a production reality check. Together, these ideas form the foundation for designing agent systems that are capable, reliable, safe, and practical in production.





Interview Questions and Answers




Thread: RAG Fundamentals


    

  1. 

    What problem does RAG solve?

    RAG reduces hallucination and works around knowledge cutoffs by retrieving external evidence at runtime and conditioning generation on that evidence instead of relying on the model’s parametric memory.


  2. 

    When do you prefer RAG over fine-tuning?

    Prefer RAG when the required knowledge is large, dynamic, private, or needs citations and verifiability. Prefer fine-tuning when you need to change model behavior, such as tone, format, or decision policy, or when the knowledge is stable and retrieval latency is unacceptable. In many systems, fine-tuning shapes behavior while RAG supplies facts.


  3. 

    Walk me through the RAG pipeline end-to-end. Where do failures typically occur?

    A standard pipeline is as follows: ingest documents, chunk them, compute embeddings, store vectors offline; then embed the query, retrieve top-k chunks, build a context window, and generate an answer online. Many production failures happen in retrieval, before generation; for example in poor chunking, weak embeddings, wrong filters, missing metadata, or retrieval returning irrelevant context that the model then treats as authoritative.


  4. 

    What are common chunking strategies in RAG?

    Common chunking strategies include:

      

    • 

      Fixed-size chunking (often with overlap) splits text into uniform chunks, for example by tokens or characters. It is simple and efficient, but it may cut across sentence or section boundaries. Adding overlap between adjacent chunks helps preserve boundary context, at the cost of more storage and redundancy.


    • 

      Semantic chunking splits text at meaning-based boundaries, often where topic similarity changes. It preserves coherence better, but chunk sizes become less predictable.


    • 

      Hierarchical chunking stores chunks at multiple levels, for example document → section → paragraph. It supports precise retrieval with optional context expansion.


    • 

      Document-aware chunking uses document structure such as headers, lists, tables, and sections. It works especially well for structured content because it preserves the author’s organization.


    • 

      Late chunking encodes the full document first, then derives chunk representations. It preserves cross-chunk context better than embedding each chunk independently, but is more expensive.


    

    Most teams start with fixed-size + overlap as a baseline, then upgrade if retrieval quality falls short. Document-aware chunking works best for structured docs such as API docs, manuals, and policies. Hierarchical chunking is useful when queries need both a precise answer and surrounding context. Semantic chunking helps when topic coherence matters more than fixed chunk size.


  5. 

    What are the practical limitations of embedding-based retrieval, and why is BM25 still relevant?

    Embeddings are approximate and optimize semantic similarity, not exact identity. They often miss identifiers, error codes, file paths, and domain-specific tokens. They can also struggle with domain mismatch and ambiguous terms. Put simply, embeddings retrieve “related,” not necessarily “correct.”

    This is exactly where BM25 (Best Matching 25) earns its place. BM25 handles exact lexical matching, which dense embeddings are fundamentally weak at. For IDs, error codes, product names, and configuration keys, lexical retrieval is often the difference between finding the right doc and retrieving a vaguely related one. Most strong systems use hybrid retrieval because semantic similarity and exact matching solve different problems.


  6. 

    Explain hybrid retrieval and re-ranking. Why are they commonly used in enterprise RAG, and when is re-ranking worth the added cost?

    Production systems often use a two-stage retrieval pipeline. In Stage 1, hybrid retrieval combines semantic retrieval, which is embedding-based search, with lexical retrieval, which is keyword or BM25 search. Semantic retrieval captures meaning, for example matching automobile to car, but may miss exact identifiers. Lexical retrieval is strong on exact strings, codes, and names, but can miss semantically related results. Systems often combine these signals using a fusion method such as reciprocal rank fusion (RRF), which scores each document by summing 1/(k+rank) across the retrievers’ ranked lists so results ranked highly by multiple retrievers rise to the top.

    In Stage 2, re-ranking applies a more accurate but slower model, often a cross-encoder, to the retrieved candidates, rescoring them more precisely and selecting the final top results. The pattern is to retrieve many candidates cheaply, then rescore a smaller subset with the more expensive cross-encoder. This two-stage design balances recall in Stage 1 and precision in Stage 2, which is why hybrid retrieval is a default pattern in production.

    Re-ranking is worth the extra cost when retrieval mistakes are costly, the corpus is large or noisy, or queries are subtle. It improves precision without requiring a slow, high-precision model to run across the entire corpus.


  7. 

    What chunk-context techniques improve retrieval, and when do you use them?

    Two techniques address the same underlying problem, that a good retrieval unit and a good generation unit are often not the same size, but they attack it from different angles: parent-document retrieval changes what unit is returned, while contextual retrieval changes what is embedded.

    Parent-document retrieval (small-to-big) embeds small chunks for precise matching but returns the larger parent section for context richness. The idea is that small chunks give better retrieval precision because there is less noise per chunk, but the model often needs surrounding context to generate a good answer. A typical setup stores chunks at two levels: child chunks, which may be a few sentences and are used for embedding and retrieval, linked to parent chunks, which may be full sections or pages and are returned to the model. When a child chunk matches, the system retrieves the parent instead of or in addition to the child. Use it when answers require more context than the retrieval unit provides. It is especially effective for legal documents, technical manuals, and long-form content where a single paragraph rarely contains everything needed.

    Contextual retrieval prepends each chunk with LLM-generated context explaining where it fits in the original document. For example, a chunk about Q3 revenue might get the header: “This chunk is from the 2024 Annual Report, Section 3: Financial Results, discussing third-quarter revenue by region.” Without this context, a chunk like “Revenue increased 12% year-over-year” is ambiguous: which year, which company, which metric? The added header disambiguates the chunk for the embedding model and for the retriever. The technique is simple to implement, requiring one LLM call per chunk at indexing time, and often improves retrieval precision substantially, especially for corpora where chunks are short and lose context when separated from their source document.


  8. 

    How do you handle conflicting information across retrieved documents?

    When retrieved chunks contradict each other, the system needs a strategy beyond naive concatenation. Options include:

      

    • 

      Recency weighting: prefer newer documents when timestamps are available.


    • 

      Source authority: rank official documentation above informal sources.


    • 

      Conflict detection: use NLI or an LLM check to identify contradictions before generation.


    • 

      Transparent synthesis: instruct the model to acknowledge the conflict and present both perspectives with citations.


    • 

      Escalation: flag conflicting evidence for human review rather than generating a potentially wrong answer.


    

    The worst outcome is generating a confident answer that silently picks one side of a contradiction. A good system either resolves the conflict with clear reasoning or surfaces it to the user.








Thread: RAG Evaluation and Debugging


    

  1. 

    How do you evaluate a RAG system beyond “does the answer look good”?

    For retrieval-based systems, the RAG Triad evaluates quality across three separate dimensions:

      

    • 

      Context relevance: Did retrieval return relevant evidence?


    • 

      Groundedness (faithfulness): Is the answer supported by the retrieved context?


    • 

      Answer relevance: Does the response actually address the user’s question?


    

    These three metrics diagnose different failure modes. Low groundedness with high answer relevance often indicates hallucination, while low context relevance points to retrieval failure. Beyond the triad, track latency, cost per query, and failure slices. Aggregate accuracy hides systematic failures.


  2. 

    How do you handle document updates in a production RAG system?

    Source documents change, get deleted, or become outdated. A production system needs a strategy for keeping the index current:

      

    • 

      Incremental re-indexing: re-embed only changed or new documents rather than the entire corpus. This requires tracking document versions or modification timestamps.


    • 

      Stale chunk detection: when a source document is updated, all chunks derived from it must be invalidated and re-embedded. If the document is deleted, its chunks must be removed from the index.


    • 

      Versioning: some systems maintain multiple versions of chunks, with timestamps, so retrieval can prefer newer content or surface version conflicts.


    • 

      Freshness signals: pass document timestamps to the model so it can weigh recent sources more heavily, or flag potentially outdated information.


    

    The central design decision is the balance between index freshness and re-indexing cost. High-churn corpora such as support tickets or news need near-real-time updates. Stable corpora such as policies or manuals can use batch re-indexing on a schedule. Failing to handle staleness leads to answers grounded in outdated information, which is a subtle and hard-to-detect failure mode.








Thread: From Static RAG to Agentic RAG


    

  1. 

    What is the key difference between static RAG and Agentic RAG?

    Static RAG is a fixed pipeline: retrieve, then generate. It runs the same way for every query, even when retrieval is unnecessary or low quality. It becomes brittle in real systems because user intent is messy: queries can be underspecified, ambiguous, multi-part, or use vocabulary that does not match indexed text. A static pipeline cannot recognize that retrieval failed or that the wrong source was queried; it just generates anyway.

    Agentic RAG treats retrieval as a tool the agent can reason about, which lets it adapt and self-correct: it can inspect retrieval results, detect failures, and recover, for example by rewriting the query or switching sources. Three decisions define “agency” in retrieval:

      

    • 

      Whether to retrieve, since some questions do not need it.


    • 

      Where to retrieve from, meaning source routing across indexes and data types.


    • 

      How to retrieve, including query rewriting, decomposition, and retry loops, and whether to retry if results are weak.


    

    Traditional RAG is simpler and faster, but Agentic RAG is more reliable when queries are diverse, sources are multiple, or retrieval quality is critical.


  2. 

    What are Self-RAG and Corrective RAG (CRAG), and how do they self-correct retrieval?

    Both improve reliability by evaluating retrieval quality, but they differ in where the correction lives: Self-RAG makes the judgment internally, inside the model, while CRAG uses an external evaluator.

    Self-RAG (Asai et al., 2023) trains special reflection tokens directly into the model so it can decide, at generation time, whether to retrieve, whether retrieved passages are relevant, and whether its own output is supported by the evidence. The model learns to critique itself as part of generation rather than relying on external orchestration. It emits tokens like [Retrieve], [Relevant], and [Supported] during generation, which control the pipeline. The advantage is tighter integration and fewer external components. The disadvantage is that it requires training; you cannot retrofit Self-RAG onto an existing model with prompting alone, and the reflection tokens must be calibrated carefully to avoid over-retrieval or false confidence.

    CRAG (Yan et al., 2024) adds a lightweight external retrieval evaluator that scores each retrieved document’s quality before generation. Based on the confidence score, it takes one of three actions:

      

    • 

      Correct (high confidence): retrieved documents are relevant. Proceed to generation, but first strip irrelevant sentences within the documents to reduce noise.


    • 

      Incorrect (low confidence): retrieved documents are off-topic. Trigger a fallback strategy, typically web search, to find better evidence before generating.


    • 

      Ambiguous (medium confidence): combine both the original retrieval and the web search fallback, then generate from the merged evidence.


    

    What makes CRAG effective is a simple observation: retrieval quality varies per query, and a system that detects bad retrieval and corrects before generation is more reliable than one that always trusts its retriever. CRAG is simpler to implement than Self-RAG because it uses an external evaluator rather than requiring model retraining.


  3. 

    What is query reformulation, and where does HyDE fit in?

    Query reformulation generates alternative queries when the first retrieval attempt is weak. It matters because the user’s phrasing often differs from how documents are written. Reformulation can add missing keywords, expand acronyms, split multi-intent queries, or target specific fields.

    HyDE (Hypothetical Document Embeddings) (Gao et al., 2022) is a named sub-technique of query reformulation, but it works differently from keyword-style rewriting. Instead of embedding the user’s query directly, the system asks the LLM to generate a hypothetical answer, then embeds that hypothetical answer and uses it for retrieval. The reason it works is that user queries and documents often live in different parts of the embedding space. A query like “how do I fix error 503?” is phrased as a question, but the relevant document is phrased as an explanation. HyDE bridges this gap by generating text that looks like the target document, making the embedding closer to what needs to be retrieved.

    It helps most when queries are short, vague, or phrased differently from how documents are written. It adds latency because it introduces one extra LLM call before retrieval, and it can hurt if the hypothetical answer is wrong and pulls retrieval in the wrong direction. For well-formed queries in domains with consistent terminology, direct embedding often works just as well.


  4. 

    What new failure modes does Agentic RAG introduce, and how do you know when to stop retrieving?

    Agentic RAG introduces its own failure modes: loops, such as retrying forever; over-retrieval, such as stuffing context until quality degrades; wasted cost and latency; and over-reliance on retrieval when parametric knowledge is enough. Agentic systems need budgets, retry limits, and stopping criteria.

    The stopping decision needs a sufficiency check that evaluates whether retrieved evidence is relevant and adequate to support an answer. Practically, it might check similarity scores, coverage of key entities, contradictions across sources, or whether the agent can extract the needed facts. If evidence is insufficient, the system should reformulate, route to another source, or ask a clarifying question. Sufficiency and stopping are the flip side of over-retrieval and looping: a good check is what tells the agent it can stop searching and generate.


  5. 

    When is GraphRAG justified, and when is it overkill?

    GraphRAG (Edge et al., 2024) augments retrieval with a graph structure, where entities are nodes and relationships are edges, so the system can answer multi-hop questions that require connecting facts across documents.

    It is useful when the answer depends on relationships, not just semantic similarity. For example, a query may require linking people, companies, acquisitions, and timelines across multiple sources. In these cases, vector retrieval may retrieve relevant documents but still miss the connection path needed to answer the question.

    It is overkill when most queries can be answered by retrieving a few documents. The trade-off is complexity: GraphRAG requires entity extraction, relationship extraction, entity resolution, graph storage, and graph-aware retrieval logic. Start with vector RAG, and add GraphRAG only when you repeatedly see multi-hop, entity-relationship queries that vector retrieval cannot handle reliably.








Thread: Agents, Tools, and the Agent Loop


    

  1. 

    Compare CoT, ReAct, and plan-then-execute vs interleaved planning. When do you use each?

    Chain-of-Thought (CoT) and ReAct are related but serve different roles in agentic systems.

    CoT is a reasoning pattern in which the model works through intermediate steps before producing a final answer, all within a single generation. The model reasons internally, then responds.

    ReAct (Reason + Act) extends this idea by interleaving reasoning with external actions. The model reasons about what it needs, takes an action such as retrieval or a tool call, observes the result, and then reasons again. This loop continues until the task is complete.

    CoT is a good fit for tasks that can be solved through reasoning alone, such as math, logic, or questions answerable from the model’s existing knowledge. ReAct is more appropriate when the task depends on external information, changing state, or tool use. CoT is often used for reasoning within a step, while ReAct is used for multi-step execution with feedback from the environment. A key trade-off is cost and latency, since CoT is usually a single-call pattern while ReAct may require multiple model calls, tool calls, and retries.

    Zooming out from a single step to the whole task, there are two planning strategies:

    Plan-then-execute: the agent decomposes the entire task into steps up front, then executes them sequentially. This is easier to understand and debug because you can inspect the plan before execution starts. The weakness is brittleness: if an early step fails or returns unexpected results, the rest of the plan may be invalid.

    Interleaved planning and execution: the agent plans one step, executes it, observes the result, and then decides the next step. ReAct is the canonical example. This is more adaptive because each step incorporates new information. The weakness is that behavior is harder to predict and evaluate, and the agent may take more steps than necessary.

    Most production systems use a hybrid: plan a rough outline, then execute each sub-step with local adaptation, replanning from the current state if a step fails. Highly structured tasks benefit from upfront planning, while exploratory tasks benefit from interleaving.


  2. 

    Why do agent systems need standardized tool interfaces?

    Without standard interfaces, every tool is a custom integration with unique parameters, authentication, and error handling. That does not scale. Standard schemas enable tool discovery, composability, uniform security policy enforcement, and consistent observability. The architectural value is the decoupling between reasoning and tool implementation: you describe a tool once rather than duplicating integration logic across every agent that uses it. MCP is one implementation of this pattern.


  3. 

    How should agents decide between retrieval, tools, or parametric knowledge?

    Agents should choose the source based on what the task requires.

    Parametric knowledge is best for stable, general facts that the model likely already knows, such as basic definitions or common concepts.

    Retrieval is best when the answer depends on specific, recent, or private information, including company documents, customer data, or domain knowledge not in the model’s training data. To gate retrieval, many systems implement an explicit “retrieval-needed” classifier or a lightweight reasoning step that decides whether retrieval is warranted before paying for it.

    Tools are needed when the task requires an action or an exact operation, such as querying a database, running a calculation, sending a message, or calling an API. The reason computation belongs in tools is that LLMs predict what answers look like rather than computing them, so on complex calculations they tend to produce plausible-looking wrong results. Reasoning models narrow this gap by working through intermediate steps and checking their own arithmetic, but even they remain probabilistic and offer no guarantee of an exact result.

    Some tasks need a combination. For example, a query may require retrieval for facts, tools for computation, and parametric knowledge for explanation. Systems make this decision either with an explicit router, such as a classifier or prompt, or through agent reasoning during the loop.








Thread: Agent Architecture and Orchestration


    

  1. 

    Describe memory tiers, what each is for.

    Agent memory is best organized by time horizon and function:

      

    • 

      Ephemeral memory (prompt context): the immediate context available within a single model call, including the current prompt, retrieved evidence, and tool results. It exists only for that generation.


    • 

      Working memory: task-local state that persists across multiple model and tool steps within the same task. It tracks goals, completed steps, intermediate results, and retry history. It is usually cleared when the task finishes.


    • 

      Short-term memory: session-level conversational history across turns. It helps maintain continuity in a chat or workflow, but often requires truncation, summarization, or selective retrieval because of context-window limits.


    • 

      Long-term memory: persistent memory across sessions. It stores information the agent may need later, such as user preferences, stable facts, or prior outcomes. It is typically retrieved rather than appended directly to every prompt. Two common forms are:
_* _Semantic memory:* stable facts, preferences, and structured knowledge, for example user preferences or system conventions.
_* _Episodic memory:* specific past events with context and timestamps, for example a prior billing issue and how it was resolved.


    

    The main design challenge is deciding what to store, where to store it, and how to retrieve it. Too much memory adds noise and cost; too little breaks continuity and task performance.


  2. 

    When should you adopt multi-agent architectures?

    In most cases, start with a single-agent design. Single-agent systems are simpler to build, easier to debug, and easier to evaluate. Multi-agent designs are most useful in a few cases:

      

    • 

      Context management: the task involves too much information for one agent to handle effectively, so work is split across agents with narrower contexts.


    • 

      Specialization: different subtasks require different capabilities, and specialized agents perform better than one general agent.


    • 

      Parallelization: independent subtasks can run concurrently to reduce end-to-end latency.


    • 

      Quality improvement: multiple agents can critique, verify, or debate outputs to improve reliability on high-stakes tasks.


    

    A good design heuristic is: start with one agent, add more only when you can point to a specific bottleneck that multi-agent coordination can solve.


  3. 

    What coordination patterns exist in multi-agent design?

    When you do go multi-agent, systems are usually organized using a small number of coordination patterns:

      

    • 

      Manager-Worker: a central manager agent decomposes the task, delegates subtasks to specialized workers, and synthesizes the final result. This is easy to reason about and debug because control flow is explicit. However, the manager can become a bottleneck, and the system depends heavily on the manager’s quality.


    • 

      Peer-to-Peer: agents communicate directly and coordinate without a single central controller. This is more flexible and can work well when tasks are naturally distributed across specialists. The downside is higher coordination complexity: agents may duplicate work, miss important context, or require more effort to resolve conflicts.


    • 

      Debate (or Critique): multiple agents generate competing solutions or perspectives and critique one another before a final answer is selected. This can improve robustness and surface errors that a single agent might miss. However, it is usually slower and more expensive, and it may not converge without a clear stopping rule.


    

    Hybrid designs are common. For example, a manager-worker system may use a debate step for high-stakes decisions, or a peer-to-peer system may escalate to a manager when agents disagree.


  4. 

    What are common multi-agent coordination failures, and how do you prevent them?

    Multi-agent systems fail less often from weak reasoning and more often from coordination bugs:

      

    • 

      Circular delegation: Agent A delegates to B, and B delegates back to A. Prevention: track delegation chains, detect loops, and enforce a maximum handoff depth.


    • 

      Context loss at handoff: one agent has critical information, but it is not passed to the next agent. Prevention: use explicit handoff protocols that include task state, constraints, evidence, and unresolved questions.


    • 

      Conflicting actions: two agents act on the same shared resource, for example both reserve the same inventory. Prevention: use locks, transactions, idempotent operations, and coordination rules for shared state.


    • 

      Deadlocks: Agent A waits for B, while B waits for A, or a longer waiting cycle forms. Prevention: avoid circular dependencies, define ownership clearly, and enforce timeouts with fallback behavior.


    • 

      Runaway coordination: agents spend more time coordinating than doing useful work. Prevention: set coordination budgets, including token, time, and handoff limits, and prefer centralized planning when tasks are tightly coupled.


    

    The best way to validate a multi-agent design is to test adversarial scenarios that intentionally trigger these issues.








Thread: Production Operations


    

  1. 

    What is bounded autonomy, how do you define the right boundaries, and how does human-in-the-loop escalation fit in?

    Bounded autonomy means an agent is allowed to act freely within clearly defined limits and must escalate beyond them. It is the practical middle ground between full autonomy, which is too risky, and full manual control, which is too slow.

    The core design task is to define where the boundaries should be. In production systems, boundaries are typically expressed along a few dimensions:

    

      

    • 

      Action type: read actions are usually lower risk than write or destructive actions, since writes can have irreversible consequences.


    • 

      Impact magnitude: larger financial, operational, or user-facing impact requires stricter controls.


    • 

      Scope: actions that affect many users, systems, or datasets should be more tightly constrained.


    • 

      Confidence and uncertainty: low-confidence outputs or ambiguous situations should trigger escalation.


    • 

      Policy and compliance: regulated or policy-sensitive actions may require approval regardless of confidence.


    

    

    A good design usually starts conservative. Agents are given autonomy for low-risk, reversible actions, while higher-risk actions require validation, approval, or escalation. Over time, teams refine these boundaries based on observed failures, false positives, and business risk tolerance.

    Human-in-the-loop (HITL) is how escalation is handled well, and it is not just an approval button. The review interface should help the reviewer make an informed decision by showing what the agent intends to do, why it chose that action, what evidence it used, and what the expected impact is. Approval flows should support more than approve or reject; useful options include approve, reject, approve with modifications, approve with conditions, defer pending more information, and escalate to a higher authority. Escalation paths should be explicit. A common pattern is: agent → review queue → human operator → domain expert, with the escalation target matching the type of risk, such as technical failure, policy violation, or financial impact.

    The key trade-off is efficiency versus risk. If boundaries are too tight, the system escalates too often and loses the benefit of automation. If boundaries are too loose, the agent can take unsafe actions.


  2. 

    How do you observe and evaluate agent systems in production (what to trace, what to measure)?

    Observability is a core requirement because agent failures are often multi-step and emergent. Unlike traditional software, the same user request may lead to different reasoning paths, different tool calls, and different outcomes, so debugging cannot rely on a single execution path or one failed line of code. This means capturing the full execution trajectory, not just final outputs. At minimum, production traces should include:

    

      

    • 

      all LLM calls, including prompts, model outputs, and metadata,


    • 

      all retrieval events, including queries, retrieved documents, scores, and reranking results,


    • 

      all tool calls, including tool name, parameters, return values, timing, and errors,


    • 

      state transitions, including memory updates, planner decisions, retries, and stop conditions.


    

    

    Traces should be structured so they can be analyzed later. This usually means adding timestamps, parent-child relationships between events, request IDs, and task-level metadata. Without this structure, debugging becomes guesswork.

    You trace in order to measure. Agent evaluation should measure more than whether the final answer looks good:

    

      

    • 

      Task success rate: did the agent complete the user’s goal?


    • 

      Planning efficiency: how many steps or tool calls did it take, relative to task complexity?


    • 

      Cost per task: what was the total cost, including LLM, retrieval, and tools, per completed task?


    • 

      Latency: what was the end-to-end response time and step-level latency percentiles?


    • 

      Tool success rate: how often do tool calls succeed versus fail?


    • 

      Retry rate: how often does the agent need to retry because of poor retrieval, tool errors, or invalid inputs?


    • 

      Escalation rate: how often does the task require human review or approval?


    • 

      Failure breakdown: what fraction of failures come from retrieval, tool execution, timeouts, policy blocks, or reasoning errors?


    

    

    A strong answer distinguishes between business outcomes such as task success, system efficiency such as latency and cost, and operational reliability such as tool failures, retries, and escalations.


  3. 

    What security threats are unique to tool-using agents, and how do guardrails and sandboxing defend against them?

    Agents introduce security risks beyond standard application security because they combine model outputs, external content, and tool execution:

    

      

    • 

      Prompt injection: malicious instructions in user input attempt to override system behavior. Defense: enforce instruction hierarchy, validate tool parameters, and apply output filtering.


    • 

      Indirect prompt injection: malicious instructions hidden in retrieved documents, web pages, or tool outputs. Defense: treat retrieved content as untrusted data, not trusted instructions; isolate instructions from retrieved context.


    • 

      Tool misuse: the agent is tricked into calling tools it should not use, or using them with unsafe parameters. Defense: strict schema validation, permission scoping, semantic validation, and policy checks before execution.


    • 

      Data exfiltration: sensitive information extracted through outputs or passed to unauthorized tools. Defense: access controls, output filtering, per-tool data policies, and least-privilege credentials.


    • 

      Resource exhaustion: attackers trigger expensive or long-running tool loops to degrade service. Defense: rate limits, token budgets, timeout thresholds, and per-task cost caps.


    

    

    Guardrails are the first half of the defense, applied at three stages of execution. Input guardrails run before the agent processes a request: they validate user intent, detect prompt injection attempts, block disallowed topics, and enforce rate limits, and if one triggers, the agent never executes. Intermediate guardrails run during execution, typically before tool calls: they validate that proposed tool parameters are safe, block writes to a production database, and flag unusually large API requests. Output guardrails run after generation, before the response reaches the user: they check for PII leakage, hallucinated claims, or policy violations, and can redact, regenerate, or escalate. Guardrails can be implemented as rules such as regexes or blocklists, classifiers trained on policy violations, or LLM-based checks in which a smaller model evaluates the larger model’s output.

    Sandboxing is the second half. It limits the blast radius even when the agent is wrong or manipulated, constraining file access, credentials, network egress, execution time, and resource usage. The goal is an explicit trust boundary: the model can propose actions, but the execution environment enforces what is actually allowed.

    No single mechanism is sufficient. Production agent security is a layered defense problem: prompt safeguards, policy enforcement, sandboxing, access control, and monitoring all work together.


  4. 

    What is FinOps for agents, and what optimization strategies matter most?

    FinOps stands for Financial Operations; for agents, it means tracking and optimizing model costs, including tokens and model choice, retrieval and tool costs, and latency versus cost. The most effective strategies are usually architectural:

      

    • 

      Model routing (the router pattern): not every request needs a frontier model. A small model acts as a decision layer that directs each request to the appropriate path, sending structured decisions to cheaper models and reserving frontier models for tasks that truly require deeper reasoning. The key requirement is routing reliability: a good router must correctly distinguish simple requests from complex ones. Router training data often comes from logged traffic, where teams collect requests, label the best handling path, and train a classifier or lightweight model to predict the route. A useful rule of thumb is to use small models for structured decisions such as intent classification, topic routing, extraction, and guardrails, and to reserve larger models for open-ended reasoning such as complex planning, nuanced synthesis, or multi-step tool use.


    • 

      Caching: use semantic caching for repeated or similar requests, and cache intermediate tool outputs when appropriate.


    • 

      Budgeting: set explicit budgets for tokens, tool calls, retries, and wall-clock time to bound worst-case cost.


    • 

      Prompt and context optimization: reduce unnecessary tokens, trim prompts, and pass only the context needed for the current step.


    

    Since the router directs simpler requests to deterministic workflows or lightweight RAG pipelines rather than a full agent loop, routing is what keeps overall cost bounded as traffic grows.
