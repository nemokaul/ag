Chapter 13. LLM Inference

You’ve spent months and millions training a 70B-parameter model. Now a user types “Hello” and your system needs to respond in under a second. That single reply kicks off inference: the process of generating output tokens from a prompt. At scale, inference is where the money goes; for a widely deployed model, the serving bill can exceed the original training cost within weeks.

In this chapter we explain how LLM inference works and how production systems make it fast, scalable, and cost-efficient. We start with the fundamentals of inference. We then cover optimization techniques to accelerate inference, and finally we conclude the chapter with deployment topics, including multi-GPU parallelism, continuous batching, model routing, and more.

Inference Fundamentals

We begin with the two-phase process by which LLMs generate text.

Prefill and Decode

When a user types “Summarize this article in three bullet points” and hits Enter, the model’s work begins in two distinct phases.

Prefill phase: The model processes all of the user’s input tokens in parallel, computing the key and value vectors that form the KV cache (explained in Section “Attention and Memory Optimization”) for every prompt position. The final prompt position also produces the logits from which the first output token is selected. From the user’s perspective, prefill is the pause between pressing Enter and seeing the first token appear.

Decode phase: Starting with the first output token produced during prefill, the model generates the remaining tokens one at a time. At each step, it processes the latest token, attends to the key and value vectors cached for all preceding tokens, appends the new token’s vectors to the KV cache, and predicts the next token. This requires repeatedly accessing the model’s weights and an increasingly large KV cache while performing relatively little computation, so the GPU often spends more time moving data from memory than doing arithmetic. From the user’s perspective, decode determines how quickly text streams onto the screen.

To understand why these two phases behave so differently, it helps to look at the two GPU resources they stress. A GPU has two main assets: thousands of compute cores that do arithmetic, and memory bandwidth, the speed at which data travels from memory to those cores. When the cores are the bottleneck, the workload is compute-bound; when waiting for data is the bottleneck, it is memory-bound.

Prefill is compute-bound: the cores are fully occupied multiplying large matrices for all prompt tokens at once. Decode is memory-bound: the model loads its entire weights and the full KV cache each step, but performs only a tiny amount of arithmetic per load. Figure 13-1 summarizes the contrast.

With that two-phase picture in mind, the next question is how to measure whether the system is fast enough.

Key Metrics

During interactive inference, users notice two things: how long they wait before the first token appears, and how quickly subsequent tokens stream onto the screen. The first experience is dominated by prefill, while the second is determined by decode. The industry tracks a few key metrics that capture these aspects of inference performance.

Time to First Token (TTFT). The wait before the first word appears. This is almost entirely determined by prefill speed. For interactive chat, a few hundred milliseconds feels highly responsive; above a second feels the system is broken.

Time Per Output Token (TPOT). How long the user waits between each subsequent word. At 50-100ms per token (equivalent to 10-20 tokens per second), streaming feels fluid; above 200ms it feels sluggish. This is fully determined by decode speed.

Throughput. The total number of output tokens generated per second across all concurrent requests. Unlike per-request generation speed, throughput measures the overall capacity of the serving system: higher throughput means more users served per GPU-dollar. A related refinement, goodput, counts only tokens that reach the user, excluding work that is wasted when a request is cancelled mid-generation or tokens are generated speculatively and then discarded.

For the rest of this chapter, we focus on TTFT and TPOT because they are the latency metrics users directly perceive; throughput matters more for serving efficiency, capacity planning, and cost. TTFT maps to prefill; TPOT maps to decode. Figure 13-2 summarizes this mapping.

If TTFT is 2 seconds but TPOT is 50ms, the bottleneck is mostly the prefill phase, not decode. The model starts responding too slowly, but once generation begins, tokens stream at a healthy speed. In this case, optimization should therefore focus on reducing TTFT—for example, by shortening prompts, reusing common prefixes through prefix caching, using more efficient attention kernels, or improving scheduling with techniques such as chunked prefill. If TPOT were high instead, the bottleneck would be decode, and the focus would shift to decode optimizations.

Latency metrics tell us how quickly a model produces tokens, but they do not explain how those tokens are selected. At each decode step, the model assigns a probability to every possible next token, and the decoding strategy determines how that probability distribution is turned into an actual choice.

Decoding Strategies

Decoding strategies serve four distinct goals:

  • what to sample — controlling output quality, diversity, and randomness;

  • what to guarantee — enforcing structural or formatting constraints;

  • what to ground — improving factuality and linking outputs to reliable evidence or provenance; and

  • how fast to generate — producing multiple tokens per model pass.

We cover the first three goals in this section and discuss the fourth in Section “Decoding Acceleration”. To make the differences concrete, suppose the model has generated the phrase The cat sat on and assigns the following probabilities to the next token: the (0.40), a (0.25), my (0.15), his (0.08), her (0.05), with thousands of other tokens sharing the remaining 0.07 probability. Different decoding strategies turn this same probability distribution into very different outputs.

Greedy decoding always selects the highest-probability token i.e. the in this example. It is deterministic and computationally simple, but it can produce bland or repetitive text. Because it chooses the most likely token independently at every step, it may repeatedly follow locally attractive choices rather than producing the best overall sequence.

Beam search maintains B candidate sequences, called beams, in parallel. With B=2, instead of immediately committing to the, it retains two candidates: the (0.40) and a (0.25). At each step the model expands both, scores the resulting sequences by cumulative probability, and again retains the two highest-scoring. After several steps, a sequence beginning with a may achieve a higher overall score than one beginning with the, even though the was initially more likely. Beam search has historically been useful for tasks with a narrow set of good outputs, such as machine translation and transcription. For open-ended generation, however, it often produces generic and repetitive text.

Temperature scaling adjusts how concentrated or flat the token distribution is. Before applying softmax, each logit zi is divided by a temperature T:

pi=exp(zi/T)∑jexp(zj/T)

At T=1, the distribution is unchanged. Considering only the five displayed tokens in Figure 13-3 and renormalizing, at T=0.5 the distribution sharpens (the probability of the rises from about 0.43 to 0.63, while her falls from about 0.05 to 0.01), and at T=2.0 it flattens (the falls to about 0.31, her rises to about 0.11). In general, T<1 concentrates probability on the most likely tokens, making outputs less random and closer to greedy; T>1 spreads probability across more tokens, producing more varied but potentially less coherent outputs. As T→0, the distribution collapses onto the highest-logit token, recovering greedy decoding.

Temperature scaling in practice

Temperature is one of the most commonly tuned generation parameters. Useful starting points: T=0−0.3 for code, extraction, and factual Q&A (precision over creativity); T=0.3−0.8 for general chat (a balance of stability and variation); T=0.7−1.0 for creative writing; and T=0.8−1.2 with multiple filtered candidates for brainstorming or synthetic data. Many frameworks treat T=0 as greedy decoding, useful when reproducibility matters.

Top-k sampling restricts the candidate set to the k highest-probability tokens, discards the rest, and renormalizes. With k=3 in our example, only the, a, and my remain eligible. This removes the low-probability tail, but k fixes the number of candidates regardless of the shape of the distribution: when the model is highly confident, even the kth token may be implausible; when the distribution is flatter, restricting to k tokens may discard reasonable alternatives.

Top-p (nucleus) sampling (Holtzman et al., 2020) chooses the cutoff dynamically. It retains the smallest set of highest-probability tokens whose cumulative probability reaches p, renormalizes, and samples from that set. With p=0.9 in our example, the nucleus is {the, a, my, his, her} (cumulative 0.93). When the model is confident, the nucleus is small; when the distribution is flatter, it grows. This makes top-p more adaptive than top-k.

Min-p sampling sets a threshold relative to the top token: keep any token whose probability exceeds minp×pmax. This avoids top-p’s failure mode where a mildly confident distribution still admits a long, partly nonsensical tail. Min-p is supported by widely used libraries including llama.cpp, vLLM, and Hugging Face Transformers.

Most serving systems combine temperature scaling (overall randomness) with top-p or min-p (tail truncation). Typical defaults are T=0.7−1.0, p=0.9−0.95, or minp=0.05−0.1.

Structured (constrained) decoding. When an output must be valid JSON, match a regular expression, or follow a grammar, the inference system masks invalid next-token choices at every decoding step: any token that would move the partial output off all valid paths is assigned zero probability, and the remaining tokens are renormalized. For example, a sentiment classifier constrained to positive|negative|neutral|non-relevant that has generated the prefix ne can only continue toward negative or neutral; the other options are masked out. Constrained decoding is especially useful for function calls, tool arguments, API responses, SQL queries, JSON objects, and code, where every generated token must preserve the required syntax.

Factuality-oriented decoding. Some inference-time methods reduce hallucinations by contrasting distributions. DoLa (Decoding by Contrasting Layers; Chuang et al., 2024) contrasts the next-token distributions of a mature later layer and a premature earlier layer, amplifying tokens whose support emerges in the deeper layers and downweighting tokens favored mainly by early layers; it needs no extra training but adds some overhead. A related idea, contrastive decoding (Li et al., 2023), applies the same principle across two models, subtracting a weak “amateur” model’s log-probabilities from a strong “expert” model’s to suppress generic continuations.

Always match the decoding strategy to the application. For factual Q&A, use low temperature (T≤0.3) or greedy. For creative writing, use nucleus sampling with higher temperature. For API outputs, add structured decoding constraints. A strong interview answer connects strategy to use case.

So far, we have focused on how the model selects each output token. We now turn to the main resources required to generate those tokens efficiently: attention computation and the memory used to store the KV cache.

Attention and Memory Optimization

Attention is one of the main memory and bandwidth bottlenecks in LLM inference. Recall from Chapter 7 that each token is projected into a query (Q), a key (K), and a value (V); scaled dot-product attention compares the query with the keys to produce scores, then uses those scores to weight the values into an output vector. Figure 13-4 shows this for a single decode step.

The critical detail for inference is that attention is pairwise: each token’s query must be compared against every key in the sequence. Figure 13-5 shows the resulting attention matrix. Because the model is autoregressive (causal), token 4 attends to tokens 1-4 but not the reverse. When the model generates a new token, it only computes one new row of this matrix, but that row requires reading all the keys from every previous token.

Those previous keys and values have not changed since they were first computed. Recomputing them at every step would be wasteful, so the system stores them in a KV cache, saving one key vector and one value vector for each token at every layer and key-value head. Figure 13-6 shows the mechanics: during prefill, all prompt tokens are processed in parallel and their K/V vectors fill the cache; during each decode step, the model computes only the new token’s Q, attends against the full cache, appends the new K/V, and moves on. The cache grows by one entry per step.

The cache can get really large. For a 70B model with 80 layers, 8 KV heads (using GQA, explained below), and 128-dimensional heads, a single 4,096-token sequence at FP16 requires:

2⏟K and V×80⏟layers×8⏟KV heads×128⏟head dim×4096⏟tokens×2⏟bytes (FP16)≈1.3 GB

On an 80 GB GPU, that limits you to a few dozen concurrent sequences, even before accounting for model weights. This memory pressure is the starting point for several inference optimizations. Some reduce how much KV data the model produces, some manage the remaining cache more efficiently at runtime, and some speed up the attention computation itself by reducing GPU memory traffic. The rest of this section covers three complementary families:

  1. Architecture-Level KV Cache Reduction: Model architecture choices that reduce how much KV data is produced in the first place, such as GQA and MLA.

  2. Runtime KV Cache Optimization: Serving-time techniques that manage, reuse, quantize, or offload the remaining cache more efficiently, such as PagedAttention, prefix caching, and KV cache quantization.

  3. Efficient Attention Computation: Kernel-level techniques that compute attention with less memory traffic, especially FlashAttention.

Architecture-Level KV Cache Reduction

In standard multi-head attention (MHA), each attention head has its own key and value projections, so a model with 64 heads stores 64 sets of K/V vectors per token per layer. Architecture-level reduction changes the model so it produces less KV data. One family reduces the number of KV heads through sharing, giving a spectrum from MHA (every head has its own K/V pair), to grouped-query attention (GQA, where groups of query heads share K/V pairs), to multi-query attention (MQA, where all query heads share a single K/V pair). Figure 13-7 shows this spectrum.

Grouped-Query Attention (GQA). Multiple query heads share the same key and value projections. Dividing 64 query heads into 8 groups that each share one K/V pair reduces the KV cache by 8× while preserving more expressiveness than sharing a single K/V pair across all heads.

Multi-Query Attention (MQA). The extreme case: all query heads share one K/V pair. This gives the smallest cache but can reduce quality, since every head attends through the same shared representation.

Multi-Head Latent Attention (MLA). Rather than reduce the number of KV heads, MLA (introduced by DeepSeek-V2) compresses the KV representation itself: it stores a compact latent vector per token and reconstructs the needed per-head K/V during attention. This can reduce cache memory further than aggressive KV sharing while preserving more head-specific information, at the cost of extra reconstruction compute. Figure 13-8 illustrates the idea.

Both KV head sharing and MLA are architectural decisions baked into the model. The techniques that follow work at serving time: they manage, reuse, quantize, or offload the KV cache produced by an already-trained model.

Runtime KV Cache Optimization

Once the model is fixed, the serving system must manage KV cache memory efficiently across many concurrent requests as they arrive, grow, and complete. Runtime techniques focus on four tasks: allocating cache memory efficiently, reusing shared prefixes, compressing cached data, and moving it between memory tiers.

The KV cache allocation problem. Earlier serving systems reserved a contiguous block per request sized for the maximum sequence length. If the maximum is 4,096 tokens but a request generates only 50, most of the space is wasted; across many requests this over-allocation wastes a large fraction of GPU memory. Fragmentation adds a second problem: because requests start and finish at different times, free memory splits into small gaps that are hard to reuse. Figure 13-9 illustrates both.

PagedAttention (Kwon et al., 2023) applies virtual-memory ideas to the KV cache. Instead of one contiguous block per request, the cache is divided into fixed-size pages (often 16 tokens each), and each sequence keeps a page table mapping logical positions to physical pages. Pages are allocated only when needed and freed on completion. Figure 13-10 contrasts this with contiguous allocation.

This makes cache memory far easier to share and drops waste sharply, since requests receive only the pages they use. It also makes prefix sharing natural: sequences with the same system prompt or few-shot examples can point to the same physical pages. This idea underlies modern high-throughput serving systems such as vLLM, SGLang, TensorRT-LLM, and Hugging Face TGI.

Prefix caching. Many applications send the same prefix (a system prompt, policy instructions, or few-shot examples) with every request. Prefix caching computes the KV cache for that shared prefix once and reuses it, so only the new user-specific tokens are prefilled. This reduces TTFT and works especially well with paged layouts, where shared prefix pages can be marked read-only and referenced by multiple sequences.

KV cache quantization. Storing cache entries at lower precision (INT8 or INT4 instead of FP16) lowers both memory usage and memory bandwidth. Since the cache is written once but read repeatedly during decode, this can improve concurrency and TPOT.

Beyond these, specialized policies target specific constraints: a static cache pre-allocates a fixed length to enable graph compilation; a sliding window cache keeps only the most recent W tokens; attention sinks (Xiao et al., 2024, as in StreamingLLM) retain a few initial tokens alongside a sliding window to stabilize very long generation; and an offloaded cache moves part of the KV cache to CPU memory when GPU memory runs out, trading latency for capacity.

Efficient Attention Computation (FlashAttention)

Standard attention computes the full N×N score matrix QKT, writes it to GPU high-bandwidth memory (HBM), applies softmax, then reads it back to multiply by V. For a 4,096-token sequence that matrix has 16 million entries, read and written multiple times through the slow HBM bus.

FlashAttention (Dao et al., 2022) processes attention in small blocks, or tiles, that fit inside the GPU’s fast on-chip SRAM. On an NVIDIA A100, SRAM is much smaller than HBM but moves data more than ten times faster, so keeping each tile close to the compute cores avoids repeatedly shuttling large intermediate results to and from HBM. Rather than building the full N×N matrix, FlashAttention computes the result one tile at a time and combines partial results as it goes, reducing attention memory from O(N2) to O(N) and making attention several times faster. FlashAttention-2 (Dao, 2023) improves parallelism across thread blocks and is the default backend in PyTorch 2.0+ via scaled_dot_product_attention.

FlashAttention is an exact attention computation algorithm: it produces bit-identical results to standard attention. The speedup comes entirely from reducing memory traffic, not from approximation.

So far we have reduced the cost of moving and storing intermediate data during inference. Another major cost is the model itself: billions of parameters must be stored in GPU memory and repeatedly read during generation. The next group of techniques reduces this footprint by compressing the model’s weights and, in some cases, its activations.

Model Compression

Model compression makes an LLM smaller and cheaper to run. A 70B model in FP16 needs about 140 GB for weights alone, more than a single 80 GB GPU, before any KV cache. Compression reduces this footprint through four main approaches:

  1. Quantization: Reduces numerical precision, such as FP16 to INT8 or INT4.

  2. Pruning: Removes weights, neurons, heads, or layers to produce a smaller or sparser model.

  3. FP8 inference: Uses 8-bit floating-point formats to reduce memory bandwidth while preserving more dynamic range than INT8.

  4. Knowledge distillation: Trains a smaller student model to mimic a larger teacher.

Quantization is usually the first technique teams try: it applies after training and often delivers large savings with little quality loss. For example, 4-bit weight quantization can reduce a 70B model’s weights from about 140 GB to roughly 35 GB.

Quantization

Instead of storing each weight as a 16-bit float, store it as an 8-bit or 4-bit integer. The model uses less memory, loads faster, and the decode speedup (memory-bound) is nearly proportional to the data-size reduction. Quantization can be applied at two times: post-training quantization (PTQ) uses a small calibration dataset after training and takes minutes to hours; quantization-aware training (QAT) simulates low precision during training, often preserving quality better at the same bit width but requiring expensive retraining. PTQ dominates LLM deployment because teams usually need to compress already-trained models without the original pipeline or compute; GPTQ, AWQ, and SmoothQuant are all PTQ methods.

Figure 13-11 shows the trade-off between precision, memory, speed, and quality. For a 70B model, FP32→FP16 cuts weight memory from about 280 GB to 140 GB; 8-bit brings it to roughly 70 GB; INT4 to about 35 GB. Lower precision moves less data and can improve speed on supporting hardware, at some risk to quality: FP8 and INT8 usually preserve quality well, while INT4 compresses more but risks degradation.

PTQ methods differ in what they quantize: weights only (simpler to deploy) or both weights and activations (larger gains, harder to keep accurate).

Weight-Only Quantization

Weight-only quantization reduces the precision of the weights (commonly INT8 or INT4) while leaving activations in FP16 or BF16. This suits LLM serving because decode is often limited by the bandwidth needed to load weights. Two widely used PTQ methods are:

  • GPTQ (Frantar et al., 2023) quantizes one layer at a time, estimating which rounding errors most affect a layer’s output and adjusting the not-yet-quantized weights to compensate. It can compress very large models to 4-bit with little quality loss.

  • AWQ (Lin et al., 2024) observes that some weight channels matter far more than others (those tied to large activations). Using a small calibration set, it rescales these salient channels so they survive quantization, without GPTQ’s Hessian-based compensation, making it simpler and faster.

Both store weights at roughly one quarter of FP16 size (INT4) and accelerate memory-bound decode, but leave activations in FP16/BF16. The next subsection quantizes both.

Weight-and-Activation Quantization

To use GPU INT8 tensor cores fully, both weights and activations must be quantized, which is harder because activations are dynamic and contain outliers. LLM.int8() (Dettmers et al., 2022) observed that at multi-billion-parameter scale a few hidden dimensions carry values much larger than the rest; it keeps those outlier channels in FP16 and processes the rest in INT8 (mixed-precision decomposition), preserving quality but not fully realizing INT8 speed.

SmoothQuant (Xiao et al., 2023) instead applies an offline transformation before quantization. For a linear layer Y=X·W, it rewrites the computation as:

Y=(X·diag(s)−1)·(diag(s)·W)=X^·W^

where s is a per-channel scaling vector from calibration. Dividing activation channels by s reduces outliers while multiplying the corresponding weight channels by s preserves the output. The transformed activations and weights are easier to quantize, enabling W8A8 (8-bit weights and activations) inference, which can accelerate both prefill and decode on supporting hardware. The trade-off is that activation quantization is more sensitive and needs careful calibration.

Pruning

Pruning removes parts of the model that contribute little to its output. Unstructured pruning zeroes individual low-magnitude weights; at 50% sparsity half the weights are zero, but because the zeros are scattered, standard GPUs cannot skip them efficiently, so the model needs less storage but is rarely faster without specialized kernels. Structured pruning removes whole rows, columns, heads, or layers, keeping tensors dense so GPUs process them efficiently; the trade-off is that it removes important and unimportant weights together, so quality can degrade faster. In practice quantization is usually the first choice; pruning becomes attractive when quantization alone is insufficient or when hardware supports sparsity, such as NVIDIA’s 2:4 pattern (two zeros in every four weights), which can roughly double throughput on supported Tensor Cores.

FP8 Inference

FP8 inference stores and computes tensors in 8-bit floating-point formats, reducing memory and bandwidth versus FP16/BF16. NVIDIA H100 and newer GPUs provide native FP8 tensor cores, making FP8 a practical middle ground between INT8 and 16-bit inference. Unlike INT8, FP8 keeps a floating-point representation, giving it a wider dynamic range that makes activation quantization easier, especially with outliers. Common formats are E4M3 and E5M2; FP8 can preserve quality close to FP16 while improving throughput when model, kernels, and hardware support it.

Knowledge Distillation

Knowledge distillation trains a smaller student model to mimic a larger teacher, which may provide target outputs, probability distributions, reasoning traces, or synthetic instruction data. Because it is fundamentally a training-time technique, we cover it in detail in Chapter 9. For inference, the key point is that distillation is one of the main ways to produce smaller models that are cheaper and faster to serve, especially for latency-sensitive or on-device deployment.

Quantization, pruning, FP8 inference, and distillation all attack the same problem: reducing the memory, bandwidth, and compute required to serve a model. The next set of techniques, decoding acceleration, instead makes token generation faster by reducing the work needed during the decode phase.

Decoding Acceleration

Decoding generates one token per forward pass, and each pass loads the full model weights from memory. The decoding acceleration techniques all attack that bottleneck by getting more useful tokens per unit of GPU work. They differ in where the candidate tokens come from, but share a key insight: verifying multiple tokens in parallel is nearly as cheap as generating one, because the cost is dominated by loading weights, not by arithmetic.

Speculative Decoding

Speculative decoding (Leviathan et al., 2023; Chen et al., 2023) uses a small, fast draft model (say 1B parameters) to propose several tokens, which a much larger target model (say 70B) then evaluates in parallel. When the target accepts several proposals, the system generates multiple tokens from a single target pass plus the cheap draft work.

The process, illustrated in Figure 13-12, works as follows:

  1. The draft model generates k candidate tokens autoregressively.

  2. Using the existing KV cache, the target model evaluates all k candidate positions in a single forward pass.

  3. Candidates are checked left to right. A token is accepted with probability min(1,p/q), where p is its target probability and q its draft probability; it is always accepted when the target assigns it at least as much probability as the draft.

  4. At the first rejection, the remaining draft tokens are discarded and a replacement is sampled from a corrected target distribution.

  5. If all k candidates are accepted, the target samples one additional token. The process then repeats.

The acceptance rule and corrected resampling together preserve the target model’s output distribution: the final tokens follow the same distribution as sampling directly from the target. Speculative decoding works best at low batch sizes, where decode is memory-bandwidth bound, giving roughly 2–3× speedups; the benefit shrinks with large batches or a low draft acceptance rate, and the draft model needs extra GPU memory.

Draft-Free and Self-Speculative Variants

Several methods avoid maintaining a separate draft model, all of them lossless because the target still verifies every proposal. Prompt-lookup decoding proposes tokens by matching n-grams between the prompt and the generated text so far, ideal for copy-heavy tasks like summarization and extraction. Multi-token prediction methods add lightweight prediction heads to the target model: Medusa (Cai et al., 2024) attaches extra heads that propose a tree of continuations verified in one pass, while EAGLE/EAGLE-2 (Li et al., 2024) use early-layer features with dynamic draft trees, reaching 3–4× speedups on LLaMA-2-Chat 70B. Lookahead decoding (Fu et al., 2024) uses Jacobi iteration to explore future tokens with the target model itself, needing no auxiliary model. Early-exit and self-speculative decoding (e.g. LayerSkip, Elhoushi et al., 2024) treat the model’s early layers as a drafter and the remaining layers as the verifier, reusing a single model and KV cache.

Every technique in this section produces exact output, matching the target model token-for-token; the speedup comes at no quality cost. The interview question is “when would you use which?” Speculative decoding with a separate draft model gives the best speedups but requires memory for two models. Medusa and self-speculative decoding avoid the second model. Prompt lookup is ideal for summarization and extraction. Lookahead requires no changes at all. Early exit reduces per-token cost rather than generating multiple tokens at once.

Faster decoding is only part of the story: production performance also depends on how the serving system schedules requests, manages hardware, and coordinates execution at scale.

Serving and System-Level Optimizations

In production, performance also depends on how the serving system executes the model across hardware and across many concurrent requests. This section covers compiling computation graphs, splitting models across GPUs, batching requests continuously, separating prefill from decode, scheduling under load, serving MoE models, and routing requests across models.

Graph Compilation with torch.compile

By default PyTorch executes a model eagerly, launching one operation at a time. torch.compile (PyTorch 2.0) captures regions of computation and compiles them into optimized kernels, fusing operations and cutting Python and kernel-launch overhead; mode="reduce-overhead" uses CUDA Graphs to help small batches. The catch is that it requires consistent tensor shapes to avoid recompilation, so a growing KV cache can trigger recompiles; pairing it with a static cache solves this. Most serving frameworks handle this internally.

Multi-GPU Parallelism

A 70B model needs about 140 GB for FP16 weights alone, exceeding a single GPU; even at INT4 (~35 GB), splitting across GPUs can improve latency and free memory for the KV cache. We covered parallelism for training in <sec:parallelism_training>; here we focus on inference. Tensor parallelism (TP) splits weight matrices within each layer across GPUs, so all GPUs collaborate on every token; it reduces per-GPU computation and latency but requires exchanging partial results within each block, so it works best within a node connected by NVLink or NVSwitch. Pipeline parallelism (PP) assigns consecutive layer groups to different GPUs, needing only activation transfers between stages, but suffers pipeline bubbles where GPUs idle. For low-latency inference TP is generally preferred; for models spanning multiple nodes, TP is often used within a node and PP across nodes.

Continuous Batching

Early serving used static batching: a fixed set of requests runs until every request completes, so shorter requests leave their slots idle and new arrivals wait. Continuous batching (iteration-level scheduling) updates the batch after every decoding step, removing finished sequences and inserting waiting requests, which keeps slots occupied and improves GPU utilization and throughput. Figure 13-13 compares the two. It is now a standard feature in modern LLM serving frameworks.

Prefill/Decode Disaggregation

Since prefill and decode have opposite hardware requirements, disaggregated serving (Zhong et al., 2024; Patel et al., 2024) runs them on separate GPU pools: prefill on compute-optimized GPUs, decode on bandwidth-optimized hardware, with the KV cache transferred over the network after prefill. This brings substantial cost savings at the cost of system complexity, since the system must move large KV caches with low latency, coordinate handoffs, and recover from worker failures.

Request Scheduling Under Load

When many requests compete for the same GPUs, the serving system must decide which run now and prevent one expensive request from hurting everyone’s latency. Priority queues rank requests by urgency, tier, SLO, or estimated cost. Preemption pauses a lower-priority request so a higher-priority one can run, at the cost of restoring or recomputing its KV cache later. Chunked prefill breaks long prompts into smaller chunks interleaved with decode steps from other requests, so a single long prompt cannot monopolize the GPU and TPOT stays stable for ongoing generations.

MoE Inference Challenges

Mixture-of-Experts models like Mixtral and DeepSeek-V3 activate only a subset of expert sub-networks per token (Mixtral selects 2 of 8; DeepSeek-V3 activates 37B of 671B). Serving them introduces new challenges. . Expert placement: because all experts may not fit on one GPU, expert parallelism distributes them, routing each token to the GPUs holding its experts and requiring all-to-all communication that can dominate latency, especially across nodes. . Load imbalance: some experts receive far more tokens than others, so systems co-locate hot and cold experts, replicate popular ones, or rebalance dynamically. . Expert offloading: less-used experts can live in CPU memory and load on demand, saving GPU memory but adding latency unless prefetched.

Model Routing and Cascading

Not every query needs a 70B model. Model routing sends easy queries to a small, cheap model and hard queries to a large one, using a rule-based or lightweight-classifier router. A well-tuned router can cut serving costs 50-70% while maintaining quality on hard queries; OpenAI’s GPT-4o-mini/GPT-4o split is one public example.

Inference Frameworks

Most teams use one of four major open-source serving frameworks, which package scheduling, batching, KV cache management, and optimized kernels behind a serving API. vLLM (Kwon et al., 2023) introduced PagedAttention and is a flexible, Python-friendly default for prototyping and production. TensorRT-LLM is NVIDIA’s performance-focused framework for NVIDIA GPUs, best when maximum performance justifies hardware-specific tuning. SGLang (Zheng et al., 2024) uses RadixAttention for efficient prefix reuse and strong structured-output support, suiting multi-turn, agentic, and structured-generation workloads. Text Generation Inference (TGI) is Hugging Face’s framework, well integrated with that ecosystem but now in maintenance mode. (The interview Q&A below compares these in more depth.)

Summary

The central idea running through this chapter is that prefill is compute-bound, decode is memory-bound, and every optimization targets one side of that divide. Grouped-Query Attention (GQA) and Multi-Head Latent Attention (MLA) reduce the KV cache at training time; PagedAttention, prefix caching, and cache quantization manage it at serving time. FlashAttention keeps attention computation on fast SRAM instead of slow HBM. Quantization and pruning shrink the model itself.

Decoding acceleration, from speculative decoding and EAGLE-2 to prompt lookup and early exit, gets multiple tokens per forward pass. Graph compilation via torch.compile fuses operations. Parallelism, batching, and disaggregation scale serving across hardware. Structured generation, DoLa, and model routing shape what work gets done and by which model. The major frameworks (vLLM, TensorRT-LLM, SGLang, TGI) implement most of these techniques out of the box.

Interview Questions and Answers

Thread: LLM Inference Fundamentals

  1. What happens when a user sends a message to an LLM?

    Two phases fire in sequence: prefill and decode.

    During prefill, the model processes all prompt tokens in parallel, builds the KV cache, and generates the first output token. Because this involves large matrix multiplications, prefill is usually compute-bound. Its latency is measured by Time to First Token (TTFT).

    During decode, the model generates one token at a time. Each step reuses the KV cache but must repeatedly read the model weights and cached values from memory. This makes decode largely memory-bandwidth-bound. Its latency is measured by Time per Output Token (TPOT).

  2. Can you explain why decode is memory-bound?

    During decoding, the model generates one token at a time. At each step, the GPU must fetch the weights of every layer, along with the relevant KV-cache entries, from high-bandwidth memory (HBM) into faster on-chip memory near the compute units. It then performs mostly matrix-vector operations to compute the hidden representation for the new token.

    Because only one token is being processed, each weight is used for relatively little computation before the next layer’s weights must be loaded. For example, multiplying a 4096×4096 FP16 weight matrix by a single vector requires reading about 33 MB of weights. As a result, decode speed is often limited by how quickly data can be moved from memory rather than by the GPU’s raw compute capacity.

  3. What exactly is arithmetic intensity, and how do you use the roofline model?

    Arithmetic intensity is defined as

    Arithmetic intensity=FLOPsBytes accessed.

    Every GPU has a crossover point, often visualized in the roofline model: below this point, an operation is memory-bound; above it, it is compute-bound. For an A100 at FP16, this crossover is approximately 156 FLOPs/byte.

    During prefill, with 1024 tokens and a 4096×4096 matrix, you perform roughly 34B FLOPs while accessing about 33 MB, giving

    34B33M≈1024 FLOPs/byte

    This is well above the crossover, so prefill is compute-bound.

    During decode, with just 1 token, you perform only about 33M FLOPs while still accessing the same 33 MB of weights, giving

    33M33M≈1 FLOP/byte

    This is far below the crossover, so decode is deeply memory-bound.

  4. What is the single biggest lever for speeding up decode?

    The biggest lever is to reduce the amount of data read from memory at each token step. For that, weight quantization helps the most: converting weights from FP16 to INT4 reduces their size by roughly 4 times, which can significantly improve decode speed.

    Reducing the KV cache through techniques such as GQA or KV-cache quantization also helps, especially for long contexts, and allows the server to handle more concurrent requests.

Thread: The KV Cache

  1. Tell me about the KV cache. How big does it get?

    In each attention layer, every token produces a key (K) and value (V) vector. During generation, only the new token’s query changes; all previous K/V vectors are the same as last step. Rather than recompute them, we cache them: one K and one V per token, per layer, per KV head. The cache grows by one entry per step, and the GPU reads the entire cache every step. This is why decode is memory-bound.

    For LLaMA-70B (80 layers, 8 KV heads, dim 128) at FP16 with 4,096 tokens, the total KV-cache size is therefore:

    2⏟K,V×80×8×128×4096×2⏟FP16≈1.3 GB per sequence

    On an 80 GB GPU with about 30 GB for model weights, you can fit roughly 38 concurrent sequences. At 128K context it is about 41× worse. The KV cache, not the weights, is usually the binding constraint on concurrency.

  2. What is grouped query attention?

    In standard multi-head attention, each query head has its own key and value heads. Grouped-query attention (GQA) reduces this number by allowing multiple query heads to share the same key and value heads.

    For example, a model with 64 query heads and 8 KV heads groups 8 query heads around each KV head. This reduces KV-cache memory and memory bandwidth by 8 times, making decode faster and allowing more concurrent requests, with little impact on model quality.

  3. What are the alternatives to grouped-query attention?

    One related approach is Multi-Query Attention (MQA), where all query heads share a single key and value projection. MQA minimizes KV cache size, but it can reduce quality because every head attends through the same shared K/V representation. GQA is a middle ground between standard multi-head attention and MQA as it groups query heads so each group shares a K/V pair.

    Another approach is Multi-Head Latent Attention (MLA), introduced by DeepSeek-V2. Instead of reducing KV cache size by sharing K/V heads, MLA compresses each token’s key-value information into a smaller latent vector and reconstructs the needed representations during attention. This can reduce cache memory further while preserving more head-specific information, at the cost of extra reconstruction compute.

  4. What can you do at serving time to manage the KV cache?

    There are three complementary techniques.

    • PagedAttention borrows the idea of virtual memory from operating systems. Instead of preallocating contiguous blocks—which can waste 60–80% of memory on padding—it divides KV-cache memory into fixed-size pages allocated on demand. This reduces waste to below 5%, enabling 4×--8× more concurrent sequences.

    • Prefix caching: If every request includes the same 2,000-token system prompt, compute its KV cache once and reuse it. Only the unique suffix requires prefill, reducing TTFT by 50–90% in applications with substantial prompt reuse.

    • KV cache quantization: Store the cache in INT8 or INT4 rather than FP16. Because the cache is written once but read repeatedly during decoding, the reduced memory traffic directly improves TPOT with negligible quality loss.

Thread: Model Compression

  1. How can we deploy a 70B model on a single 80 GB A100?

    At FP16, a 70B model requires about 140 GB for weights alone, so it will not fit. The most practical option is INT4 weight-only quantization using GPTQ or AWQ. This reduces the weights to roughly 35 GB, leaving about 45 GB for the KV cache and runtime overhead. GPTQ uses Hessian-based error compensation, while AWQ protects activation-sensitive weights through scaling. In practice, choose the method best supported by your serving framework.

  2. How does GPTQ achieve INT4 with minimal quality loss?

    GPTQ quantizes one layer at a time using a small calibration set, typically 128–256 samples. It estimates which weights are most sensitive to quantization using second-order information from the layer’s reconstruction error.

    GPTQ then quantizes the weights sequentially. After rounding one group of weights to INT4, it adjusts the remaining weights to compensate for the introduced error. This error correction produces much lower quality loss than naive rounding. Quantizing a large model typically takes minutes to hours.

  3. How does AWQ differ from GPTQ?

    GPTQ uses approximate second-order information to quantize weights while compensating for the resulting error. AWQ instead uses calibration data to identify salient weight channels based on activation magnitudes. It applies scaling to protect these important channels before low-bit weight quantization. Unlike GPTQ, AWQ does not rely on Hessian-based error correction or weight reconstruction, making the quantization procedure simpler.

  4. What if I also want to quantize activations?

    Activation quantization is harder because a small number of channels can contain values much larger than the rest. These outliers widen the quantization range and reduce precision for normal values.

    LLM.int8() handles this by keeping the outlier channels in FP16 while quantizing the rest to INT8. SmoothQuant instead rescales the activations to reduce these outliers and applies the inverse scaling to the weights, preserving the computation:

    Y=XW=X^W^

    This allows both weights and activations to use INT8, enabling efficient W8A8 inference with little quality loss.

  5. When would you choose W4A16 versus W8A8?

    Choose W4A16 when memory capacity and decode latency are the main constraints. INT4 weights provide roughly 4× compression and reduce the amount of data read during decoding, while activations remain in FP16.

    Choose W8A8 when you want to accelerate both prefill and decode. INT8 weights and activations can use optimized tensor-core kernels, but weight compression is only about 2×, so the model requires more memory than W4A16.

    A common serving configuration uses W4A16 weights together with an INT8 KV cache to reduce both weight and cache memory.

  6. How do unstructured and structured pruning differ, and how does it compare to quantization?

    Unstructured pruning zeros out individual weights by magnitude. A 50%-sparse model is smaller on disk but runs at roughly the same speed on standard GPUs; scattered zeros do not help without sparse-matrix hardware.

    Structured pruning removes entire attention heads, FFN neurons, or layers, preserving dense matrix shapes GPUs can exploit. Coarser granularity means quality degrades faster at the same sparsity level.

    For most deployments, quantization is the simpler and more effective first step. Pruning is most useful when combined with quantization for extreme compression or when the hardware provides native support for structured sparsity.

Thread: Serving at Scale

  1. Your model is deployed, and 1,000 users hit it. Which system-level optimizations would you apply?

    Three optimizations matter most:

    • Continuous batching dynamically adds and removes requests at each decoding step, keeping the GPU busy.

    • PagedAttention allocates KV-cache memory on demand, reducing waste and supporting more concurrent requests.

    • Prefill/decode disaggregation runs the two phases on separate resource pools so each can be scaled independently.

    Together, these techniques can dramatically increase throughput and the number of users served per GPU compared with a naive deployment.

  2. What is continuous batching?

    Static batching processes a fixed group of requests and waits for every sequence to finish before admitting new ones. Because output lengths vary, completed sequences leave unused batch slots.

    Continuous batching updates the batch after each decode step. Finished sequences are removed, and waiting requests are added immediately. This keeps GPU capacity better utilized and can improve throughput by 2−5 times under concurrent workloads.

  3. When is prefill/decode disaggregation worth it?

    Prefill is typically compute-bound, while decode is more memory-bandwidth-bound. Disaggregated serving runs them on separate GPU pools, allowing each phase to be scaled and optimized independently. After prefill, the system transfers the KV cache to a decode worker. This approach is most valuable at large scale, where better utilization can offset the added complexity of KV-cache transfers, cross-pool scheduling, and fault tolerance.

  4. What is chunked prefill?

    Chunked prefill divides a long prompt into smaller chunks, such as 512 tokens, and schedules them alongside decode steps from active requests. Without it, a single 32K-token prompt can occupy the GPU for a long prefill pass and delay token generation for other users.

    Chunking may increase the long request’s prefill time, but it reduces interference with ongoing requests and helps keep TPOT more predictable.

  5. Here is a scenario: you have a 70B parameter model on 2×A100. TTFT is 3 seconds, TPOT is 40ms. Users complain. What do you do?

    A TPOT of 40 ms, or about 25 tokens per second, is reasonable, so decode is not the bottleneck. The problem is TTFT, which points to prefill latency, queueing delay, or both.

    I would first inspect prompt length and cache behavior. If requests share a long system prompt, tool schema, or few-shot prefix, I would enable prefix caching. If the prompt is RAG-heavy, I would reduce the number or size of retrieved chunks. I would also check whether TTFT is coming from scheduler queue time; under load, continuous batching and chunked prefill can prevent long prompts from blocking other requests.

    If TTFT is still too high, I would consider adding more prefill compute, for example by increasing tensor parallelism or moving prefill to a larger/faster GPU pool. I would not start with speculative decoding, because it mainly improves decode speed, and TPOT is already fine. I also would not expect weight-only quantization to solve the main issue, because this case is dominated by first-token latency rather than decode bandwidth.

Thread: Decoding and Speculation

  1. What are the main decoding strategies?

    The main decoding strategies are greedy, beam and sampling based decodings. In all strategies, the LLM generate one token at a time, and at each generation step, it produces a probability distribution over the vocabulary. Different decoding strategies decide differently on how to choose the next token from that distribution.

    • Greedy decoding always selects the highest-probability token. It is deterministic and fast, but it often produces bland or repetitive text.

    • Beam search keeps B candidate sequences in parallel and expands the most promising ones. It is useful for tasks with a well-defined target, such as translation or summarization, but it is often too conservative for open-ended generation.

    • Sampling-based decoding introduces randomness by sampling from the probability distribution instead of always taking the maximum. Temperature controls how sharp or flat the distribution is: T<1 makes outputs more deterministic, while T>1 makes them more diverse. Top-k restricts sampling to the k most likely tokens. Top-p, or nucleus sampling, samples from the smallest set of tokens whose cumulative probability exceeds p. Min-p keeps tokens whose probability exceeds a fraction of the most likely token’s probability, such as 0.1×pmax. In production chat systems, a common default is temperature combined with top-p, top-k, or min-p.

  2. Can you reduce hallucinations at decode time, without changing the model?

    Yes. There are two techniques for it.

    DoLa (Decoding by Contrasting Layers) exploits the fact that factual knowledge emerges progressively across transformer layers. It computes the next-token distribution at both the final layer and an earlier layer, then takes the difference. Tokens where the deeper layers “changed their mind” (typically factual corrections) get amplified; tokens where both layers agree pass through unchanged. This does not require training and it has minimal compute overhead.

    Contrastive decoding applies the same principle between two separate models: a strong expert model and a weaker amateur model. It subtracts the log-probabilities of the amateur model from the expert model. Both models make the same generic mistakes in next token prediction, but the small model makes them more. The subtraction amplifies what the large model uniquely knows therefore supresses repetitive, or low-quality continuations.

  3. How does speculative decoding work?

    A small draft model (e.g., 1B parameters) first proposes k tokens. The large target model (e.g., 70B parameters) then evaluates all of them in one forward pass instead of generating them one by one. Since decode is memory-bound, verifying k tokens costs about the same as generating one.

    For each draft token, if the target model assigns equal or higher probability, the token is accepted. Otherwise, it is accepted with probability proportional to the ratio of target to draft probability. At the first rejected token, the system samples a corrected token from the target distribution and discards the remaining draft tokens. The output is mathematically identical to sampling from the target alone.

    When the draft model predicts well, several tokens are accepted at once; this reduces decode latency while preserving the same output distribution as sampling from the target model alone.

  4. When does speculative decoding help, and when can it hurt?

    Speculative decoding works best at small batch sizes, where the target model is not fully utilizing the GPU, and when the draft model has a high acceptance rate. In these conditions, it can provide roughly 2−3 times speedups.

    It helps less at large batch sizes, where the target model is already compute-saturated and verification adds overhead. It can also hurt when the draft model predicts poorly or when storing a second model reduces memory available for the KV cache and concurrent requests.

  5. Beyond a separate draft model, what other acceleration approaches exist?

    Several acceleration methods avoid the need for a separate standalone draft model, or at least reduce the cost of draft generation compared with classic speculative decoding. Here are five such methods:

    Prompt-lookup decoding is a retrieval-based variant of speculative decoding. Instead of using a draft model, it searches for overlapping n-grams in the prompt and uses the continuation of those matches as candidate draft tokens. It works especially well for input-grounded tasks such as summarization or extraction, where the output often reuses spans from the input. Its main advantage is that it avoids an auxiliary drafting model altogether.

    Medusa augments the target model with lightweight decoding heads attached to its hidden states. These heads predict multiple future tokens, producing a tree of candidate continuations that can be verified in parallel in one pass. This keeps the drafting mechanism inside the main model and adds far less overhead than maintaining a separate draft model.

    EAGLE-2 is another speculative decoding variant, but instead of predicting tokens directly, it drafts from intermediate model features and uses a context-aware dynamic draft tree. The core idea is to increase acceptance rates by adapting the draft structure to the current decoding state, which improves speedup over earlier EAGLE-style approaches.

    Lookahead decoding removes the auxiliary draft model entirely. It is based on Jacobi-style parallel decoding: a window of future positions is updated simultaneously, and once a consecutive prefix stabilizes across iterations, those tokens are accepted. Its appeal is that it is an exact decoding algorithm that does not require extra models or architectural modifications.

    Early-exit / self-speculative decoding uses the same model at two effective depths. Earlier layers generate provisional predictions, and later layers verify or correct them. Methods such as LayerSkip train the model so intermediate layers become more reliable for early exit, allowing the shallow portion of the model to act as an internal drafter with lower memory overhead than two-model speculative decoding.

    The unifying idea across these methods is the same: propose multiple candidate tokens cheaply, then verify them in parallel with the target model so that fewer full decoding steps are needed. Many of these methods are designed to be lossless, meaning they preserve the target model’s output distribution under the same decoding setup.

Thread: Deployment

  1. Compare the major serving frameworks.

    There is no single “best” serving framework; the right choice depends on your hardware, latency target, model family, and how much systems complexity you are willing to take on.

    vLLM: the most common starting point for general-purpose LLM serving. Its main strengths are broad model and hardware support, an easy OpenAI-compatible server, paged KV-cache management, and a good balance between usability and performance. It is usually the safest default for prototyping and for many production deployments.

    TensorRT-LLM: the most performance-oriented option when you are firmly in the NVIDIA ecosystem. It offers aggressive runtime optimization, strong support for quantization, long-context features, guided decoding, and advanced scheduling, but it comes with more setup and hardware specialization. It is a strong choice when low latency or high throughput on NVIDIA GPUs is the top priority.

    SGLang: a high-performance framework that is especially strong for advanced serving patterns such as prefix caching, structured outputs, speculative decoding, long-context serving, and large-scale distributed setups. It is attractive when you want both high performance and fine-grained control over structured or agent-style generation.

    TGI (Hugging Face Text Generation Inference): the most natural choice when your stack is already centered on Hugging Face models and tooling. It provides a production-oriented server with tensor parallelism, continuous batching, streaming, observability, and optimized inference kernels. It is often the easiest path when you want a reliable Hugging Face-native serving layer.

    A practical rule of thumb is to start with vLLM for general use, choose TensorRT-LLM for maximum performance on NVIDIA, choose SGLang when you need more advanced serving control or structured-generation features, and choose TGI when you want the simplest Hugging Face-centric deployment path.

  2. What are the key considerations when deploying LLMs on phones or laptops?

    Running models on phones, tablets, or laptops is a very different deployment setting from the data center. Memory is limited to a few GB to a few tens of GB, compute is far weaker than server GPUs, and the system usually serves only one user at a time. This makes small language models the natural choice. Models such as Phi-3-mini, Gemma 2 2B, and Llama 3.2 1B/3B are the best choices in resource-constrained environments.

    Quantization is also important for reducing memory usage. Many on-device deployments use 4-bit or 8-bit weights so the model can fit within the available memory. The KV cache adds another memory cost because it grows with sequence length, so long contexts can quickly become expensive on resource-constrained devices. Local runtimes such as llama.cpp, often with formats such as GGUF, are commonly used to run these quantized models efficiently.

    The optimization goal is also different from server deployment. Since a phone or laptop usually serves only one user, high-throughput techniques such as large batching are much less important. Instead, the priorities are interactive latency, low memory usage, and low power consumption. When a request exceeds what the device can handle efficiently, a hybrid architecture can run simpler or privacy-sensitive requests locally and route more demanding requests to a cloud model.

  3. How does post-training quantization compare to quantization-aware training?

    Post-training quantization (PTQ) applies quantization after a model has already been trained, usually using a small calibration set to estimate activation ranges or identify important weights. It is fast, often taking minutes to hours, and does not require access to the original training pipeline. Methods such as GPTQ, AWQ, and SmoothQuant are all examples of PTQ.

    Quantization-aware training (QAT) simulates quantization during training or fine-tuning so the model can adapt to quantization noise. This usually gives better accuracy than PTQ at the same bit width, especially at very low precision, but it is much more expensive because it requires updating model parameters with quantization in the loop.

    In practice, PTQ dominates deployment. Most teams serve pretrained models they did not originally train, so retraining with QAT is often impractical. Plus, PTQ methods at INT8 and even INT4 are often good enough for real systems, which makes them the default choice for inference optimization.

    A simple rule of thumb is to use PTQ when you need a fast, practical deployment path, and use QAT when you need maximum quality at aggressive low-bit settings and can afford additional training.
