Chapter 8. Data Preparation

The first step in training any large language model (LLM) is to prepare a massive, diverse, high-quality dataset called the pretraining dataset. Preparing this data is not a single-step process; it involves a complex pipeline of stages, including collection, cleaning, sampling, tokenization, and scheduling. This chapter walks through the practical stages involved in building such pretraining datasets, as illustrated in Figure 8-1.

Data Collection

The first step in data preparation is to gather a large amount of data from various sources. LLMs are typically trained on multi-terabyte-scale corpora drawn from a mixture of general, domain-specific, and structured data. Common data sources includes:

  • Web and Crawl Data (e.g., Common Crawl): Massive, unstructured and loosely filtered web text from open domains. While rich in linguistic diversity and volume, this data requires extensive cleaning and filtering due to its noisiness and uneven quality.

  • Curated Reference Texts (e.g., Wikipedia, Books): High-quality, edited text from encyclopedias, literature, and educational materials. These sources provide grammatical correctness, factual grounding, and structured exposition.

  • Code and Software Repositories (e.g., GitHub): Used in code-focused models, this data enables learning of syntax, logic, and API usage patterns across programming languages.

  • Scientific, Legal, and Financial Documents (e.g., arXiv, PubMed, SEC filings): Domain-specific corpora designed to inject subject-matter expertise into the model. These help in tasks like question answering, summarization, and reasoning in specialized verticals.

  • Forums, Dialogues, and Social Media (e.g., StackExchange, Reddit): Conversational and opinion-rich data that aids in training instruction-following and dialogue-capable models. These sources also enhance model alignment to informal or multi-turn interactions.

  • Multilingual and Cross-lingual Data (e.g., CC100, mC4, OSCAR): Non-English text datasets used to train multilingual or cross-lingual models. These datasets are typically crawled, segmented by language, and filtered based on language classification models.

The composition of training datasets can vary significantly across LLMs. This strongly affects their downstream performance and generalization ability. The pie charts in Figure 8-2 summarize the distribution of data sources used to train a few well-known LLMs. Each chart also includes the model size as a tuple of (model parameters, training tokens), displayed under the model name.

The choice of sources must also consider factors such as licensing terms, data privacy compliance, and domain alignment with intended applications. For example, models trained for healthcare or legal reasoning may require curated datasets sourced under specific regulatory constraints.

Data Cleaning

Large-scale raw data collected from the Web and other open sources are inherently noisy. Left unfiltered, these data can degrade model performance, introduce spurious correlations, encode harmful biases, and even lead to memorization of sensitive information. As a result, it is critical to apply data cleaning to ensure data quality, enhance model safety, mitigate bias, and promote generalization.

At scale, data cleaning pipelines combine rule-based heuristics, statistical methods, and machine learning classifiers. The specific pipeline used depends on the nature of the data, the scale of ingestion, and the intended use cases of the model. The data cleaning stage consists of the following filtering and de-duplication steps:

  1. Low-quality content filtering: The first layer of cleaning applies text normalization to remove structural noise from documents. This includes converting text to a consistent Unicode format, removing non-printable characters, fixing broken encodings, and stripping HTML or boilerplate tags.

  2. Toxicity and NSFW Filtering: To mitigate harmful or offensive content, pipelines apply keyword-based and classifier-based filters.

  3. Privacy filtering: Pipelines redact personally identifiable information (PII), such as emails, phone numbers, or usernames.

  4. Language filtering: Uses language identification tools like FastText or langdetect to ensure desired language coverage.

  5. Domain filtering: Excludes spammy or low-quality sources based on heuristics and domain reputation.

  6. Deduplication: Removes duplicate or near-duplicate content using hashing and similarity-based methods.

Do not confuse deduplication with decontamination. Deduplication removes repeated or near-repeated examples within the training corpus, reducing memorization and wasted training. Decontamination removes evaluation examples, or close variants of them, from the training data so benchmark scores reflect genuine generalization. A dataset can be well deduplicated and still contain benchmark contamination.

Synthetic Data Generation

Modern LLM pipelines increasingly supplement their pretraining corpora with synthetic data, that is, examples generated by existing models.

Synthetic data is especially useful when natural data is scarce, imbalanced, expensive to curate, or missing important capabilities such as instruction following, long-form reasoning, tool use, code explanations, or low-resource language coverage. In this sense, synthetic data is not a replacement for natural corpora, but rather a targeted augmentation strategy that helps fill gaps in the training mixture.

It is worth noting that synthetic data is more commonly used in supervised fine-tuning and post-training than in raw pretraining. However, it is increasingly being incorporated into pretraining pipelines as well, especially when the goal is to improve domain coverage, rebalance underrepresented skills, or expose the model to cleaner and more structured examples than those found in large web corpora.

There are several common motivations for using synthetic data. One is improving coverage of underrepresented domains. Some domains, such as healthcare, legal reasoning, finance, or enterprise workflows, may not appear in sufficient quantity or quality in general web data, and synthetic data can help increase coverage in such areas. Another is creating structured supervision signals. Synthetic examples can be generated as question-answer pairs, step-by-step explanations, summaries, or transformations, making the data easier for the model to learn from. Synthetic data is also useful for supporting low-resource languages and tasks. When natural corpora are limited, synthetic translation, paraphrasing, or reformulation can expand the available training material. Finally, synthetic data can help with improving data quality, since carefully generated examples are often cleaner, more consistent, and more targeted than noisy web text.

In practice, synthetic data is typically generated using one or more of the following strategies:

  1. Teacher-model generation: A stronger model is used to generate new examples for a weaker model to train on. This is common in distillation pipelines and self-instruction settings. The canonical recipes here are Self-Instruct (Wang et al., 2023), which bootstraps an instruction dataset from a small seed set of human-written tasks, and Alpaca (Taori et al., 2023), which used the same idea to instruction-tune Llama from a few thousand examples generated by a stronger model. Evol-Instruct (Xu et al., 2023, the WizardLM recipe) extends this by iteratively rewriting prompts to be more complex or constrained, producing a harder, more diverse instruction mix.

  2. Transformation-based synthesis: Existing documents are transformed into alternative forms, such as summaries, question-answer pairs, paraphrases, translations, or explanations.

  3. Reasoning-trace synthesis: For tasks with checkable answers (math, code, logic), a model generates step-by-step solutions that are kept only when a verifier confirms the final answer is correct. This reinforcement learning with verifiable rewards (RLVR) approach, popularized by DeepSeek-R1, produces large corpora of high-quality reasoning traces without human annotation. See Chapter 12 for how these traces are used to train reasoning models.

  4. Template- or rule-based generation: Synthetic examples are produced from structured schemas, templates, or simulators. This is useful when the desired output format is known in advance.

  5. Retrieval-grounded generation: A model generates examples based on trusted source documents, which can help constrain hallucinations and improve factual consistency.

Although synthetic data can be highly valuable, it also introduces important risks:

  • Error propagation: If the teacher model makes systematic mistakes, those mistakes may be reproduced at scale in the synthetic corpus.

  • Bias amplification: Synthetic generation can reinforce stylistic, cultural, or factual biases present in the generating model.

  • Reduced diversity: Overusing synthetic data may lead to a narrower distribution of language patterns compared to naturally occurring text.

  • Model collapse risk: If future models are trained too heavily on data generated by previous models, the training distribution may gradually lose richness and drift away from real-world language use. Shumailov et al. (2024, in Nature) demonstrated this failure mode: under recursive training on model output, the distribution narrows over generations, the tails are lost, and the model forgets rare but real patterns. Dohmatob et al. (2024) analyzed the same effect theoretically. The practical guardrail is to treat synthetic data as a supplement to a strong base of fresh human data, not a wholesale replacement.

For these reasons, synthetic data should be treated like any other corpus source: it must be filtered, evaluated, deduplicated, and carefully mixed with natural data rather than used blindly. In practice, teams often keep synthetic data as a relatively small but high-value portion of the overall training mixture, especially in pretraining.

A robust synthetic data pipeline usually includes several quality-control steps. First, the generated examples should be verified to ensure they are factually consistent with the source material, when a trusted source exists. Next, they should be filtered to remove toxic, nonsensical, low-diversity, or low-confidence outputs. The pipeline should also include deduplication, since repeated or near-duplicate examples can oversample narrow patterns and reduce diversity. In addition, mixture control is important: synthetic data should be blended with natural data in a controlled proportion rather than dominating the final corpus. Finally, provenance tracking should record which examples were synthetically generated, by which teacher model or pipeline, and under what conditions.

Example: Synthetic Data Generation Example

Suppose we are preparing a corpus for a finance-focused LLM. Raw web data may contain general financial news, but may lack enough high-quality examples of analyst-style question answering or document-grounded explanations.

One approach is to use a stronger model to generate synthetic question-answer pairs from trusted documents such as SEC filings, earnings reports, and investor letters. For example, a source paragraph from a filing can be transformed into:

  • a question-answer pair,

  • a concise summary,

  • a risk-factor explanation, or

  • a step-by-step reasoning example.

These generated examples are then filtered for quality, checked against the source text, and mixed back into the corpus at a controlled ratio. This allows the model to see more structured financial supervision without relying entirely on naturally occurring conversational finance data.

In summary, synthetic data generation is a useful extension of corpus preparation. It allows practitioners to augment scarce or noisy datasets with targeted examples, but it must be used carefully.

Corpus Sampling

After collecting and cleaning raw corpora, the next step is to decide in what proportion each data source should appear in the training data. Simply concatenating all data leads to dominance by large sources like Common Crawl. To prevent this imbalance, practitioners apply mixture-based sampling.

Common strategies include:

  • Fixed mixture weights sampling: Predefined ratios (e.g., 30% web, 20% books, 10% Wikipedia).

  • Temperature-based sampling: A softmax over source weights scaled by temperature to flatten or amplify differences.

A subtle but important point is that the size of a source in the raw pool is not the same as its sampling weight in the final mix. For GPT-3, filtered Common Crawl made up about 82% of the raw token pool but was deliberately down-weighted to 60% of the tokens the model actually trained on, while tiny high-quality sources were up-weighted far above their raw share: Wikipedia was under 1% of the raw pool but 3% of the training mix. LLaMA’s mix, by contrast, kept Common Crawl as the majority of trained tokens (about 67%), with 15% C4 and the remainder from code, books, and academic texts.

When discussing pretraining data, distinguish the raw data distribution from the training mixture. A dataset that contains most of the available tokens does not necessarily receive the same share of training tokens. Large, noisy sources may be down-weighted, while smaller, high-quality or strategically important sources may be sampled more often. The training mixture is a modeling decision, not simply a reflection of how much data was collected.

Tokenization

We covered tokenization in depth in Chapter 2. Here, we provide a practical overview to explain why it matters when working with pretrained models.

Tokenization is the process of converting raw text into smaller units called tokens. Before text is passed to a language model, the tokenizer maps it into a sequence of token IDs. Depending on the tokenization strategy, a token may correspond to a word, part of a word, a character, a byte, or a punctuation mark.

Modern LLMs typically use subword-level tokenization, which balances vocabulary size with flexibility. Instead of storing every possible word as a separate token, subword tokenizers can represent rare or unseen words by breaking them into smaller pieces. Common approaches include Byte-Pair Encoding (BPE), WordPiece, and Unigram LM. SentencePiece is a widely used tokenizer framework that supports subword tokenization methods such as BPE and Unigram.

The example below illustrates how the same sentence might be split under different tokenization strategies. The exact output depends on the specific tokenizer.

Example: Different Tokenization Strategies Example

  • Word-level: ['The','quick','brown','fox','jumps','over','the','lazy','dog']

  • Character-level: ['T','h','e',' ','q','u',...]

  • Subword (WordPiece): ['The','quick','bro','wn','fox','jump','s',...]

  • Subword (BPE): ['The','quick','b','row','n','fox','jump','s',...]

Each tokenizer has a fixed vocabulary, which is the set of tokens it knows how to represent. Every token in this vocabulary is assigned a unique integer called a token ID, and the model actually processes these IDs rather than the raw text. Tokenizers also reserve special tokens for control purposes, such as marking the beginning or end of a sequence, padding shorter inputs, or separating parts of a prompt. Figure 8-3 illustrates how a tokenizer converts input text into tokens and then maps each token to a numeric token ID using its vocabulary. The tokenizer’s vocabulary contains regular tokens, such as bro or fox, as well as special tokens, such as [PAD] and [CLS], which are reserved for control purposes.

It is usually easier to use a pretrained tokenizer such as BERT’s WordPiece, but custom tokenizers can yield better results for specialized domains.

Treat the tokenizer as part of the model, not as interchangeable preprocessing. Its vocabulary determines the model’s embedding and output spaces, while its tokenization efficiency affects sequence length, context usage, and inference cost. When comparing tokenizers, look beyond vocabulary size and examine fertility across the languages and domains the model must support. Once model training begins, the tokenizer and its token IDs are effectively fixed.

Data Scheduling

Once the data is collected, cleaned, sampled, and tokenized, the next key question is in what order should it be presented to the model during training. This process, called data scheduling, shown in Figure 8-4, shapes how the model learns over time. The order in which each data source is scheduled for training is called the data curriculum.

In practice, three strategies are common:

  • Static scheduling keeps all sources mixed in fixed ratios.

  • Dynamic scheduling adapts ratios based on model performance.

  • Curriculum-based scheduling introduces simpler or cleaner data first and noisier data later.

Practitioners also choose between document-level and token-level scheduling depending on the desired balance between context preservation and diversity.

Summary

Preparing data for LLM pretraining involves much more than collecting a large corpus. The pipeline includes selecting diverse data sources, cleaning and deduplicating noisy content, incorporating synthetic data where useful, controlling the mixture of different sources, choosing and training a tokenizer, and scheduling data throughout training.

Each stage introduces trade-offs. Aggressive filtering can improve quality but reduce diversity; oversampling can strengthen important domains but increase memorization risk; synthetic data can expand coverage but may propagate errors or reduce diversity; and tokenizer choices affect vocabulary size, sequence length, multilingual efficiency, and context usage. Data scheduling further determines how these sources are presented to the model over the course of training.

Together, these decisions shape what the model learns, how efficiently it learns, and how well it generalizes. The interview questions that follow examine these design choices and their practical trade-offs in greater depth.

Interview Questions and Answers

Thread: Building a Pretraining Corpus

  1. Where does the data for pretraining a large language model actually come from?

    Most pretraining corpora draw from several broad categories:

    • Web crawls: Common Crawl is the dominant source, providing petabytes of raw HTML collected from the open web. It is large and diverse but noisy, requiring heavy filtering. Heavily filtered derivatives have become standard starting points, including FineWeb, DCLM, and Nemotron-CC, which apply model-based quality classifiers to extract higher-quality subsets from raw Common Crawl.

    • Curated text: Wikipedia, books such as Project Gutenberg and Books3, and academic papers such as arXiv and Semantic Scholar offer high-quality, well-structured prose.

    • Code repositories: GitHub, GitLab, and Stack Overflow supply programming-language data that improves reasoning and tool-use capabilities.

    • Conversational data: Forums, Q&A sites such as StackExchange, and dialogue corpora help the model learn interactive language patterns.

    • Multilingual sources: Parallel corpora and non-English web pages extend coverage beyond English.

    • Synthetic data: Increasingly, teams generate textbook-quality or instruction-following examples from stronger models to fill quality gaps. Phi-3, for instance, was trained on a mix of heavily filtered web data and model-generated synthetic content.

    Real-world corpora combine these sources at carefully chosen ratios. LLaMA’s training mix, for example, included 67% Common Crawl, 15% C4, 4.5% GitHub, 4.5% Wikipedia, 4.5% books, 2.5% ArXiv, and 2% StackExchange.

  2. When should you use synthetic data for LLM training, and what are the risks?

    Synthetic data is useful when high-quality natural data is scarce, when particular domains or languages are underrepresented, or when we want to generate targeted examples for capabilities such as reasoning, instruction following, or tool use.

    The main risks are error propagation, where mistakes from the teacher model are reproduced at scale; bias amplification; reduced diversity; and, when models are repeatedly trained on model-generated data, model collapse. For this reason, synthetic data should generally supplement rather than blindly replace natural data.

    A production synthetic-data pipeline should include verification, quality filtering, deduplication, mixture control, and provenance tracking so that generated examples can be traced back to their source and generation process.

  3. Why does the mixture ratio between data sources matter?

    Naively concatenating and shuffling all datasets lets large, noisy sources like Common Crawl dominate the training distribution. Smaller but higher-quality datasets, such as Wikipedia, books, and curated code, get drowned out. The result is that the model underperforms on tasks requiring precise, structured, or domain-specific knowledge.

    Controlling the mixture ratio ensures the model sees enough high-quality data to learn clean linguistic patterns while still benefiting from the scale and diversity of web data. Getting this ratio wrong can bias the model toward low-quality patterns or, conversely, leave it undertrained on broad language use.

  4. How does temperature sampling control dataset balance during pretraining?

    Each dataset i starts with a natural weight pi proportional to its token count:

    pi=Ni∑jNj

    where Ni is the number of tokens in dataset i. A temperature parameter T reshapes these weights:

    pi’=pi1/T∑jpj1/T

    When T>1, the distribution flattens, so smaller datasets get sampled more often relative to their natural proportion. When T<1, dominant datasets grow even more dominant. At T=1, sampling matches the natural proportions exactly. As T→∞, every dataset gets equal weight regardless of size.

    Multilingual models commonly use temperature sampling to upweight low-resource languages. XLM-R, for example, raises each language’s probability to the power α=0.3. That exponent plays the role of 1/T in the formula above, so it corresponds to T≈3.3, aggressively upweighting low-resource languages relative to their natural proportions.

  5. Can you oversample a small dataset to boost its influence? What are the risks?

    Yes. High-value datasets like curated code or Wikipedia are often oversampled by assigning them higher sampling weights or duplicating their entries in the data stream. Some LLaMA training configurations sample Wikipedia and books multiple times per epoch.

    The risk is overfitting and memorization. When the model sees the same documents repeatedly, it may memorize specific sequences rather than learning generalizable patterns. A common heuristic is that if a dataset would be seen more than 4 to 5 times during training, further oversampling offers diminishing returns and increasing memorization risk.

  6. What is data contamination, and why is it a serious concern?

    Data contamination occurs when evaluation benchmark examples, or close paraphrases, appear in the training data. Because web-scale corpora are so large, benchmark datasets like MMLU, GSM8K, or HumanEval can accidentally end up in the pretraining set. When this happens, the model effectively memorizes test answers, inflating benchmark scores without genuine capability.

    Detection methods include n-gram overlap analysis, checking whether long n-grams from benchmarks appear verbatim in training data, embedding similarity search, and membership inference tests. Teams building open datasets like The Pile, RefinedWeb, and FineWeb explicitly remove known benchmark datasets from the corpus. GPT-4’s technical report and LLaMA’s documentation both discuss contamination analysis as a standard part of the evaluation pipeline.

Thread: Cleaning and Filtering at Scale

  1. Walk me through a typical cleaning pipeline for web-crawled data.

    A standard pipeline processes data in roughly this order:

    1. Text extraction: Raw HTML is converted to plain text using tools like Trafilatura or Resiliparse, stripping navigation menus, ads, and boilerplate.

    2. Language identification: A language classifier such as fastText removes non-target-language documents. Multilingual corpora route documents to language-specific streams instead.

    3. URL and domain filtering: Blocklists remove known spam, adult, or low-quality domains.

    4. Heuristic rules: Rule-based filters catch documents that are too short, have abnormal punctuation ratios, excessive repetition, or high symbol density. C4’s heuristics, such as removing lines without terminal punctuation, pages containing too many bad words, and deduplicating by 3-sentence spans, are widely reused.

    5. Deduplication: Exact and near-duplicate documents are removed.

    6. Quality classification: A trained classifier or perplexity score separates high-quality pages from low-quality ones.

    7. PII and toxicity removal: Regex patterns, NER models, and toxicity classifiers handle sensitive content.

    Modern pipelines like FineWeb and Dolma apply these steps at massive scale, processing hundreds of billions of documents.

  2. Why is deduplication so important, and how is it implemented at scale?

    Duplicate documents are surprisingly common in web corpora. An analysis of large web datasets, WIMBD, 2023, found that roughly 50% of documents in RedPajama and LAION-2B-en were duplicates. Without deduplication, the model memorizes repeated content instead of learning general patterns, and evaluation integrity suffers if test data appears in the training set.

    At scale, deduplication uses multiple techniques in sequence:

    • Exact deduplication (hashing): Each document is hashed, for example with SHA-256 or MD5, and identical hashes are removed. This is fast but only catches character-for-character duplicates.

    • Near-deduplication (MinHash + LSH): Documents are converted into overlapping k-word shingles, and MinHash signatures approximate their Jaccard similarity. Locality-Sensitive Hashing, or LSH, groups similar signatures efficiently. Document pairs exceeding a similarity threshold, for example Jaccard >0.8, are flagged as near-duplicates. This catches reformatted, lightly edited, or scraped-and-reposted content.

    • Substring deduplication: Suffix arrays detect repeated multi-sentence passages shared across otherwise distinct documents. This is more expensive but catches paragraph-level plagiarism that document-level methods miss.

    Production pipelines typically layer exact hashing first, since it is cheapest, and then MinHash + LSH. The Pile, RefinedWeb, and FineWeb all use aggressive deduplication as a core quality step.

  3. How do quality classifiers and perplexity filtering work?

    Not all web pages that survive heuristic filters are actually useful for training. Quality classifiers add a second, more nuanced layer of filtering.

    Classifier-based filtering trains a binary classifier to distinguish high-quality text, such as Wikipedia, books, and curated references, from low-quality web text. Documents scoring below a confidence threshold are discarded. FineWeb-Edu uses this approach, training an educational quality classifier on annotated samples. The challenge is defining “quality”: the classifier inherits whatever biases exist in the reference corpus.

    Perplexity filtering scores each document using a small language model trained on high-quality text. CCNet pioneered this approach by training a KenLM n-gram model on Wikipedia and keeping only documents with low perplexity, meaning documents whose language resembles Wikipedia-quality prose. Documents with very high perplexity, which are incoherent or off-topic, are removed. Documents with very low perplexity, which are often boilerplate or repetitive, may also be filtered. Research has shown that perplexity-based pruning can match or exceed the performance of rule-based heuristics, sometimes allowing models to train on as little as 30% of the original corpus with no quality loss.

  4. How are PII and sensitive data handled during data preparation?

    Personally Identifiable Information, or PII, such as names, emails, phone numbers, and addresses, must be removed to protect privacy and comply with regulations like GDPR. Common removal methods include:

    • Regex filters: Pattern-match and redact emails, phone numbers, Social Security numbers, and credit card numbers.

    • NER models: Detect person names, addresses, and organizations that regex cannot catch.

    • Heuristic scrubbing: Replace detected entities with placeholder tokens such as [NAME] or [EMAIL].

    Beyond PII, some teams apply differential privacy during training to limit the model’s ability to memorize and regurgitate individual data points. Encrypted storage and access controls protect the corpus itself.

  5. How is toxicity and NSFW content filtered?

    Three main approaches are often combined:

    • Keyword-based filtering: Predefined lists of profane, explicit, or offensive terms flag content for removal. This is fast but brittle and prone to false negatives on subtle toxicity.

    • Toxicity classifiers: Models like Perspective API or custom classifiers assign toxicity scores. Documents exceeding a threshold are filtered. This is more flexible than keywords but may introduce false positives or bias against certain dialects and communities.

    • Regex and URL filtering: Removes structured adult content such as explicit URLs and HTML tags associated with NSFW material.

    Aggressive toxicity filtering improves model safety but creates a tension: it can disproportionately remove content from marginalized communities whose language patterns overlap with the classifier’s notion of “toxic.” Calibrating the threshold is an active area of research.

  6. Can aggressive filtering actually hurt model quality?

    Yes. Over-filtering removes rare, diverse, or unconventional text that helps the model generalize to a wider range of inputs. It can erase useful examples from underrepresented domains, dialects, or communities, narrowing the model’s linguistic range. Research on data pruning has shown that quality filtering follows diminishing returns: beyond a certain aggressiveness threshold, the model starts losing capability rather than gaining it.

    The practical takeaway is to balance cleanliness with coverage. Filter the clearly harmful and clearly useless, but preserve diversity in the middle.

Thread: Data Scheduling and Curriculum

  1. What are the main data scheduling strategies for LLM pretraining?

    Three strategies dominate:

    • Static scheduling: A fixed mixture ratio is defined before training and held constant throughout, for example 40% Common Crawl, 30% Wikipedia, and 30% books at every batch. This is simple to implement and reproduce.

    • Curriculum scheduling: High-quality or “easier” data, such as Wikipedia and books, is presented first to bootstrap stable representations. Noisier or harder data, such as Common Crawl and domain-specific corpora, is introduced gradually. Some instruction-tuning pipelines apply curriculum-like strategies at the task level, starting with simpler tasks before progressing to harder ones.

    • Dynamic scheduling: Sampling weights are updated during training based on model signals like per-domain loss. Domains where the model underperforms get upweighted automatically, creating a feedback-driven curriculum. DoReMi (Xie et al., 2023) uses group distributionally robust optimization to learn domain weights automatically with a small proxy model, then trains the full model with those weights.

    The key distinction is that curriculum scheduling is predetermined based on external criteria such as data quality or estimated difficulty, while dynamic scheduling adapts in real time based on the model’s own performance.

  2. What is data annealing, and when is it used?

    Data annealing refers to a final training phase where the data mixture shifts toward high-quality, curated sources. After the model has trained on a broad, diverse corpus for most of the run, the last few percent of training steps upweight clean data such as Wikipedia, textbooks, and high-quality code, and sometimes reduce the learning rate simultaneously.

    The motivation is analogous to simulated annealing in optimization: broad exploration early, fine refinement late. LLaMA 3 used a two-phase schedule where the final phase upsampled high-quality data. Empirically, annealing improves benchmark scores without requiring a separate fine-tuning stage.

  3. How does data scheduling relate to multi-phase training?

    Multi-phase training applies distinct scheduling strategies at each phase. Pretraining might use a broad mixture, a mid-training phase might upweight domain-specific data, and a final annealing phase might shift to curated high-quality sources. After pretraining, supervised fine-tuning and alignment phases introduce instruction-following and preference data with entirely different distributions.

    Each phase transition represents a deliberate change in the data schedule, shaping the model’s capabilities in a specific direction. Scheduling across these phases is just as important as scheduling within any single phase.

Thread: Tokenization

  1. What are the three main levels of tokenization, and what are their tradeoffs?

    • Word-level: Splits on spaces and punctuation. Simple and intuitive, but produces enormous vocabularies. Transformer-XL used 267K tokens. It also cannot handle out-of-vocabulary words. Morphological variants like “book” and “books” get entirely separate representations despite sharing meaning.

    • Character-level: Splits into individual characters. This eliminates OOV problems entirely and handles misspellings, rare words, and non-Latin scripts gracefully. The downside is that sequences become very long, one word may span 5 to 10 tokens, increasing computational cost due to attention’s quadratic scaling. Individual characters also carry limited semantic information in alphabetic languages.

    • Subword-level: Splits into frequently occurring subword units, such as prefixes, suffixes, and common roots. This balances the two extremes: manageable vocabulary size, typically 32K to 100K tokens, no OOV problem because rare words decompose into known subwords, and reasonable sequence lengths. Nearly all modern LLMs use subword tokenization.

  2. Walk me through how BPE (Byte Pair Encoding) builds its vocabulary.

    BPE has two phases: vocabulary learning and text encoding.

    Vocabulary learning starts from individual characters and iteratively merges the most frequent adjacent pair:

    1. Initialize: Split the training corpus into characters. A special boundary marker, for example _, is prepended to each word to mark word boundaries. For the corpus “low lower lowest,” the initial tokens are [_l, o, w, _l, o, w, e, r, _l, o, w, e, s, t] and the vocabulary is {_l, o, w, e, r, s, t}.

    2. Count pairs: Tally every adjacent token pair. Here (_l, o): 3, (o, w): 3, (w, e): 2, and so on.

    3. Merge the top pair: Replace all occurrences of the most frequent pair with a single new token. Merging (_l, o) yields _lo, which is added to the vocabulary. Tokens become [_lo, w, _lo, w, e, r, _lo, w, e, s, t].

    4. Repeat until the target vocabulary size is reached. The next merge would combine (_lo, w) into _low with frequency 3, then (_low, e) into _lowe with frequency 2, then (_lowe, r) into _lower, and so on.

    Text encoding applies the learned merge rules greedily: split the input into characters, then apply merges in the order they were learned until no more apply.

  3. How does WordPiece differ from BPE?

    Both are iterative merge-based algorithms, but they choose which pair to merge differently:

    • BPE merges the most frequent pair.

    • WordPiece merges the pair that maximizes the likelihood of the training data under a unigram language model. Frequency matters, but so does how much the merge improves the overall model fit.

      WordPiece also marks continuation subwords with a ## prefix, for example “playing” → [play, ##ing], making it easy to reconstruct the original word. BERT and DistilBERT use WordPiece.

    When encountering an unknown word at inference, the WordPiece tokenizer greedily matches the longest vocabulary entry from left to right, then continues with the remainder. If no valid segmentation exists at all, which is rare with a well-trained vocabulary, it falls back to <unk>.

  4. What is the Unigram Language Model approach to tokenization?

    Unlike BPE and WordPiece, which build the vocabulary bottom-up by merging, the Unigram model works top-down by pruning.

    It starts with a large initial vocabulary, including all characters plus frequent substrings, and iteratively removes tokens whose removal causes the smallest increase in the corpus likelihood under a unigram language model. At each step, the algorithm recomputes the probability of each token and prunes the least useful ones until the target vocabulary size is reached.

    During encoding, the Viterbi algorithm finds the single most probable segmentation of each word. Unlike BPE, which applies merge rules in a fixed order, the Unigram model considers all possible segmentations and picks the one with the highest joint probability. SentencePiece also supports a sampling mode that randomly samples from multiple segmentations weighted by probability, which serves as a regularization technique during training. XLNet and ALBERT use Unigram-based tokenization, often through SentencePiece.

  5. What is byte-level BPE, and why do GPT-2 and later models use it?

    Standard BPE operates on Unicode characters, which means the base vocabulary must include every Unicode character the model might encounter. Byte-level BPE instead treats raw bytes, 256 possible values, as the base alphabet. Any UTF-8 encoded text can be represented as a sequence of bytes, so the tokenizer can handle any language, emoji, or symbol without ever producing an <unk> token.

    GPT-2 introduced this approach, and GPT-3, GPT-4, and LLaMA all use byte-level BPE. The tradeoff is that rare characters and non-Latin scripts may require more bytes, and thus more tokens, to represent, increasing sequence length. But the guarantee of universal coverage, with no special handling needed for new languages or scripts, makes it the dominant choice for general-purpose LLMs.

  6. What makes SentencePiece different from other tokenizers?

    Most tokenizers assume pre-tokenized input: text is first split on whitespace, then subword algorithms run within each word. SentencePiece operates directly on raw text, treating the input as a sequence of Unicode characters, or bytes, with no whitespace pre-processing. Spaces are treated as regular characters, often replaced by a special symbol like _ (U+2581).

    This design makes SentencePiece language-agnostic. Languages without clear word boundaries, such as Chinese, Japanese, and Thai, work without any special pre-processing. SentencePiece supports both BPE and Unigram model algorithms internally.

    Models like T5, ALBERT, XLNet, and LLaMA use SentencePiece. It also provides a self-contained training and encoding pipeline: you feed it raw text, it learns a vocabulary, and it produces a model file that handles both tokenization and detokenization.

  7. How do you choose the right vocabulary size?

    Vocabulary size involves a three-way tension:

    • Too small, for example under 16K: common words get split into many subword tokens, inflating sequence lengths and increasing compute cost. The model may struggle to learn coherent representations from overly fragmented input.

    • Too large, for example over 200K: the embedding matrix grows proportionally, V×d, where V is vocabulary size and d is embedding dimension, consuming memory and adding parameters. Rare tokens in the vocabulary see too few training examples to learn useful embeddings.

    • Sweet spot: most modern LLMs land between 32K and 128K tokens. GPT-2 uses 50,257; LLaMA uses 32,000; LLaMA 3 expanded to 128,256; GPT-4 uses approximately 100K.

    Larger vocabularies tend to improve throughput by compressing text into fewer tokens, since each token carries more information, but only if the model is large enough to support the bigger embedding table. For smaller models, a compact vocabulary is more efficient.

  8. How do you train a tokenizer from scratch?

    Training a tokenizer means learning a vocabulary from a representative text corpus. With SentencePiece, the typical workflow is:

    1. Collect a representative sample: A subset of the training corpus, typically a few billion tokens, covering all target languages and domains.

    2. Choose an algorithm: BPE or Unigram, with a target vocabulary size.

    3. Train: SentencePiece processes the raw text, learns merge rules for BPE or prunes the vocabulary for Unigram, and outputs a model file.

    4. Add special tokens: Reserve IDs for <bos>, <eos>, <pad>, <unk>, and any task-specific tokens.

    5. Validate: Check fertility, meaning tokens per word, across languages, verify no <unk> tokens appear on representative inputs, and spot-check that common words are single tokens.

    The tokenizer is trained once before model training begins and stays frozen throughout. Changing the tokenizer mid-training would invalidate all learned embeddings.

  9. What is tokenizer fertility, and why does it matter for multilingual models?

    Fertility measures how many tokens a tokenizer produces per word, or per character, in a given language. A tokenizer trained predominantly on English text might tokenize English at 1.2 tokens per word but Korean at 3.5 tokens per word, meaning Korean text consumes roughly three times more of the context window for the same amount of information.

    High fertility in a language means longer sequences, higher compute cost, and less text fitting in the context window. Multilingual models address this by training the tokenizer on a balanced multilingual corpus, ensuring reasonable fertility across all target languages. Byte-level BPE helps as a fallback, since any script is representable, but without multilingual training data in the vocabulary-building phase, non-English fertility can still be poor.

  10. What are special tokens, and how does the tokenizer handle them?

    Special tokens are reserved entries in the vocabulary that carry structural meaning rather than linguistic content:

    • `[BOS]` / <s>: Beginning of sequence. Signals the start of generation.

    • `[EOS]` / </s>: End of sequence. Tells the model to stop generating.

    • `[PAD]`: Padding token for batching variable-length sequences.

    • `[MASK]`: Used in masked language modeling, BERT-style, to indicate tokens the model must predict.

    • `[SEP]`: Separates segments, for example a question from context in a QA task.

    • `[CLS]`: Classification token in BERT whose output embedding represents the full sequence.

    These tokens are predefined with fixed IDs, for example [PAD] → 0 and [CLS] → 101 in BERT’s vocabulary. The tokenizer inserts them automatically based on the task format, such as [CLS] sentence1 [SEP] sentence2 [SEP] for sentence-pair inputs.

  11. How does tokenization affect the effective context window?

    A transformer’s context window is measured in tokens, not words or characters. Finer-grained tokenization, such as character-level or a small subword vocabulary, produces more tokens per word, which means less actual text fits in the window. Coarser tokenization, such as a large vocabulary or word-level tokenization, produces fewer tokens but has other drawbacks like OOV issues and large embedding tables.

    Efficient tokenization directly determines how much information the model can process in a single forward pass. A tokenizer that compresses English at 1.1 tokens per word lets the model see nearly twice as much text as one running at 2.0 tokens per word, given the same context length.
