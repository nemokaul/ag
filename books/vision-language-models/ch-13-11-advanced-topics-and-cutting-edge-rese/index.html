Chapter 11. Advanced Topics and Cutting-Edge Research

We began this journey by reflecting on our nature as social and visual beings: creatures who evolved to perceive the world through sight and coordinate through language. Perception and communication alone were never enough for survival; our ancestors had to act on what they saw and discussed: they had to hunt, build, navigate, and collaborate to shape their environment.

As vision language models (VLMs) mature beyond passive understanding, we face a parallel challenge: enabling AI systems to not just see and speak but to do. This chapter explores that challenge in two domains that share the same core idea. In the digital world, agents use VLMs to reason, plan, and execute actions through tools and graphical interfaces: clicking buttons, filling forms, and writing code. In the physical world, vision-language-action (VLA) models take the same see-and-understand capabilities and wire them to robot motors: picking objects, folding laundry, and pouring coffee—very similar architectural patterns but different deployments. You will start by learning about digital agents then move on to physical ones.

Learning Objective

Understand how VLMs extend from passive understanding to taking action in digital interfaces and physical environments.

Agentic Vision Language Models

As VLMs developed better reasoning capabilities, another use case emerged: they can be agents too! Use cases keep growing over time. A very popular one is computer use agents that operate solely by taking screenshots. You will actually explore that one in detail. Before that, every bar discussion I had about agents started with a misalignment on what an agent is. We discussed, and, toward the middle, we realized we had different understandings of what an agent is. Let’s save you a discussion and start by defining an agent.

Introduction to Agents

Language models are incredibly capable, but answering questions is not the same as getting things done. Even when using modern coding editors, we consistently give the model the green and red light, which adds friction. To actually automate things, we need to give LLMs agency: the ability to decide and execute actions in the outside world.

A useful working definition for agents comes from Simon Willison: an agent is a large language model (LLM) running in a loop, with access to tools. The loop is the key ingredient: the model reasons about what to do, calls a tool, inspects the result, and decides whether to continue or stop. That loop can be as simple as a single function call or as complex as a multihour research workflow. Agency is not binary but is a spectrum, and agents come in many shapes. How much agency you give a model is a design choice. Table 11-1 shows the spectrum from least to most autonomy.

Table 11-1. The agency spectrum: from a single tool dispatch to a code-writing agent; the first two levels are straightforward and are often the right choice for most of the applications
LevelWhat the LLM doesExample

Tool selection

Picks which tool or function to invoke, given the user’s intent.

A classifier routes “translate this” to a translation API and “summarize this” to a summarization prompt.

Tool calling

Calls a tool with structured arguments and returns its output.

An LLM calls a weather API with {'city':'Bern'} and returns the forecast.

Multistep loop (ReAct)

Think -> act -> observe write to memory -> repeat until done.

An agent researches vendors, compares pricing, drafts an email, and creates calendar holds.

The ReAct loop

The multistep loop in ReAct is where things get interesting. Let’s break it down step by step (or see the process in Figure 11-1):

  1. The user asks a question or gives a command to the agent.

  2. The agent reasons around the query and makes an action plan. This plan can include which tools to call with which inputs, etc.

  3. Steps in the plan are executed.

  4. The agent observes the results of the execution steps and evaluates if it achieved its goal. If it is, it extracts the answer and returns it. If not, it writes the facts to the memory, and the think -> act -> observe loop continues.

Do all practical use cases need an agent? No. As you saw in Table 11-1, there are cases where the VLM/LLM acting as a router or executing tools for you gets the job done. For example, if you want to build an agent that decides which ImageMagick command line to use to recover an old photo with low contrast, a VLM with tool calling is more than enough.

Let’s look at a scenario that actually needs an agent. Imagine you are evaluating cloud GPU providers for your team. You ask your agent: “Research the top 3 GPU cloud providers, compare their H100 pricing and availability, check our current monthly spend in our billing dashboard, draft a recommendation email to the team, and create a task in our project tracker to revisit in 30 days.”

No single tool call solves this. The agent has to:

  • Search the web for current GPU pricing (information changes weekly)

  • Navigate each provider’s dashboard or docs to extract comparable numbers

  • Open your internal billing tool to check current spend

  • Synthesize findings into a structured comparison and draft the email

  • Create a calendar reminder or task, and only then return a final answer

Here’s what can go wrong along the way and why you need an agent loop:

  • A provider’s pricing page requires clicking through a calculator: the agent writes the result to memory, adjusts its approach, and tries a different route.

  • The provider’s website might be protected by a CAPTCHA or similar mechanism, making it more difficult for the VLM to continue its task.

  • Your billing dashboard has a pop-up or two-factor prompt: this is where deterministic fallbacks matter. If you have an API for billing data, use it. Don’t ask the agent to fight a crazy login flow.

  • The draft email contains a hallucinated number: a good agent setup would include a verification step (recheck the source) before sending.

The first, second, and fourth obstacles require open-ended reasoning that benefits from an agent loop. The third one is better handled deterministically through an API. At scale, always implement deterministic parts yourself and give the agent the open-ended parts.

Evaluating agents

If you are going to ship an agent, you need to know whether it actually works. This is part of what you saw as “Observation” and “Is this the final answer?” in Figure 11-1. What do we actually check there?

Step-level grounding

Did the agent take the right action at each step? For a computer-use agent, this means: did it click the correct element? Did it type the correct text into the correct field? You can measure this by logging every ActionStep and comparing against a ground-truth trace. This is where localization models (like Holo2) and agentic models (like ScaleCUA) diverge: localization accuracy is easy to benchmark with coordinate error, while agentic step correctness requires semantic comparison.

Task-level success

Did the agent finish the job? This is harder because “finished” can be ambiguous. Did the email actually get drafted with the right content? Did the booking go through? Task-level evaluation typically requires either human judgment or verifiable end states (a file was created, a form was submitted, a value appeared in a database).

A few patterns jump out, right?

So why do we use smolagents in this book? It is not the option with the most green ticks in the table! Three reasons:

  • They are small and readable. The entire library is compact enough to read the source in an afternoon. When something breaks in an agent loop (and it will), you want to understand what is happening under the hood, not fight layers of abstraction.

  • Multimodal inputs are first-class citizens. Images flow naturally through the agent loop via observations_images on every ActionStep. This is essential for the computer use agents we will build later in this chapter, where the agent needs to see a screenshot at every step. Other frameworks support multimodal inputs, but smolagents was designed to work with them.

  • Its CodeAgent writes and executes Python as its action mechanism rather than outputting JSON tool calls; instead of being limited to predefined tool signatures, the agent can compose tools, perform arithmetic, parse data, and handle edge cases on the fly.

If you are building a production pipeline with complex branching logic, approval gates, or retrieval-heavy workflows, look at the alternatives in Table 11-2. We use smolagents here because it is the best tool for learning how agents work and for building vision-language agents specifically.

First toy example

Let’s build a tiny agent and watch what happens inside the loop. Smolagents comes with two agent classes, both based on a common MultiStepAgent that contains the ReAct loop:

  • CodeAgent writes and executes Python to perform actions.

  • ToolCallingAgent outputs JSON to call tools instead, which is the more traditional approach you will find in other frameworks.

Both need tools: smolagents ships with WebSearchTool, PythonInterpreterTool, and a tool base class for building your own.

Let’s write a trivial tool and run it. Pay attention to the description field: this is what the LLM reads to decide when and how to call your tool:

from smolagents import Tool, CodeAgent, InferenceClientModel

class AdditionTool(Tool):
name = "addition_tool"
description = "Adds two numbers together"
inputs = {
"first_number": {
"type": "integer",
"description": "first number to add"
},
"second_number": {
"type": "integer",
"description": "second number to add"
}
}
output_type = "integer"

def forward(self, first_number, second_number):
return first_number + second_number

model = InferenceClientModel()
agent = CodeAgent(tools=[AdditionTool()], model=model)
result = agent.run("What is 41 plus 1?")

# Let's inspect what happened inside the loop

for step in agent.memory.steps:
print(f"{type(step).name}: {step}")

The output reveals the full lifecycle of an agent run:

TaskStep: "What is 41 plus 1?"
ActionStep: thought="I need to add 41 and 1" | tool_calls=[addition_tool(41, 1)] 
| observations="42"
FinalAnswerStep: 42

Those four classes—TaskStep, PlanningStep, ActionStep, and FinalAnswerStep—are the memory objects that track every agent run. They map directly to the ReAct loop from Figure 11-1:

  • TaskStep stores the user’s initial instruction (and any input images—this is where screenshots enter the loop for computer-use agents).

  • PlanningStep stores a high-level plan before execution when planning is enabled. Our toy example skipped it, but for complex tasks (“research three vendors and draft an email”), planning helps the agent stay on track.

  • ActionStep is the core of the loop. Each cycle of think → act → observe produces one ActionStep containing the LLM’s reasoning (model_output), which tools were called (tool_calls), what came back as text (observations), and what came back as images (observations_images). That last field is how screenshots flow through the loop in computer-use agents—you will see this in “Computer Use Agents”.

  • FinalAnswerStep stores the return value when the agent decides it is done.

Now that you have seen the lifecycle in action, let’s look at the different ways to connect models and external capabilities to your agent.

Leveraging Hugging Face Spaces as tools

Your tools don’t have to be hand-written functions. One of smolagents’ nicest tricks is turning any Hugging Face Space into a callable tool with a single line of code. Tool.from_space() wraps any of them as a tool your agent can call midloop.

For example, let’s give our agent access to FLUX.1-schnell, a fast image generation model:

from smolagents import CodeAgent, Tool

image_gen_tool = Tool.from_space(
space_id="black-forest-labs/FLUX.1-dev",
name="image_generator",
description="Generates an image following your prompt. Returns the image.")
agent = CodeAgent(tools=[image_gen_tool], model=model)
agent.run("Generate an image of a futuristic city with flying cars at sunset")

You can see in Figure 11-2 what the agent got for you!

The agent writes code that calls image_generator(prompt="..."), receives the generated image as an observations_images entry in its ActionStep, and can then reason about it or return it as the final answer. The same pattern works for any space: swap in a speech-to-text space, and your agent can transcribe audio, swap in a document OCR Space, and read PDFs. The key insight is that models become tools, so your agent doesn’t need to do everything itself but just needs to know which specialist to call.

Connecting your model

You may have noticed we have been writing model=model in every snippet without explaining where it comes from. That’s because smolagents is model-agnostic: it doesn’t care whether your LLM runs on your laptop, on a rented GPU, or behind an API. You just need to pick the right wrapper class for your setup.

For local models, smolagents offers three options depending on your hardware:

TransformersModel

Runs models locally via the transformers library, e.g., Tran⁠sfo⁠rmers​Mod⁠el(model_id="Qwen/Qwen2.5-Coder-32B-Instruct", device="cuda")

MLXModel

Optimized for Apple Silicon (M1/M2/M3/M4) using the mlx library, e.g. MLX​Mod⁠el(mo⁠del_id="mlx-community/Llama-3.2-3B-Instruct-4bit")

VLLMModel

Connects to a vLLM server, which is useful when you want to serve a model once and share it across multiple agents or applications.

For hosted models, you have three more:

InferenceClientModel

Connects to Hugging Face Inference Providers, a router that gives you access to models served by multiple providers. Hugging Face also offers Inference Endpoints, where you rent a dedicated instance for any model. This class works with both, e.g., InferenceClientModel(model_id="moonshotai/Kimi-K2-Thinking").

OpenAIServerModel

Connects to OpenAI’s API or any OpenAI-compatible endpoint.

LiteLLMModel

A wrapper around LiteLLM that lets you call almost any API (Anthropic, Gemini, Bedrock, Mistral, etc.) through a unified interface.

In practice, InferenceClientModel is the fastest way to get started: it doesn’t require a beefy computer and third-party APIs. All it needs is a Hugging Face token. Here is a complete working example:

from smolagents import CodeAgent, InferenceClientModel, DuckDuckGoSearchTool
model = InferenceClientModel()
agent = CodeAgent(
	tools=[DuckDuckGoSearchTool()],
	model=model
	)
result = agent.run("What is the current weather in Paris?")
print(result)

If you look at the output, you can see that while writing the book, we enjoyed the perfect weather to do that (hopefully you enjoy good weather while reading!):

Now that you know how to wire up an agent with tools and models, let’s look at the most visual use case: agents that operate computers by looking at the screen, just like you do.

Computer Use Agents

Automating computer tasks has always been either hard-coded with automation tools like Playwright or done through LLMs parsing HTML code behind websites. This is very brittle in many ways: websites can have images that can never be parsed to pass to LLM, the hardcoded website automations break when website layouts change and many other failures occur. Luckily, we can also use VLMs to operate over graphical user interfaces (GUIs).

Industry Snapshot: Computer Use Agents in Early 2026

Computer use agents (CUAs) have moved from research demos to products fast. By early 2026, three flavors coexist.

API and tool-calling agents interact with software through structured APIs and function calls. This is the most reliable approach: no screenshots, no pixel coordinates, just JSON in and JSON out. Most production agent systems (including enterprise automation) work this way.

Screenshot-based CUAs from commercial providers, such as Anthropic’s computer use tools and OpenAI’s Operator, use VLMs to observe and act on GUIs from screenshots. These are useful when APIs don’t exist, but they are slower and more brittle than API-based approaches.

Open-source research CUAs, such as ScaleCUA, Fara-7B, and Jan-v2-VL, offer the same screenshot-based paradigm with open weights you can fine-tune and deploy on your own infrastructure.

This section focuses on the open models you can run and modify yourself.

There are two types of VLMs used for agentic workflows:

  • Some models can spot where to click and return coordinates. These models come in different shapes, too: some are lightweight object detection models trained on screenshots or VLMs trained on the task. A good example of object detection models is UI-DETR-v1 by Racine. Most models employ VLMs, though. A good example is the Holo series of models by H-Company.

  • Reasoning models decide on what to do, calling actions like click, scroll and more. There are many models in that spectrum: ScaleCUA, Fara-7B, Jan-v2-VL, and Qwen3-VL. Qwen3-VL is a special case: it is a good model for agentic tasks, and, at the same time, other labs fine-tune it using their GUI control data.

In the following examples, we will work with one model of each type: Holo2 for localization and ScaleCUA for agentic control, so you can see how they differ in practice.

Using Holo2-Localization

Holo2-Localization is a spot-and-click model developed by H-Company and used with their agentic framework. It’s based on the Qwen3-VL-Thinking model and has three sizes:

  • 4B dense model

  • 8B dense model

  • Mixture-of-experts model with 30B total, of which 3B are active parameters

Let’s see how to use Holo2-Localization. Remember that the full code ready to run is available in the chapter notebook:

model = AutoModelForImageTextToText.from_pretrained(

Using ScaleCUA for agentic computer use
ScaleCUA is an agentic model capable of performing many actions when given a task. It’s based on Qwen2.5-VL, and comes in 3B, 7B, and 32B. It comes with its own configuration, so there’s a slight adjustment when loading the processor:
from transformers import (
    Qwen2_5_VLForConditionalGeneration,
    AutoTokenizer,
    AutoProcessor,
)

model = Qwen2_5_VLForConditionalGeneration.from_pretrained(
"OpenGVLab/ScaleCUA-3B", torch_dtype="auto", device_map="auto"
)
processor = AutoProcessor.from_pretrained(
"OpenGVLab/ScaleCUA-3B", min_pixels=3136, max_pixels=2109744
)

Vision browser example
Let’s tie everything together with a full browser agent. For this, we will rely on a ready-to-run web agent example that connects the ReAct loop to a real browser via Selenium and Helium. You can find the full code on the GitHub platform, but rather than walking through each line, let’s focus on the three pieces that make it work because they map directly to the loop you already know:
  1. The screenshot callback closes the observe step. After every ActionStep, the agent takes a browser screenshot and attaches it to observations_images. This is exactly the mechanism you saw earlier. Without this, the VLM is blind between actions:
    def save_screenshot(memory_step: ActionStep, agent: CodeAgent) -> None:
    sleep(1.0)
    driver = helium.get_driver()
    png_bytes = driver.get_screenshot_as_png()
    image = PIL.Image.open(BytesIO(png_bytes))
    memory_step.observations_images = [image.copy()]
    memory_step.observations = f"Current url: {driver.current_url}"
    One subtle detail: the callback also clears screenshots from steps older than two cycles. This keeps the context window from filling up with stale frames: a practical constraint you will hit with any multistep visual agent.
  2. The system prompt defines the action space. The agent’s system prompt teaches the VLM what browser primitives it can use: go_to(), click(), scroll_down(), close_popups(), and so on. These aren’t formal tool definitions: they are Helium library calls that the CodeAgent writes and executes as Python. The prompt also encodes practical heuristics: “stop after each click to see what happened,” “don’t try to log in,” “use web_search for Google, Helium for navigating sites.” These guard rails matter more than the code itself: they shape how the agent reasons.
  3. The outer loop is just agent.run(). The main function initializes a browser driver, creates a CodeAgent with a few tools (go_back, close_popups, web_search), and calls agent.run(prompt). From there, the ReAct loop you studied earlier takes over: the VLM sees the screenshot, writes Python to interact with the page, observes the result, and decides whether to continue or return a final_answer.

    Case Study: OpenClaw
    

    If you want to see what a “for-loop with tools and memory” becomes in production, OpenClaw is one of the most instructive open-source examples as of early 2026. Created by Peter Steinberger and released under the MIT license, OpenClaw became one of the fastest-growing GitHub projects in history, crossing 100K stars in weeks. It is not a chatbot: it is a local-first agent runtime that connects LLMs to real-world actions through messaging platforms.

    What you learned until now covers everything you need to understand its architecture (Figure 11-5).

    

    Here is how OpenClaw maps to the concepts in this chapter:

    

    Gateway as orchestrator

    

    A long-running daemon (the Gateway) acts as the agent’s control plane. It receives user messages (the TaskStep), optionally creates a plan (PlanningStep), and runs the ReAct loop: think → act → observe, writing results to memory at each step. The deterministic parts (session management, tool dispatch, permissions, run queuing) live in the Gateway, not in the LLM. This is exactly the principle you learned: agents handle the open-ended reasoning, and deterministic code handles everything else.


    Skills as versioned tool bundles

    

    OpenClaw’s “skills” are packaged, versioned bundles of tools that the agent can discover and invoke. This is essentially the tool classes from smolagents but with a registry (ClawHub) for sharing and installing. Each skill is defined in a SKILL.md file that specifies when and how to use it.


    Two-layer memory

    

    Long-term memory lives as editable Markdown files (MEMORY.md plus daily logs). Session transcripts are stored as JSONL. The agent can search its memory during the loop, which helps it maintain context across days and tasks.


    Model-agnostic

    

    OpenClaw works with any LLM provider (Claude, GPT, Gemini, DeepSeek, or local models through Ollama). The architecture separates the reasoning engine from the control plane.


    The security lesson

    

    OpenClaw is also a cautionary tale. Skills run in-process (trusted code), and the skill registry has already seen malicious submissions: researchers documented data exfiltration and prompt injection through third-party skills. The project’s maintainers warn that tool access, third-party extensions, and web content together create a security boundary you must design, not discover after deployment. If you are building agents that act in the real world, security should be part of the architecture.


    

    

    So far, every action our agents have taken happened in the digital world: clicking pixels, typing text, calling APIs. But the same observe-decide-act loop applies when the actions are physical: moving a robot arm, gripping an object, and pouring a liquid. The architectural leap from digital agents to physical ones is smaller than you’d think, and that’s where VLAs come in.




    

    Vision-Language-Action Models
    

    If agents are VLMs that act in the digital world, VLAs are their physical counterparts: models that look at a scene, understand an instruction, and move a robot arm to make it happen. The architectural leap is smaller than you might think! You are still running a VLM, you are still conditioning on instructions, and you are still generating outputs in a loop. The difference is that the outputs are joint angles rather than JSON tool calls, and the stakes of a bad prediction are a broken mug rather than a wrong API response. Let’s see how this works.

    

    Closing the Perception-Action Loop
    

    If you have made it to this section, you already know how to build a model that sees an image and talks about it. The question now is: can we make it do something? In Chapter 10, you learned about any-to-any models: architectures that handle multiple input and output modalities within unified systems. You saw three approaches: fully autoregressive models that discretize everything into tokens, hybrid models that use different generation strategies per modality (autoregressive for text, diffusion for images), and modular models that decouple understanding from generation. VLA models follow this same pattern: they take visual observations and language instructions as input (just like the omni-input models you have seen) and generate actions as output, typically using diffusion or flow matching…the same iterative refinement techniques used for generating images that you already learned about.

    Before diving into VLAs, you need to understand where they fit in the broader picture of robot learning. There are three main approaches to teaching robots, each with different trade-offs. These are split between explicit modeling (classical approach) and implicit modeling (learning based). See the diagram in Figure 11-6 and the details that follow.

    

    The classical approach decomposes the problem into three modules: perception (understanding the scene, typically using computer vision), planning (deciding on a sequence of actions), and control (executing low-level motor commands). The upside of explicit modeling is interpretability and predictable behavior: when something goes wrong, you can go back and see what happened block by block and troubleshoot. The downside is assumption debt: your perception assumes certain lighting and object properties, your planner assumes certain contact and geometry, and your controller assumes certain friction and latency. When you hit scenarios like a transparent bottle in a sink where perception fails to detect it, or an object that the robot grasps is unexpectedly fluffy rather than solid, the real scene violates those assumptions, and the pipeline can break. Classical approaches excel at high-volume pick-and-place of rigid parts on fixtures, or precision insertion tasks where the environment, geometries, and objects are known and tightly modeled. It fits very well in production plants where robots operate in controlled, stable environments.

    On the modeling-based side, we find two main approaches:

    

    Reinforcement learning (RL)

    

    You are already familiar with this! In robotics, RL excels at locomotion for legged robots, where fast simulation provides millions of cheap interactions. The downsides are hardware cost (real-world iterations break things) and reward design (when exactly do you give the robot credit?). RL shines when you have fast simulators and need nonintuitive strategies; it is less practical when you just need a robot to fold a shirt the way a human showed it.


    Supervised fine-tuning

    

    This is called imitation learning in the robotics world, and it is our path in this chapter. You show the system how to act via teleoperation: a human controls the robot with a controller to demonstrate a task, and you use this data to train a policy to mimic those demonstrations. VLAs complement imitation learning very nicely because they leverage pretrained vision-language knowledge: instead of learning to recognize objects and understand spatial relationships from scratch, they start with a foundation model that is already familiar with vision and language. This means you can train a capable policy (the function that decides what action to take given what the robot sees) from dozens to hundreds of demonstrated episodes (an episode is a task execution from start to finish) rather than the thousands of trial-and-error attempts that RL typically requires.


    

    This chapter focuses on imitation learning with VLAs because it’s the most accessible entry point. You can get started with simulation environments, standard hardware, and no RL infrastructure. The skills you will learn include recording demonstrations, converting data to standard formats, and training policies that transfer directly to physical robots when you’re ready. Let’s talk about all this in the following sections.

    

    Quick Robotics Glossary
    

    You will find that those terms appear throughout VLA papers and our book section. Refer back here as needed!

    

    Policy

    

    A function that maps what the robot sees to what it should do. In machine learning terms: a collection of observations -> actions.


    Proprioception

    

    The robot’s internal sense of its own body. In a robotic arm, that would be joint angles, velocities, and gripper state. This is the robot equivalent of knowing where your hand is without looking at it.


    Episode

    

    One complete task demonstration from start to finish—like one training sample, but temporal.


    Action chunk

    

    A sequence of future actions predicted at once (e.g., the next 10 joint positions) rather than one action at a time.


    Flow matching

    

    An iterative refinement technique for generating continuous outputs (like actions or images) by gradually denoising random vectors. You saw this in Chapter 10 for image generation. Here, it generates motor commands.


    Diffusion transformer (DiT)

    

    A transformer architecture trained with diffusion or flow matching, used as the “action expert” in many VLAs.


    Teleoperation

    

    A human controlling a robot with a controller or a leader arm to demonstrate a task. This is how VLA training data is collected.


    

    

    

    What VLAs actually do
    

    A VLA implements a policy: a function that maps observations to actions. The observation typically includes:

      

    • 

      Multi-view RGB images: for example, in a manipulator robot, we could have a base camera between the robot’s arms and wrist-mounted cameras on each gripper.


    • 

      A language task prompt: for example: “Stack the red block on the blue block.”


    • 

      The robot’s internal sense of its own state, also referred to as proprioception: for example, joint angles, joint velocities, and gripper position.


    

    The action is a set of controller set-points. This is a basic point that confuses many new practitioners in robotics. VLA outputs look like “joint 0 = 1.2 radians.” You are not sending a voltage to a motor. You are specifying a target position for a lower-level controller. The robot’s firmware handles the lower-level details to move the joint to that position. This abstraction makes policies more transferable: a policy trained on one manipulator can often transfer to another with similar kinematics, because you’re working in joint space rather than motor command space.

    Most modern VLAs don’t predict just one action but chunks of actions that you execute, and, after that, you reevaluate your planning. Think of reaching for a glass of water: you don’t recalculate your trajectory 50 times per second! There are two key reasons to act that way:

    

    Computational resources

    

    VLA inference requires diffusion or flow matching to generate actions. Those require multiple denoising steps—let’s say 5–10 forward passes through the network. If you predict one action at a time at a 50 Hz control frequency, you will need 250–500 inferences per second. By predicting 10 actions at once, you only need inference at 5 Hz, a 10x reduction in compute requirements.


    Asynchronous control

    

    While the robot executes actions from chunk A, the GPU generates chunk B in parallel. The control loop maintains an action queue. When the queue drops below a threshold (for example, five actions remaining), it triggers the generation of the next chunk. As long as the queue doesn’t run empty, the robot never stalls waiting for the model. Figure 11-7 shows an example of asynchronous control using an external service to return new actions given observations from the robot.

    


    

    

    

    Dataset requirements
    

    VLA relies to some degree on the same type of data as VLMs, with a cherry on top: imitation learning data. Imitation learning data is closer to controlled laboratory experiment data than web scraping. Let’s dig into this.

    As is the case with datasets for video language models, you will need good temporal alignment between multiple camera feeds and joint states at those same timestamps. A few dropped frames in a video dataset might be OK; in fact, sometimes we sample video at very low rates to annotate. In a VLA dataset, if your camera frame at timestamp t=1.5s gets paired with the joint angles from t=1.58s, you’re teaching your policy that this visual observation leads to those motor commands, but that’s wrong: the robot was already moving, and by giving a past frame, it will look as if it is not. Over hundreds of episodes, these small misalignments accumulate into systematic errors that make your policy unpredictable.

    You can’t learn to pour coffee from a single image; you would likely need to see it a few times. This means that to train a robot, you need complete task demonstrations from start to finish: picking up the pot, tilting it at the right angle, and stopping when the cup is full. Each episode might be 200 timesteps at 50 Hz (4 seconds), but you need hundreds of these episodes with variation in starting conditions. The mug should be in different positions, different orientations, and the coffee pot should start at different heights. Those variations prevent your policy from memorizing a single trajectory and failing when the mug is 2 cm to the left.

    What about validating data and corrupted samples? A corrupted frame in a video dataset is annoying. A corrupted joint angle reading—for example, a crazy glitch that reports joint 3 at 180° when it’s actually at 1.8 radians—teaches your robot to crash into walls. The verification pipeline must check that:

      

    • 

      All camera feeds recorded successfully at the expected framerate.


    • 

      Proprioception (joint angles, velocities) stayed within physically possible bounds.


    • 

      Actions were actually executed (the robot didn’t hit a limit or safety stop).


    • 

      All streams remained synchronized (no dropped packets, no clock drift).


    

    See the VLA data collection as a highly curated post-training data category. You need controlled environments, systematic variation of object poses, and verification that every data stream stays synchronized. Getting this right requires understanding not just machine learning but also robotics hardware, control loops, and how to build teleoperation systems that let humans guide robots through training demonstrations. The LeRobot framework (introduced in Chapter 4) standardizes much of this, but the fundamental challenge remains: VLA data collection is a calibrated experiment, not a web scrape.

    In “From VLM to VLA”, we will look under the hood to see what architectural changes occur when you extend a VLM to predict actions.

    

    

    

    From VLM to VLA
    

    You have seen what VLAs do from the outside. Now let’s open the hood. Architecturally, a VLA starts life as a plain VLM. The vision encoder produces image tokens, the text tokenizer creates language tokens, and the transformer blocks mix the two to learn visual semantics grounded in language. VLAs keep this backbone almost unchanged. π0.6, GR00T N1, and SmolVLA all reuse pretrained VLMs: Gemma-3 4B for π0.6, Eagle-2 for GR00T N1, and SmolVLM2 for SmolVLA.

    Datawise, the main difference lies in the input sequence, which now contains extra tokens. In general, you have 1-N image tokens per camera (often with token reduction to keep costs down), text tokens for the instruction (like “fold the orange shirt and stack it on the right”), and a few proprioception tokens encoding joint angles, velocities, and gripper state.

    So far, we haven’t discussed the elephant in the room:, the new piece in the architecture, the action expert.

    

    The action expert
    

    The action expert (also called action head) is usually a separate transformer trained with flow matching or diffusion to output a chunk of low-level actions: [aₜ, ..., aₜ₊ₕ₋₁]. This component runs at action frequency (e.g., 50 Hz), whereas the VLM runs slower and is often cached.

    Concretely, the pattern looks like:

      

    • 

      The VLM processes images, instructions, and proprioception to produce a sequence of hidden tokens.


    • 

      Those tokens then condition a diffusion or flow-matching network that predicts future actions.


    

    How is this brought to practice? In the “Action head” column of Table 11-3, you get a first overview. We will dig deeper during “Model Landscape Overview”.

    

    

    From input to output, step by step
    

    Most VLAs share a common processing pipeline, regardless of how they differ in architecture or training (see Figure 11-8).

    

    The common VLA pattern follows this sequence:

      

    1. 

      Encode the observation: the vision encoder processes images into visual tokens, the instruction gets tokenized into text tokens, and proprioception projects into a small set of “state tokens.”


    2. 

      Run the VLM once, concatenating all tokens and processing them through the VLM. Some models, like GR00T and SmolVLA, use middle-layer features instead of the final layer to make speed-versus-quality trade-offs.


    3. 

      Use caching to treat the VLM outputs as frozen context. During diffusion or flow-matching, these tokens remain fixed, and their key/value caches get reused across denoising steps. Only the action queries change from step to step, which keeps the per-step cost low.


    4. 

      Iterative action refinement happens through flow matching or diffusion. Starting from noisy actions or random vectors, the action expert runs for K steps: self-attention on action and state tokens, cross-attention to cached VLM tokens, then updating the actions a bit closer to the target. After K steps, you get a clean action chunk that’s pushed into the robot’s action queue. Chapter 10 already covered the mechanics of diffusion and flow matching, so here we simply note that actions are sampled by repeatedly denoising a short sequence of future actions, using the VLM tokens as conditioning. Figure 11-8 illustrates this complete flow from observation to action generation.


    

    That is the common recipe: pretrained VLM → cached context tokens → iterative action refinement via flow matching or diffusion. Now let’s see how three real models cook this recipe differently.

    π0.6: VLAs that learn from experience
    

    If you haven’t seen the video of a robot running this model preparing coffee, go for it! This is running π0.6, and that model is trained in two phases:

      

    1. 

      The training begins with an offline RL pretraining phase. Here, “offline” means that the model learns from a large, fixed dataset of previously recorded demonstrations rather than collecting new experience during training (as in standard “online” RL), and “pretraining” refers to the initial broad training stage before the model is specialized to a particular task. This phase uses tens of thousands of hours of multirobot data. The key innovation is learning not just what actions to take but which actions actually worked. A separate value function learns to predict how good each situation is. When an action leads to a better-than-expected outcome, it gets labeled “Advantage: positive.” When it disappoints, “Advantage: negative.” These labels condition the policy during training, so the model learns to favor actions that historically succeeded.


    2. 

      The system collects task demonstrations (for example, espresso making, diverse laundry, box assembly), runs the policy on-robot logging both successful and failed attempts, plus optional human interventions, retrains the value function and updates advantage labels, then fine-tunes the policy again with the “Advantage: positive/negative” token.


    

    Take a look at Figure 11-9 to see all the nuts and bolts in a single place. The result is a model that starts as a strong generalist, efficiently adapts to new tasks with a few hundred demos, and can then improve further through its own rollouts.

    

    π0.6 showed you a VLA that gets better through practice: learning from its own successes and failures after deployment. But what if your priority is not self-improvement but versatility across different robot bodies? That is the problem GR00T N1.5 was designed to solve.

    

    

    GR00T N1.5: Foundation VLA for humanoids
    

    GR00T N1 is designed as a foundation model for humanoid robots, and you can think of N1.5 as a refined, drop-in version of that recipe. Architecturally, it follows what NVIDIA called dual-system design. The VLM is an Eagle-2 that encodes the instruction and visual context at approximately 10 Hz. Middle-layer features are used for better speed and control quality. The action head is a DiT-based flow-matching policy that runs at high frequency (approximately 120 Hz), operating on action chunks and cross-attending to frozen VLM tokens plus embodiment-specific state encodings. Figure 11-10 illustrates this architecture.

    

    π0.6 needs a fleet of robots and thousands of hours of data. GR00T N1.5 requires NVIDIA-grade infrastructure for training and a Jetson module for deployment. If you have read about both and thought, “that’s impressive, but I just want to fine-tune a robot arm this weekend on my laptop,” you are exactly the audience SmolVLA was built for.

    

    

    SmolVLA: The efficient
    

    SmolVLA’s focus is on lightness: it can be trained on a single consumer GPU and deployed on very accessible GPUs. How is this achieved? Shaving size everywhere! SmolVLM2 is a very small VLM. In SmolVLA, they truncated it to use earlier layers to condition the action expert (faster, still good features), and they also achieve an aggressive token reduction via pixel shuffle to keep each frame to approximately 64 visual tokens.

    It is worth noting that the datasets used for training were developed by the LeRobot community. SmolVLA matches or beats much larger VLAs on several sim benchmarks and performs competitively with π0 (a predecessor of π0.6) while using a fraction of the compute.

    

    

    

    

    Summary
    

    You started this chapter watching VLMs answer questions. You are ending it with models that click buttons, browse the web, and move robot arms.

    On the agent side, you learned that agency is a spectrum: from simple tool selection to ReAct agents, and that the real design question is not “How autonomous can I make this?” but “Where does the open-ended reasoning actually live?” You built a toy agent with smolagents, watched the ReAct lifecycle unfold through TaskStep, ActionStep, and FinalAnswerStep, and saw how screenshots flow through observations_images to give computer-use agents their sight. You explored two flavors of CUA models: localization (Holo2) and agentic reasoning (ScaleCUA). And through OpenClaw, you saw what all these patterns look like when they grow up into a production system, including security headaches.

    On the VLA side, you discovered that the leap from “model that talks about images” to “model that moves a robot” is surprisingly small: freeze a pretrained VLM, add a diffusion transformer as the action expert, and let asynchronous chunked control keep the robot moving while the GPU thinks ahead. Three models showed you three different bets: π0.6 learns from its own mistakes, GR00T N1.5 generalizes across robot bodies, and SmolVLA proves you can do it all on a single consumer GPU with community-collected data.

    The thread connecting both halves? Observe, decide, act, observe again. Whether the action is a JSON tool call or a joint angle, the loop is the loop.

    Executive Takeaways:
    
              
      
                
    • Core Architecture: Explores OpenVINO Model Optimizer and Inference Engine (IE) integration with OpenCV.
                
    • Hardware Acceleration: Maximizes throughput on Intel CPUs, integrated GPUs, VPUs, and VPUs through heterogeneous plugin dispatching.
                
    • Model Zoo Pipelines: Streamlines pre-trained weights ingestion for face detection, image classification, and multi-modal computer vision inference.
              
    
            
    
          
    

          
          
    
            
            
            
    
              
              
    
                
    Q1: What is the primary role of OpenVINO Model Optimizer?
    
                
                
    
                  
    Answer: It converts trained models from frameworks (TensorFlow, PyTorch, ONNX) into Intermediate Representation (.xml network topology and .bin weights), performing layer fusion, precision quantization (FP32 to FP16/INT8), and dead-node elimination.
                
    
              
    

              
              
    
                
    Q2: How does OpenCV DNN module leverage OpenVINO Inference Engine?
    
                
                
    
                  
    Answer: By configuring net.setPreferableBackend(cv2.dnn.DNN_BACKEND_INFERENCE_ENGINE) and net.setPreferableTarget(cv2.dnn.DNN_TARGET_CPU), OpenCV routes layer computations directly through OpenVINO's optimized C++ kernels.
                
    
              
    
            
    
          
    

          
          
    
            
            
            
    
              
    API Pipeline Workflow:
    
              
      
                
    1. cv2.dnn.readNet(xml_path, bin_path): Ingests model topology and parameters into memory.
                
    2. cv2.dnn.blobFromImage(): Resizes input frames, scales pixel values, and converts from HWC to NCHW channel layout.
                
    3. net.setInput(blob) & net.forward(): Dispatches asynchronous inference to target hardware.
