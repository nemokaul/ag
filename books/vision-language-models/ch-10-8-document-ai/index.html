Learning Objective

In this chapter, you will learn how to solve many tasks that involve processing documents, picking the right model and technique for the right document task, and customizing document models for the task at hand.

Introduction to Document AI

Documents are one of the best examples of multimodal data: they have text, images, charts, and structured data (tables). On top of that, document contents are placed with a custom layout on top, making every document unique. Due to this, you need modern solutions to extract information from documents.

You can extract information from documents in various ways:

  • Directly asking questions to the model about documents without parsing them

  • Parsing documents into markdown format, and then processing with language models (RAG, etc.)

  • Doing simpler tasks: document classification, form field extraction, layout analysis

When asking questions about the document, the model can generate responses or can extract the exact answer from it. The difference here is called generative or extractive processing, respectively. We can even take this further by using a multimodal retrieval model to retrieve a single document from a stack of documents, then ask the question to the retrieved document and generate the answer. This is called multimodal retrieval-augmented generation (RAG).

For RAG, you need to parse everything into a format the model can understand, such as markdown. The texts are read with optical character recognition (OCR), tables are read into text-readable format (markdown, latex, html), charts and images are captioned, and formulas are rendered into mathematical expressions.

Let’s take a look at all the different ways we can process documents for different use cases.

Information Extraction

You can directly extract information from plain documents without converting them to plain text but staying in the image modality. This can be done through either generative or extractive processing. Generative information extraction is done with more generalist vision LMs trained on document understanding tasks. The models take a glance at the paper and generate a response.

Meanwhile, extractive processing is done with smaller and older architectures, where the answer is directly extracted. A small comparative example can be asking the question “What is the capital of France?” to a document that contains capital country matchings. A generalist model will say, “capital of France is Paris,” while an extractive model will just say, “Paris.” The latter model localizes and brings the answer, while the former generates an answer.

Let’s take a look at both.

Generative information extraction

Generative models understand documents and generate answers to queries. One example inference is shown in Figure 8-1.

Since they take a glance at the document and generate an answer, they are more prone to hallucinations and require better generalization capabilities.

Some of the Document AI tasks that can be solved with generative models are self-explanatory. In the machine learning community, we define the following tasks through their benchmark datasets, as those datasets helped develop these tasks. In their links, you can find the datasets for both training and testing:

  • Chart Question Answering (ChartQA)

  • Document Visual Question Answering (DocVQA)

  • Infographics Visual Question Answering (InfoVQA)

  • Scientific Diagram Question Answering (AI2D)

These tasks are often open-ended and better to be vibe tested for your model.

But not every document task requires open-ended generation. Sometimes you need to pinpoint an exact answer in the document, not generate a new one. This is especially if you need short answers, like column values, or your use case cannot bear any possibility of hallucination. That’s where extractive models come in.

Information extraction with understanding models

Extractive tasks, on the other hand, return a singular answer extracted from the text, are hallucination proof, and require no reasoning. Hence, which model you should use and the way you solve your task heavily depends on your use case.

Many modern VLMs can solve the generative document AI tasks out of the box. A good one is Qwen/Qwen3.5-2B, which you can try with pipeline or model inference with AutoModel API, as we showed in Chapter 1.

Document Parsing
Parsing documents into plain text (markdown) lets you process documents and build text-based applications. A good example is being able to pass the output text to large language models (LLMs) or text-to-speech models. As of this writing, we have both OCR-only models, which you can use to parse text-only PDFs, or complete document-to-text conversion models where charts and more are converted to text in different formats as well.
The OCR-only is mostly built with VLMs fine-tuned on transcribing text only. A good example of this is OlmOCR, built by AllenAI, as shown in Figure 8-4.

On the other hand, end-to-end markdown parsers render not only markdown but also include captions to images, figures, and charts. A good example is SmolDocling, built on the modern SmolVLM. It renders documents into a format called “DocTags,” as shown in Figures 8-7 and 8-8 (images taken from the paper “SmolDocling: An Ultra-Compact Vision-Language Model for End-to-End Multi-Modal Document Conversion”).
Think of DocTags like HTML tags: the output is represented with various tags like <picture> for image captions, <unordered_list> for unordered lists, or <otsl> (optimized table structure language) for tables. As a result, you can render and reproduce the exact PDF digitally.

As we have seen so far, there are many models, but how can we pick the right one? There’s no single best model, and it always depends on various factors, such as the task at hand. Is it information extraction, or is it OCR? What you want to use the output for also matters. Let’s see how we can pick the right model for the task at hand.
Picking the “Right” Model
Picking the right model for you can be tricky. If you have an extractive task, you can pick one of the older models, such as LayoutLM family, TrOCR or Donut. All of them are available in the transformers library and are relatively small. Since they are very small and old, you can host them yourself or use a cloud provider to host your fine-tuned model. This also depends on whether you have a dataset or not, as these models require fine-tuning before use. You can opt for labeling your dataset using a VLM and then fine-tune these models, as it will be more cost-efficient for serving on scale.
However, if you have a more sophisticated problem on hand that requires modern VLMs or parsing documents in general with modern VLMs specialized on OCR, you need to pick a model. How would you do it?
We need to evaluate the following:
  • Performance in accuracy-related benchmarks
  • Cost per page
  • Trade-off between the first two
Each modern VLM is evaluated by a benchmark. Some benchmarks are already saturated and are noisy, so evaluating one model against another on that specific benchmark makes no sense. For OCR, two go-to benchmarks are OmniDocBench and OlmOCRBench. Each model announces their evaluation based on these benchmarks. Many models are supported by both local serving frameworks, like vLLM or SGLang, or by AI providers. You need to take into account cost per million pages against how the model performs on benchmarks and pick a model and a provider (if not self-hosting) that serves the best trade-off. In Chapter 7, we learned optimizations you can do and the serving frameworks.
We’ve covered extracting information from documents and parsing them into machine-readable formats. The last core document task is retrieval: given a large collection of documents, finding the most relevant one for a given query. This requires a different kind of model altogether.
Multimodal Document Retrieval
Retrieval is the task of retrieving relevant documents given a question or a query, as shown in Figure 8-11.
Retrievers used to work for text or plain images where document AI use cases fall short due to the level of granularity document understanding requires. You might remember multimodal retrievers from Chapter 1, where we used SigLIP and retrieved artworks from text. The workflow is similar: first you index the documents and store the embeddings, and later during the inference, you run text query and get similarities. Although very efficient, models like SigLIP generally underperform compared to document retrievers.
Nowadays, there’s a variety of multimodal retrievers for documents, and we’ll discuss them based on the number of vectors they generate per document.
Primarily, there’s two approaches in document retrieval:
Single-vector models
Produce a single vector per document
Multivector models
Produce a single vector per token in the document, hence multiple vectors per document
First, we will go through the two architectures and discuss which one you should use and when, as well as the pros and cons of both. Then we will see how to infer and do RAG.
Architecture of single- and multivector models
Single-vector models are often simple dual text-image encoder models just like CLIP. However, instead of typical encoders, single-vector models employ VLMs and LLMs. The most popular one is Document Screenshot Embedding (DSE). Image and text query is fed to a VLM, and the same text query is fed to a language model. Then, you calculate cosine similarity between both models to get the final similarity.
It’s a very simple workflow illustrated in Figure 8-12 (taken from the paper by Xueguang Ma et al., “Unifying Multimodal Retrieval via Document Screenshot Embedding”). Another popular model is MCDSE, which supports multiple languages and advanced inference techniques like embedding shrinking with Matryoshka Representation Learning (don’t fret: we’ll go through this).
Multiple-vector models are a big leap forward in multimodal retrieval because of how well they perform. Similar to DSE models, they consist of a VLM and an LLM, with the difference that they output multiple vectors and have an additional operation called late interaction built to compute similarity for multiple vectors. We can define late interaction as keeping the token level embeddings and combining the image token embeddings and text token embeddings during retrieval. The similarity is calculated with the MaxSim operator: each query token embedding finds the best matching document token embedding, and then you sum the similarities and take the largest similarity.
ColPali is the most popular example to the multivector models, due to being the first ever model to use this technique (see Figure 8-13; taken from the paper “ColPali: Efficient Document Retrieval with Vision Language Models”).
The name ColPali comes from the PaliGemma model employed as the VLM. The technique was used many times with latest models like Qwen2.5-VL (ColQwen2.5). As more VLMs show up, more multimodal retrievers will show up too.
Differences between single-vector and multivector retrieval models
Now that you’re familiar with the architecture of these models, let’s discuss the upsides and downsides of each.
Single-vector models produce single vectors per document, and you calculate the memory the embeddings hold through #docs × dim × 4 bytes. For instance, if you store 1,024-dimensional vectors, 1M documents in 4 bytes, embeddings become 4 GB in FP32. This is very compact.
Multivector models produce single vectors per token, hence, multiple vectors per document. Here, tokens are technically image patches from the backbone, so the memory becomes: #docs × #tokens × dim × 4 bytes. In a similar example, 1M docs × 200 tokens × 128d → ~100 GB FP32, which is huge. The number of tokens also depend on the image patch size of the image backbone used in multivector models, which is often SigLIP as of the time of this writing. However, an embedding per token makes the accuracy go way up compared to single-vector models.
As per latency during indexing, single-vector models do a forward pass with both VLM and LLM, while multivector models encode multiple vectors. During retrieval, late interaction is much slower than simple cosine similarity as it calculates MaxSim between each query and image token separately.

Approaches in Solving Document AI Problems
We can divide methods to solve document AI as before and after the VLM boom. Early document AI models aimed to extract answers to questions and to classify documents and entities (e.g., form sections) inside the documents. After the VLMs emerged, solving open-ended problems such as generating answers to questions on complex documents with images, charts, and tables has become possible.
Early Document AI Models for Information Extraction and Document Classification
Early document models are quite different from generalist VLMs that we use today, but they’re still quite useful. They’re either completely encoder-based for document understanding or encoder-decoder-based for task conditioning or OCR.
These models can be used to:
  • Classify document types, like form, invoice etc.
  • Analyze document layouts, like texts, lists, tables, and figures.
  • Extract answers to questions asked to a document (in extractive manner, where you can see where the answer comes from).
  • Classify tokens in forms. Here the token type can be whatever you want to extract (e.g., address, full name, and form fields), and this depends on your dataset. A good example dataset for this is FUNSD dataset, an example of which is shown in the Figure 8-14, where the form name, form fields, and answers to the form are marked. This is very useful in many document AI use cases.
How these models solve these tasks depends on the architecture and how they represent the data, which you’ll see later on in this chapter.
Early document models also used to require OCR, and moving to OCR-free models was a huge leap forward. With that in mind, we divide early document models accordingly:
OCR-dependent models
These models take in the OCR output of the input document along with the input itself, and are dependent on the quality of the OCR. A good example is the LayoutLM series released by MSFT Research.
OCR-free models
These models came later, and they don’t require the documents to be processed by OCR. Good examples of these models are Donut by Naver Labs, Pix2Struct by Google, and Nougat by Meta.
Despite these categories, the models within them are quite diverse. Additionally, there’s not much standardization (especially the OCR-dependent ones). Hence, we will not cover them as much as we cover vision LMs.
Note
All of these models are very lightweight and fast, in contrast to many generalist VLMs, so it’s useful to use them if you’re solving a problem as simple as classifying documents or identifying the type of text in the document. VLMs are huge, with large amounts of data coverage, both in pretraining and post-training, so they’re like Swiss Army knives. The labs often shrink them or train smaller models (like SmolVLM!), but for now, they aren’t as small as a model like LayoutLMv3, which has only ~100M parameters and just works fine with fine-tuning for classification. So we suggest keeping this in mind as an option, since it can even be deployed to small devices.
Next, let’s look at the LayoutLMv3 and Donut models, and in the last part of the chapter, you’ll see how to fine-tune another model like LayoutLMv3, which is KOSMOS2.5.
LayoutLMv3
LayoutLMv3 is an encoder-only model. It encodes OCR text outputs, image patches from the document, and the layout (bounded box coordinates surrounding texts), and then combines them into a segment embedding. It’s heavily inspired by BERT: when it’s trained, part of the input image patch is masked while it tries to predict which text token is passing in which image patch. You can see how the architecture looks in Figure 8-15 (based on an example from the paper by Yupan Huang et al., “LayoutLMv3: Pre-training for Document AI with Unified Text and Image Masking”).
To accomplish different tasks with this model in the transformers library, you need to change the model head and fine-tune. For instance, fine-tuning with token classification looks like the following:
from transformers import AutoProcessor, AutoModelForTokenClassification
from datasets import load_dataset

model_id = "microsoft/layoutlmv3-base"
processor = AutoProcessor.from_pretrained(model_id, apply_ocr=False)
model = AutoModelForTokenClassification.from_pretrained(model_id,
num_labels=7)
Assuming you want to fine-tune on the FUNSD dataset, which has seven different token classes, you add num_labels=7 and initialize the model this way. The dataset itself has bounding boxes and OCR outputs, so you don’t need to pass apply_ocr as True.
You can run inference with LayoutLMv3 fine-tuned on the FUNSD dataset as follows. Assuming transformers and datasets are installed, we can load the test set of FUNSD and infer:

Donut
Donut is a generative document model. It’s a very simple OCR-free model that suffices for many simple tasks (see Figure 8-16; image taken from the paper “OCR-Free Document Understanding Transformer”). Essentially, it’s an encoder-decoder model (just like our modern VLMs!) that you can fine-tune to teach a specific task through text conditioning. For instance, the model learns how to classify documents with <classification> or how to do OCR with <parsing> tags in the prompts. The pretrained model is already good, and you can extend it through fine-tuning on your own dataset.

We’re interested in two parts of this dataset: images and pdf_cells. To visualize the dataset, let’s consider a generic function you can use to explore the dataset:
from PIL import Image
import matplotlib.pyplot as plt
from matplotlib.patches import Rectangle

def visualize_cells(img, pdf_cells, min_side=1.0):
    W, H = img.size

    cells = []
    if pdf_cells and isinstance(pdf_cells[0], list):
        for group in pdf_cells:
          cells.extend(group)
    else:
        cells = pdf_cells or []

    def clip_xywh(x, y, w, h):
        x1, y1, x2, y2 = x, y, x + w, y + h
        if x2 <= 0 or y2 <= 0 or x1 >= W or y1 >= H:
            return None

        x1 = max(0.0, x1)
        y1 = max(0.0, y1)
        x2 = min(W, x2)
        y2 = min(H, y2)

        if x2 - x1 < min_side or y2 - y1 < min_side:
            return None
        return x1, y1, x2 - x1, y2 - y1

    fig, ax = plt.subplots(figsize=(10, 12))
    ax.imshow(img)
    ax.set_xlim(0, W)
    ax.set_ylim(H, 0)
    for cell in cells:
        x, y, w, h = cell["bbox"]
        clipped = clip_xywh(x, y, w, h)
        if clipped is None:
            continue
        cx, cy, cw, ch = clipped
        ax.add_patch(Rectangle((cx, cy), cw, ch, fill=False, linewidth=1.5))

        ax.text(cx + 5, cy + 15, cell["text"], fontsize=8, va="center_baseline", 
        color="blue")

    plt.tight_layout(); plt.show()
    plt.close(fig)

This reveals so much about our dataset, and we will use all of this in our preprocessing function, so let’s unpack. First, we flatten the pdf_cells, because they are lists of lists of bounding boxes in the form of dictionaries, where each inner list might have variable numbers of dictionaries. Second, we have an additional function to clip the bounding boxes. This is because some bounding boxes can have negative x and y values, indicating the section might extend outside of the page. Last, there’s a min_side parameter. This eliminates the bounding boxes where the sides of them are shorter than min_side, as shown in Figure 8-18.

Here, we do everything we did in the visualization function. We now need to write our data collator, where we batch images together. Fine-tuning SmolVLM2 with TRL
Now, you will learn how to fine-tune VLMs on document VQA. This task is by default image + text input → text output, which is perfect for modern VLMs.
When solving problems like DocVQA, we pass the image to the processor as is, and format the input text prompt to be in the form of user and assistant conversation turns: “Answer this question: {question}” and append the answer. This way, we condition the model to solve the task at hand with a task phrase. Thanks to chat templates, this is made easy. You can adapt this to any task at hand.
Let’s begin. We will fine-tune SmolVLM2 using the TRL library, and track our experiments using trackio. num2words library is required for SmolVLM2, so we install that one as well:
pip install -q trl trackio num2words
